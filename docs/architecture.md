# Architecture

This document describes the design. Code that doesn't exist yet is marked as planned. [api.md](api.md) is the reference for every export, and [plan.md](plan.md), the development log, has the roadmap and the reasoning behind each decision. The library grew out of `demo/lab.html`, a single-file prototype; where a default comes from it, this document says so.

## Layers

```
          ┌──────────────┐
          │    core      │  clock, easing, tweens, motion modes, shared contracts, geometry, runner
          └──────▲───────┘
        ┌────────┴────────┐
 ┌──────┴──────┐   ┌──────┴──────┐
 │   charts    │   │   effects   │
 │ bar, line,  │   │ travel,     │
 │ donut, ...  │   │ wiggle, ... │
 └─────────────┘   └─────────────┘
```

Charts and effects both depend on core. They never depend on each other. Icons (`src/icons`) depend only on core too, and effects never import them: they look icons up by name through the run's context. They meet only through two shared contracts: the **mark geometry** and the **event stream**. Because charts and effects can't import each other, the types for both contracts live in core (`src/core/contracts/`), and so does the geometry math that charts use to build marks and effects use to draw (`src/core/geometry/`).

## Core

`src/core` depends on nothing else in the library and doesn't touch the DOM at import time, so the package can be imported in Node. Browser APIs (`requestAnimationFrame`, `matchMedia`) are looked up only when first used, and both can be injected.

### Clock

`createClock(source?)` runs one shared frame loop for the whole page. It requests a frame only while something is subscribed, so an idle page costs nothing. Outside the browser it falls back to a 16 ms timer. `defaultClock` is the page-wide instance. `manualClock()` only moves when a test calls `advance(ms)`, which makes every timing test deterministic.

**Driving it in a real browser.** The screenshot tests in `tests/visual/` need frames at exact times on a real page. They use Playwright's fake clock rather than a hook in the library. `page.clock` replaces `performance.now()` and `requestAnimationFrame` before any page script runs, and `defaultClock` looks both up only when it asks for a frame, so `page.clock.runFor(ms)` drives the page-wide clock directly. That keeps the public API as it is: no `setDefaultClock()` and no flag in the demo (`expressive-charts/testing` runs effects on manual clocks of its own, never the page's). Two details make the frames repeatable. The fake clock's frames fall every 16 ms. And each test moves the clock to the same reading before it acts, because a page starts at however much real time passed while Playwright installed the clock.

### Easing

An easing is any `(t: number) => number`. Built in: `easeInOutCubic` for data transitions, `easeOutCubic` for travel and for retargeted animations, and `linear` for playback.

### Tweens

```ts
tween({ duration, timing?, ease?, delay?, update, signal? }, env?) // → { finished, state, cancel(), finish() }
```

- `update` gets eased progress: once with `ease(0)` straight away, then on every frame, then once with `ease(1)` at the end.
- `finished` resolves to `"done"` or `"cancelled"` and never rejects, so rapid hovering can't cause unhandled rejections.
- `cancel()` stops where it is. `finish()` jumps to the end. Aborting `signal` cancels.
- If the motion mode scales the duration to 0, `update(ease(1))` runs synchronously, before `tween` returns.
- If the effective mode turns off while a tween runs (the device switches to reduced motion, or the viewer picks Off), the tween jumps to its end on the next frame.
- If `update` throws, including on the final update, the tween cancels itself and the error is reported once. `finished` never says `"done"` when the last update failed.

### Animated values

```ts
const length = animated(0, interpolateNumber, { onChange });
length.to(16, { duration: 500 });      // → Promise<"done" | "cancelled">
```

An `Animated<T>` is a value that can be retargeted mid-flight. `to()` cancels whatever is running and starts from the current in-between value, so nothing jumps. When it interrupts a moving value and starts at once, the default ease is ease-out rather than ease-in-out, because restarting an ease-in from a moving value makes the motion stall. A value still waiting out a `delay` isn't moving, and a new animation with a `delay` starts from rest after it, so both of those ease in and out. `set()` jumps, and `stop()` freezes in place. `target` equals `value` whenever it's at rest, including after a cancellation from outside (an aborted `signal`, or an `onChange` that throws). The interpolators provided are `interpolateNumber`, `interpolatePoint` and `interpolateRecord`. `interpolateRecord` grows keys that appear from 0 and shrinks keys that disappear to 0, which suits stacked segments.

### Motion modes and duration scaling

The modes are `presentation`, `analysis` and `off`. Every duration in the library passes through `motion.duration(base, timing)`, which scales it by the effective mode and by what the duration is for:

| Timing | Used for | Presentation | Analysis | Off |
| --- | --- | --- | --- | --- |
| `feedback` | hover colour and dimming | base | base | 0 |
| `transition` (default) | data changes | base, staged | base × 0.35, max 200 ms | 0 |
| `effect` | travel, wiggle, flash, pulse, trace | base | base × 0.35, min 140 ms, max 300 ms | 0 |
| `playback` | auto-play such as "Play season" | base | base × 0.3 | 0 |
| `stagger` | the wait before each mark of a [`stagger`](#stagger) | base | 0 | 0 |

A rule is `{ factor, min?, max? }` and gives `clamp(base × factor, min(base, min), max)`, so a floor never makes an animation longer than its base. `createMotion({ scaling })` accepts partial overrides. `motion.staged` is true only in presentation, and it tells charts to split data changes into stages: values first, then positions.

### Reduced motion

```
effective mode = viewerChoice ?? (prefersReduced ? "off" : requested)
```

- `setMode(mode)` is the page author's default. It never overrides `prefers-reduced-motion`.
- `chooseMode(mode)` is for on-page controls the viewer operates, like [`motionSwitch()`](#controls). The viewer's own choice does override the device setting. `clearChoice()` goes back to following the device.
- `prefers-reduced-motion` is followed live. `subscribe()` notifies on any change and watches the media query only while someone is listening.

`motion` is the page-wide instance every chart follows unless it's given its own.

## Mark geometry

Every mark, whether it's drawn by one of our charts or by another library, is described with the same `MarkGeometry` shape (`src/core/contracts/geometry.ts`). It has two parts:

- **The walk**, from where the data starts to where it ends: `start`, `end`, `length`, `path(t)`, `angle(t)` and `slice(t0, t1)`, with `gaps` where a line has no data ([below](#gaps)).
- **The body**: `thickness`, `outline`, `bounds`, `center`, `pivot`, plus ordered `segments` for stacks, `labelBounds`, the boxes of the mark's own labels ([below](#the-marks-own-labels)), and `nearbyLabels`, the boxes of other marks' labels near it ([below](#other-marks-labels-nearby)).

For a bar, the walk is the centre line from the baseline to the tip. For a donut slice, it's the mid-radius arc. For a line, it's the line itself. That's what lets one `travel` effect roll a ball along all three. Any other library's path, a curve or an area, is described as a line or as an area with no direction ([Shapes](#shapes)).

### Conventions

- **Space.** Chart pixels: the origin is the chart's top-left corner and y points down. Effects draw their overlay in the same space.
- **Angles** are screen angles: radians, 0 along +x, positive turning clockwise on screen, as `Math.atan2` gives in chart pixels. `angle(t)` is the direction of travel, in (−π, π].
- **Arc length.** `path(t)` is uniform in distance: `t = 0.5` is halfway along the walk on screen, not halfway through the data. Values of `t` outside [0, 1] are clamped. `length` is exact, for arcs too.
- **Up side.** "Up" is the left of the direction of travel, `angle − π/2`. For a bar growing right that's screen up; for a column, screen left; for a negative bar, screen down; for a donut slice walked clockwise, outward.
- **Outline sampling.** A closed outline's `sample(n)` takes n a multiple of 4 and returns n/4 points per side, evenly spaced along each side, clockwise on screen from the start-left corner: the left side (walked in the direction of travel), the end, the right side, then the start. A closed shape has no sides, so its quarters are of equal length, from its upper left. Corners land at indices 0, n/4, n/2 and 3n/4 for any n, so morph can match marks corner to corner. An open outline (a line) returns n points along the stroke, from start to end inclusive.
- **Slices.** `slice(t0, t1)` is SVG path data for that part of the walk, with its ends in either order; equal ends give a bare move that draws nothing. It leaves out the walk's gaps.
- **Path data** uses absolute `M`, `L`, `A` and `Z` only, with numbers rounded to 0.001 px. Arcs are split into pieces of at most half a turn, so a full ring still draws.
- **Missing vs zero.** A series that isn't in the stack has no segment. A zero value gives a segment with `length` 0. Effects treat both the same: a walk shorter than 0.5 px finishes at once and draws nothing.
- **Keys.** Segments are keyed `"<mark key>/<series>"`, or `"<mark key>/<index>"` when they have no series.

### Builders

The builders are public. Our charts and the adapters use the same ones, so a bar is described the same way whoever drew it. Bad input (a negative width, a `NaN`) throws a `RangeError` that names the builder and the field.

| | `describe.bar` | `describe.arc` | `describe.line` | `describe.point` | `describe.shape`, open | `describe.shape`, closed |
| --- | --- | --- | --- | --- | --- | --- |
| Input | rectangle, `baseline`, `radius`, `segments`, `gap` | `cx`, `cy`, `inner`, `outer`, `start`, `end` | `points`, `breaks`, `width` | `x`, `y`, `r` | `d`, `matrix`, `width` | `d`, `matrix` |
| Walk | middle of the baseline edge → middle of the tip | start angle → end angle on the mid-radius arc | first point → last point | none: length 0 at the point | along the path, a gap at each later move | none: length 0 at the centre |
| `angle` | 0, π, −π/2 or π/2 by baseline | the d3 angle (the arc's tangent) | per leg | 0 | per piece | 0 |
| `thickness` | across the bar | `outer − inner` | `width` (default 1, SVG's default) | `2r` | `width` (default 1) | the smaller of its width and height |
| `outline` | rectangle with a rounded tip | annular sector | the stroke, open, less its gaps | circle | the stroke, open, less its gaps | the whole path, holes too |
| `pivot` | middle of the baseline edge | the donut centre | first point | the point | first point | the centre |
| `segments` | at least one | none | none | none | none | none |

```ts
describe.bar({ key: "Okafor", x: 0, y: 0, width: 220, height: 22, baseline: "left", radius: 4, gap: 2,
  segments: [{ series: "goals", size: 160 }, { series: "assists", size: 60 }] });
describe.arc({ key: "Saved", cx: 0, cy: 0, inner: 70, outer: 116, start: d.startAngle, end: d.endAngle });
```

- **Bars.** `baseline` is the edge the bar grows from: `left` and `right` for horizontal bars (`right` for negative values), `bottom` and `top` for columns. `radius` rounds the two tip corners only; the baseline end stays square. `segments` are ordered from the baseline, each `size` px along the walk. A plain bar gets one segment named after its `series`, so `travel(…, { along: "goals" })` works whether or not the chart is stacked.
- **Gaps between segments.** The `gap` comes out of the start of the later segment, so every segment still ends at its value. It shrinks when the segment before it is shorter, and the tip rounding fades in as a segment nears the tip, so a stack that grows or shrinks never jumps. The whole bar's outline is the full rounded rectangle, gaps included.
- **Slices** use the `d3.pie()` convention: radians, 0 at 12 o'clock, clockwise. So pie output plugs straight in, and `angle(t)` equals the d3 angle. As with `d3.arc()`, radii given the wrong way round are swapped and more than a full turn draws one ring. If `end < start`, the walk runs anticlockwise and its up side is inward; the outline is still clockwise.
- **Shapes** are any SVG path data, which the library follows itself ([below](#shapes)).

### The marks' own labels

`labelBounds` is optional: the boxes of the text the chart draws for the mark, in the mark's coordinates, so an effect that draws text can keep clear of them. It's an addition under the 0.x promise: code that builds a `MarkGeometry` needs no change, and an effect that ignores it works as before.

- **What our charts give.** A bar: its category label and its value label, in that order, for bars and columns either way, each only when it's drawn ([thinning](#bar-chart) leaves out labels that would overlap). A slice: the two lines of its label outside the ring, its category then its share, or an empty list when the label is dropped. A line: its end label, or an empty list when its text is `""`. A stack's segments, a line's points, and a line with `labels: false` have none: the field is unset.
- **How they're worked out.** Each layout boxes a label as it places it, so a box is where the label is drawn in every frame of a change, a reveal and a resize. Nothing is read from the DOM. A box is the label's measured width (`src/charts/render/text.ts`) and 0.16 em more at either side (a W's lean, an f's hook), from 1.05 em above its baseline (an accented capital's top) to 0.25 em below it (a descender's foot). So in Chrome a box holds the label's `getBBox()` with Segoe UI, Arial, Georgia, Verdana and Consolas; a Times New Roman "ff" reaches 0.8 px past it. Chart text has tabular digits, so a label is measured with its digits as 0s: one that counts through values while a change plays is measured once for each shape, not each frame.
- **They follow.** A mark whose boxes moved counts as changed, so its runs hear `onChange` even when the mark itself didn't move: a line's end label pushed aside by another's, or one whose text changed.
- **The builders** take `labelBounds` and pass it through as given. A box with a coordinate that isn't finite, or a negative size, throws a `RangeError` that names the builder and the field.
- **Host marks.** The library doesn't know where a host's labels are, so marks `expressive()` reads from rects, circles and shapes, and `fromVegaView()`'s, have none. A page's `geometry` can give them, and `expressive()` keeps them; a `refresh()` that moves them counts as a change.
- **Who reads them.** [`delta` and `label`](#delta-and-label) put their text past them.

### Other marks' labels nearby

`nearbyLabels` is optional too: the boxes of other marks' text near this one, in the same coordinates, which an effect's text should keep clear of as well as its own. `labelBounds` stays the boxes of the mark's own. Unset means none is known. It's an addition under the 0.x promise, as `labelBounds` is (M10 decision 11).

- **What our charts give.** A line: every other line's end label, in series order, leaving out one whose text is `""`; a line alone has an empty list. A slice: every other slice's label (both lines of each), in the slices' order, since they all sit round the one ring, and text that goes past a neighbour's label can meet the next one round; a slice alone has an empty list. Until M11 a slice had only the nearest label each way round, and on random donuts a slice whose label was dropped could put its text on a label two slices away. Bars give none: a bar's text goes past its own end, where no other bar's label is. A line's points, a line with `labels: false` and a stack's segments have none.
- **They follow,** as `labelBounds` does: a mark whose neighbours' boxes moved counts as changed, so its runs hear `onChange` when another line's end label moves or goes, though its own line didn't move.
- **The builders** take `nearbyLabels` on every spec and pass it through as given, checked as `labelBounds` is: a `RangeError` names the builder and the field, such as `describe.arc: nearbyLabels[1].width`.
- **Host marks** have none, as they have no `labelBounds`. A page's `geometry` can give them, and `expressive()` keeps them.
- **Who reads them.** [`delta` and `label`](#delta-and-label) go past them too, but never turn for them.

### Gaps

`gaps` is optional: the stretches of the walk with no data, as `[from, to]` values of `t`, in order and apart (each `0 ≤ from < to ≤ 1`, ending at or before the next starts). A line that skips a value has one, from the value before to the value after. Unset means none. It's an addition under the 0.x promise: code that builds a `MarkGeometry` needs no change, and no mark has gaps unless a line skips a value.

- **The walk runs straight across a gap**, from the last value before it to the first after, so `start`, `end`, `length`, `path(t)` and `angle(t)` work as on any walk, and `t` is still in proportion to distance, gaps included. `outline.sample(n)` runs along the whole walk too.
- **The stroke leaves them out.** `slice(t0, t1)` writes each part between the gaps from its own move, so a gap is a move across it. A part with no length isn't written, and a slice that's all in a gap is a move where it starts, which draws nothing. An open outline's `d` is `slice(0, 1)`, so a halo and a focus ring leave the gaps out too.
- **Gaps are only between values.** A missing value before a line's first or after its last isn't on the walk, which starts and ends at values. The gaps either side of a value alone touch, and it has no stroke.
- **`describe.line({ breaks })`.** `breaks` are the indices of the points that start a new run: a gap from `points[i − 1]` to `points[i]`. Each is a whole number from 1 to the last index, in order, with no repeats; anything else throws a `RangeError` that names it (`breaks[1]`). A break between two points in the same place leaves no gap, since there's nothing between them. A page describes a D3 line drawn with `.defined()` by its defined points and the indices where they break, as `src/conformance.test.ts` does.
- **Data.** `Sample.gapBefore` is `true` on the first sample after a gap, so a data effect doesn't join it to the one before. `samplesAlong()` sets it from the mark's gaps, on the first sample past each gap's middle: a gap's ends are values, so samples there land within float noise of them, either side. `expressive()` keeps it on the samples a page gives, and throws a `RangeError` if it isn't `true` or `false`.
- **Effects.** One that draws along the walk with `slice()`, or along the outline, skips gaps with no change: `trace`, `threshold`, and the halos of `pulse` and `flash`. `wiggle` reads only the outline's samples and the pivot. One that draws its own path from `path(t)` would draw across a gap, so the [effects guide](effects-guide.md#drawing-along-a-walk-with-gaps) says to draw with `slice()`. [`travel`](#travel) jumps across a gap, and [`threshold`](#threshold) doesn't interpolate across a `gapBefore`. `delta` and `label` read `end` and `angle(1)`, the last value's. No built-in effect draws inside a gap, and both conformance sweeps check it on every frame ([Testing effects](#testing-effects-without-a-dom)).
- **`morph` keeps them.** Between two lines the stroke inside a gap of the old line fades in as it goes, and inside a gap of the new line fades out, so nothing is drawn inside a gap both have ([morph](#morph)). Two lines that each run one way across x pair by x, so two missing the same x's have their gaps in the same place; any other two are sampled along the outline, which runs along the whole walk. Its first and last frames are the outlines' own, gaps left out.
- **Who gives them.** `describe.line` with `breaks`: a host's line through `expressive()`, and [`lineChart`](#missing-values)'s lines where a value is missing. And `describe.shape`, at each later move of an open shape, so a D3 line drawn with `.defined()` is described from its own path data ([Shapes](#shapes)), as `expressive()` reads a `<path>` and `fromVegaView()` a line Vega draws as a curve.

### Shapes

`describe.shape({ key, series, d, matrix, width, labelBounds })` describes any SVG shape from its path data, so a D3 curve, a D3 area or another library's path keeps the same contract as our marks. `expressive()` reads `<path>`, `<line>`, `<polyline>`, `<polygon>` and `<ellipse>` elements with it ([Adapters](#adapters)), and `fromVegaView()` a line Vega draws as a curve ([Vega and Vega-Lite](#vega-and-vega-lite-fromvegaview)). The library follows the path itself, with no DOM, so it's the same in Node, jsdom and every browser. (The design session's sketch walked an element with the browser's `getPointAtLength`, which jsdom doesn't have.)

- **Reading.** `d` is read as SVG reads it, up to its first error, by the reader `iconFromSvg` uses (`src/core/geometry/path.ts`): every command, relative or absolute. `matrix` moves it into the marks' px, as an element's transform does, and an arc's ellipse moves with it. A move with nothing after it draws nothing, and is left out.
- **Open or closed.** A subpath is closed when it ends with `Z`, or where it started, as `d3.arc()` draws a full ring's outer edge. A shape is closed when every subpath is, and one has some length; otherwise it's open. So a path of points alone, as d3 draws a value alone between gaps (`M400,-25Z`), is open: a line with nothing to stroke.
- **Flattening** (`src/core/geometry/flatten.ts`). A walk is made of straight pieces and circular arcs. So straight pieces stay straight, and an arc whose radii are equal after `matrix` stays an arc. A Bézier, or an arc of an ellipse, becomes straight pieces at equal steps of its parameter, enough that each stays within 0.1 px of the curve: between steps h apart, a piece strays at most h²/8 times the curve's largest second derivative. The pieces end exactly at each curve's ends, so a point the page drew, such as a value on a `curveMonotoneX` line, is on the walk, where `samplesAlong` finds it. One curve makes at most 10,000 pieces, which keeps the 0.1 px for curves up to millions of px across. The line chart's [curve](#curves) flattens its pieces by the same bound (`cubicPieces`).
- **An open shape is a line.** Its walk runs along the path from its first point. Each later move starts a new run after a gap, from where the pen was to the move, so a D3 line drawn with `.defined()` comes with its gaps, with no `breaks`. A move to where the pen already is leaves none. Its outline is the stroke, less the gaps, and its `thickness`, `bounds`, `center` and `pivot` are as `describe.line`'s. A straight D3 line gives the same mark as `describe.line` with its points and breaks.
- **A closed shape has no direction**, like a point: its walk is its bounds' centre, with length 0. So `travel` and `trace` do nothing on it, and `flash`, `pulse`, `wiggle` and `morph` work on its outline. Its centre and pivot are its bounds' centre, and its `thickness` is the smaller of its width and height. Its bounds are the path's, with no stroke.
- **A closed shape's outline** is the whole path, holes too, flattened as the walk is, so path data still has only `M`, `L`, `A` and `Z`. `sample(n)` goes round the longest subpath (a ring's outside), clockwise on screen, in four quarters of equal length from its upper left: the point with the least x + y, and of two, the higher. So a circle's corners are where `describe.point`'s are, and a rectangle samples the same however its path is written. Its `d` starts there too, with the longest subpath first, clockwise. If the longest runs anticlockwise, every subpath is written the other way round, which fills the same under either fill rule, so a hole stays a hole. A subpath with no length is left out of it.
- **Errors.** Path data with nothing to draw (no move, or moves alone) throws a `RangeError` naming `d`, and so do coordinates that `matrix` takes past the largest number. So do a `matrix` that isn't six finite numbers and a `width` that isn't a number of px more than 0, each naming its field.
- **Checked** in `src/conformance.test.ts`: every built-in effect on a D3 curve, the same with missing weeks, a D3 area and D3 rings (areas with holes), each described with `describe.shape`, and on the curves, the area, the other shape elements and turned rects read by tag, with nothing drawn inside a gap; and `morph` between shapes, from a shape to a bar and a slice, and between two rings and from a ring to a dot, holes and all. No fixture is a shape, so `FixtureName` is as it was.

### Geometry helpers

For effect authors, and public (the [effects guide](effects-guide.md) covers them):

```ts
matrix.translate(x, y); matrix.rotate(radians, about?); matrix.scale(sx, sy?, about?);
matrix.multiply(a, b, c);  // like the SVG transform list "a b c": c applies first
matrix.apply(m, point);
offset(point, angle, distance); // offset(mark.end, mark.angle(1) - Math.PI / 2, 8) is 8 px to the up side of the tip
```

A `Matrix` is `[a, b, c, d, e, f]` in SVG order. Positive rotations turn clockwise on screen, like SVG's `rotate()`.

`samplesAlong(mark, points)` is public too, for pages that give host marks their samples (see [Adapters](#adapters)).

The rest of `src/core/geometry` is internal: path segments (lines and circular arcs), walks parameterised by distance, outlines with canonical sampling, path-data writing, reading any path data and flattening its curves, shape elements' outlines as path commands (`shapeOutline`, shared by `iconFromSvg` and the adapter), and reading SVG transform lists (`parseTransform`, `invert`, shared by `iconFromSvg` and the adapter). Charts and effects inside the library use it directly.

## Events and effect slots

Charts and adapters emit `enter`, `update`, `exit`, `hover` and `leave` (the [bar](#bar-chart), [donut](#donut-chart) and [line](#line-chart) charts and [`expressive()`](#adapters) do), each a `MarkEvent`: the mark's geometry, its data and its position in the batch. An `update` event also carries the previous geometry (`from`), and a `hover` event its `source` (`"pointer"`, `"touch"`, `"keyboard"` for focus, or `"linked"` for a [linked hover](#linked-hover)) and the `segment` under the pointer. Data events fire when a change starts: `enter` and `update` with the new geometry, `exit` with the geometry on screen. `hover` and `leave` carry the geometry on screen too, which is part way to the new one while a change plays. `chart.on(type, listener)` and the effect slots consume the same events. Effects attach to events through the `on` option, typed `EffectSlots<D>` (`src/core/contracts/slots.ts`); each slot takes an effect or a preset name:

```ts
import { sport } from "expressive-charts/icons/sport";

registerIcons(sport); // the sport pack's icons, by name; the examples below assume it too
barChart("#goals", { data, label, y: "name", x: "goals", on: { hover: travel("soccer-ball"), update: "flash" } });
```

| Slot | Runs | Until |
| --- | --- | --- |
| `hover` | on pointer hover or keyboard focus | leave; cleared during a data transition and replayed after it |
| `enter` | when a mark appears | it re-triggers, or the mark exits |
| `update` | when a mark's values change, as the transition starts (not on a re-sort alone) | it re-triggers, the chart's next update, or the mark exits |
| `exit` | before a mark is removed; removal waits for it | it finishes, and the mark goes |
| `decorate` | from enter, for persistent effects like `threshold` | the mark exits; it redraws on every geometry change |

**The chart's next update** ends every `update` run, on the marks it changes and on the ones it leaves alone, so what an update explained goes with it: a `flash` still playing stops, and a `delta` goes. An update is:

- a chart's `update()` with `data`, even if no value changed: a matchweek where nobody scores gives new rows with the same values, and last week's "+1" goes;
- a chart's `update()` without `data` that changes a value or adds or removes a mark (new `series`, say);
- an attachment's `refresh()` that finds a new row, a new value, or a mark entering or leaving.

So `update({ on })` alone, a re-sort, a resize, a line's `reveal()`, and an attachment's read that finds nothing new (a Vega render for a hover signal, or a resize) keep them. Something meant to stay past the next update goes in `decorate`.

## Effects

The effect interfaces and the drawing API are built as types (`src/core/contracts/`), and the [runner](#runner) drives them. The effects [`travel`](#travel), [`flash`](#flash), [`wiggle`](#wiggle), [`pulse`](#pulse), [`trace`](#trace) and [`drawIn`](#drawin), the data effects [`threshold`](#threshold), [`delta` and `label`](#delta-and-label), the transition effect [`morph`](#morph), and the combinators `sequence`, `parallel`, `only` and [`stagger`](#stagger), are in `src/effects/`.

There are three kinds, distinguished by a `kind` field:

- **Geometry effects** (`GeometryEffect`) receive a `MarkGeometry`.
- **Data effects** (`DataEffect<D>`) also receive the mark's `MarkData<D>`: values along the walk, related series and the previous values. Their `run`, `end` and `clear` are function-typed properties rather than methods, so TypeScript checks the row type strictly and an effect that needs fields a chart's rows don't have is a type error.
- **Transition effects** (`TransitionEffect`) receive two geometries, `run(from, to, ctx)` and `end(from, to, ctx)`, on a [`TransitionContext`](#transition-effects) (`morph`). They can't be used where a mark effect is expected.

Each one has `run`, `end` (the final state, used for reduced motion) and `clear`. Effects are stateless: one effect object can run on many marks at once, and per-run state lives on the `EffectContext`:

| Field | What it is |
| --- | --- |
| `signal` | Aborted on leave, re-trigger, data update or destroy |
| `motion`, `tween()` | The motion view, and tweens with the clock, motion and signal already bound |
| `mark` | Restyles the mark itself |
| `layer` | This run's own overlay group, above the marks (on a line chart, above its lines and below its points) |
| `icons` | Resolves icon names |
| `batch` | The mark's position in a multi-mark event, for stagger |
| `onChange()` | Called when the geometry moves |
| `previous` | The geometry before this update, on update events |

### Transition effects

A transition effect plays between two views of the same mark: `run(from, to, ctx)` turns `from` into `to`, `end(from, to, ctx)` draws the final state at once (motion off), and `clear(ctx)` does any extra cleanup. A run resolves when it's done or aborted, leaving its end state drawn until it's cleared. Its context, `TransitionContext`, is an `EffectContext` with one more field:

- **`start`**, from 0 to 1: where the run begins, in the effect's own progress (morph's is the shapes' eased progress). 0 plays it all. A switch back mid-way plays the reverse pair from 1 minus the progress the first had reached, so an effect that honours `start` retraces; one that ignores it replays from its beginning.
- **`mark` does nothing and `onChange` never fires.** Both views' marks are hidden while a transition plays, so there's nothing to restyle, and a resize mid-switch lands it rather than moving its shapes. `previous` isn't set: `from` is the previous geometry.

The [transition player](#playing-transitions) plays them with the runner's rules. `checkTransition` in `expressive-charts/testing` checks one (see [below](#testing-effects-without-a-dom)). `TransitionEffect` and `TransitionContext` are under the 0.x promise, with the other contracts.

### Writing effects

Effects written outside the library are made with `defineEffect(spec)` and `defineDataEffect<D>(spec)` (`src/effects/define.ts`). A spec is the effect without its `kind`, with `clear` optional. Each fills in the kind and a `clear()` that does nothing, throws a `TypeError` unless `run` and `end` are functions (every effect needs an end state, for reduced motion), and freezes the result, keeping only `run`, `end`, `clear` and, for data effects, a frozen copy of `needs`. `DataEffectSpec<D>`'s functions are properties, as on `DataEffect`, so a spec that reads fields `D` doesn't have is a type error. The [effects guide](effects-guide.md) is the author's documentation: the contract, the context and drawing API, timing, end states, the data guardrails, data effects, composing, testing with `checkEffect`, transition effects and `checkTransition`, worked examples and a review checklist. A transition effect is written as a plain object of kind `"transition"`: there's no definer for it. This API, with `matrix`, `offset`, `describe.*`, the contracts and `expressive-charts/testing`, is under the 0.x promise in [CHANGELOG.md](../CHANGELOG.md).

### travel

```ts
travel(icon, { along?, gait?, size?, orient?, ride? }) // icon: an Icon, or a registered icon's name
sequence(travel(soccerBall, { along: "goals" }), travel(cleat, { along: "assists" }))
```

`travel` carries an icon along the mark's walk, or along one segment, and leaves it resting at the end. It reads only the walk, `thickness` and `segments`, so the same effect rolls a ball out a bar, around a donut slice and along a line.

- **Where.** `along` names a segment's series; a mark with no segments counts as its own one segment. A missing segment, or a walk shorter than 0.5 px, makes it a no-op: nothing is drawn and it finishes at once. The icon is inset by its footprint so it stays inside the mark. If the walk is shorter than the footprint, the icon rests at the start without moving; on a very short walk it carries on past the end rather than covering the baseline.
- **How long.** The base duration is `max(260 ms, distance ÷ 360 px/s)`, with `effect` timing, times the gait's `pace`, and at most 4 s. The cap comes after the pace, so past 1,440 px at pace 1 (about 1,250 px for a step) the icon goes faster, not longer. With `stagger`'s longest spread (500 ms) in front, a trip still ends within 5 s, so it never needs a pause control (WCAG 2.2.2). Analysis and Off scale it as any other `effect` duration. The easing is the gait's, or `easeOutCubic`.
- **`size`** is the icon's length along the walk in px, or `"fit"`: scaled so the icon's box is 85% of the mark's thickness across the walk. Default: the icon's own size.
- **`orient`.** `"follow"` turns the icon with the walk, `"level"` never turns it, and the default `"auto"` follows but mirrors an icon marked `upright` when the walk heads left, so a boot on a negative bar keeps its sole down.
- **`ride`.** `"center"` (default) puts the icon's anchor on the walk; `"on"` sits the icon on top of it: half the mark's thickness plus the anchor's height above the icon's bottom, towards the icon's up side.
- **Corners.** The heading is smoothed over half the icon's length either side: it's the chord between the window's ends, which is exactly the tangent on straight legs and arcs and turns gradually across a polyline corner.
- **Gaps.** The icon jumps across a [gap](#gaps). The trip runs along the parts between the gaps, each inset by the footprint as the walk's ends are, so the icon is never drawn over a gap and goes from one part to the next at once. Its time and a roll's spin count only the parts it's drawn on, and its heading is smoothed within the part it's on, never across a gap. A part shorter than the icon is passed at once, unless it's the last: then the icon rests there, at the last value, as on a walk that short. So riding a line as it's revealed, it rests at the last value while the line is revealed into a gap, and moves on when the next value comes. A walk whose parts add up to less than 0.5 px, every value alone, draws nothing.
- **Geometry changes.** The icon follows `onChange` and keeps its progress, so on a resize a ball resting at the end of a bar stays at the new end. It's removed while its segment is missing and drawn again when the segment is back.
- An icon given by name is looked up in `ctx.icons` each time the effect runs or ends. An unknown name throws there, so the runner reports it.

**Gaits** (`gaits.roll()`, `gaits.step({ stride, lift, tilt })`, `gaits.slide()`) decide how the icon moves: `options.gait`, then the icon's own `gait`, then `slide`. A gait is a function from the trip so far (`distance`, `length`, `progress` and the icon's `radius`) to a pose: `lift` towards the icon's up side, and `spin` and `tilt` about its pivot. Distances are in the icon's own units, so a gait looks the same at any size. A gait can carry its own `ease` and `pace`.

| Gait | Pose | Trip |
| --- | --- | --- |
| `roll()` | spin = distance ÷ radius | default |
| `step({ stride: 42, lift: 3.2, tilt: 9 })` | a whole number of steps, at least one; each lifts by `lift` and raises the front by `tilt` degrees, easing off to 70% over the trip; flat at every landing | eased in and out, 15% longer (the prototype's cleat) |
| `slide()` | still | default |

### flash

```ts
flash({ width?, opacity?, color? })   // or the preset: on: { update: "flash" }
```

`flash` marks a change with one blink of a halo along the mark's outline, as the prototype's CSS flash does: the stroke grows from 0 to `width` (default 8 px, half of it outside the mark) by a quarter of the way through, then fades back to 0, each half eased like CSS's `ease-out`. It's drawn through `mark.set({ halo })` at `opacity` (default 0.35) in the mark's own colour unless `color` names a theme token or a CSS colour. The base duration is 900 ms with `effect` timing, so about 300 ms in Analysis.

- **End state: nothing.** That's deliberate. A flash is emphasis, not information: the change it points at (the bar's new length and value label) stays on the chart, so with motion off or reduced the viewer misses nothing.
- **Any mark.** It reads nothing of the geometry. The renderer strokes the halo along the outline as it is on screen, so in the `update` slot it follows the bar through the transition it runs alongside, and a stacked bar's segments each get their own halo.
- **Where it runs.** In the `update` slot it runs on the marks whose values changed, not on a re-sort or a new scale: on our charts, and on `expressive()` when the page passes `value`. Without `value` the adapter can't see values, so there an update means a mark's length changed, which a new axis maximum or a resize also does (see [Adapters](#adapters)).

### wiggle

```ts
wiggle({ swing? })   // or the preset: on: { hover: "wiggle" }
```

`wiggle` rocks the mark about its `pivot` in three half-swings, each half the last and on the other side, every one a sine arch, over 450 ms base with `effect` timing (about 160 ms in Analysis). The pivot is where the mark is attached to the chart, so a bar rocks on its baseline, a donut slice about the donut's centre and a line about its first point. It's drawn through `mark.set({ transform: matrix.rotate(angle, pivot) })`, which moves the mark's body only: its labels and pointer target stay put. What other effects draw for the mark in the overlay, such as `threshold`'s runs or a riding ball, turns with it, all but text ([Drawing API](#drawing-api)).

- **The guardrail.** The angle is capped so the outline point farthest from the pivot moves at most `swing` px (default 3, the most allowed). The reach is the largest distance from the pivot to `outline.sample(64)`, not the walk's length: a slice's far edge is on its outer radius, beyond the walk at mid-radius. A point at distance r turned by θ moves 2r·sin(θ/2), so the cap is `2·asin(swing / (2·reach))`. It's also never more than 15°, so a tiny mark nods rather than spins, and a mark whose outline is all within 0.5 px of its pivot doesn't move at all. The first half-swing reaches the cap.
- **End state: no transform.** The mark rests where the chart drew it, so with motion off or reduced nothing happens, and a full run ends with `transform` unset.
- **Geometry changes.** It follows `onChange`, so a wiggle running alongside a transition rocks about the pivot as it is now, with the cap for the mark as it is now.
- `swing` must be more than 0 and at most 3 px; anything else throws a `RangeError` when the effect is made.

### pulse

```ts
pulse({ times?, width?, color? })   // or the preset: on: { enter: "pulse" }
```

`pulse` draws attention with a halo that widens from 0 to `width` (default 12 px, half of it outside the mark) while it fades from 40% opacity to nothing, `times` over (default 2). The width eases out (the ring rushes out and slows) and the fade is linear. Each pulse is 600 ms base, `effect` timing, and its own tween, so Analysis shortens every pulse (to 210 ms) instead of dropping any. It's drawn through `mark.set({ halo })` in the mark's own colour unless `color` names a theme token or a CSS colour.

- **Under 5 s.** Before each pulse it asks the motion how long the pulse will take (`motion.duration(600, "effect")`), and drops it, and the rest, if the pulses so far plus this one would end at 5 s or later. So a page's `createMotion({ scaling })` can't stretch it into something that needs a pause control (WCAG 2.2.2); with effects scaled ×2, 6 pulses become 4.
- **Never a size change.** It only sets the halo, never a transform, so a value never looks bigger than it is.
- **End state: nothing**, as for `flash`: a pulse is emphasis, and what it points at stays on the chart.
- `times` is a whole number from 1 to 6, `width` a finite number more than 0, and `color` a non-empty string; anything else throws a `RangeError`.

### trace

```ts
trace({ color?, width?, opacity?, duration? })   // on: { hover: trace() }
```

`trace` is a highlighter: an overlay stroke drawn along the mark's walk, from its start to its end, which stays. It's the effects guide's [worked example](effects-guide.md#trace), grown. The stroke is `mark.slice(0, p)` in `color` (default `"mark"`, the mark's own colour), `width` px (default 3) at `opacity` (default 0.5), with round caps. It's drawn in over `duration` (default 500 ms base) with `effect` timing, eased in and out, so about 175 ms in Analysis.

- **The mark is untouched.** It only draws in the overlay, never through `mark.set()`, so it hides nothing and is safe in any slot. Drawing a mark itself in, over the mark made faint, is [`drawIn`](#drawin)'s, for `enter`: in the hover slot it would hide data.
- **Any mark.** It reads only the walk. On a stack it runs the whole walk, across every segment, in the stack's `"mark"` colour (its first segment's). A walk under 0.5 px (a point) draws nothing, and a run on one finishes at once.
- **Geometry changes.** The stroke follows `onChange` and keeps its progress, so it stays on the mark through a transition or a resize. While the walk is under 0.5 px it's removed, and drawn again when the walk is back.
- **End state: the whole stroke.** Reduced motion shows what a full run ends with. The path is made when the run starts, at progress 0 a lone moveto that SVG doesn't stroke, so in a combination it stacks where `end()` puts it.
- It isn't a preset. `color` must be a non-empty string; `width` and `duration` finite numbers, 0 or more; and `opacity` a number from 0 to 1. Anything else throws a `RangeError` when it's made.

### drawIn

```ts
drawIn({ duration?, faint? })   // on: { enter: drawIn() }
```

`drawIn` draws a mark in along its walk as it enters (M12 decision 12). Its body goes to `faint` (default 0.3, as hover dims the other marks) through `mark.set({ opacity })`, so its labels stay as they are. The overlay draws it over that, along its walk, at its own width and colour, with butt caps, over `duration` (default 750 ms base) with `effect` timing, so about 263 ms in Analysis. Then the paths go and the mark is back at full strength.

- **Any mark, by its walk and thickness alone.** Each part is `part.slice(0, p)` stroked `part.thickness` wide in `"mark"`, with no branch on the mark's kind. So a line draws along its stroke, its gaps left out as `slice()` leaves them; a bar from its baseline to its tip, a rectangle at its width, its rounded tip showing as the mark comes back; a slice round its mid-radius arc, at its ring's width. Overlay paths have round joins, so a line's corners are as the chart draws them. A walk under 0.5 px (a point, a closed shape) has nothing to draw along: the run finishes at once, with the mark untouched.
- **A stack, part by part.** The parts are the mark's `segments`, from the baseline, or the mark itself. Each is drawn in turn, eased in and out over its share of the time, its share of the parts' length, so a stack's gaps between segments take none. Each path names its segment with [`Paint.part`](#drawing-api), so it's drawn in that segment's colours. The paths are made when the run starts, at a lone moveto that SVG doesn't stroke, so they stack in order.
- **Geometry changes.** It follows `onChange`, drawing again at the same progress, its widths and parts too, so it keeps to a mark that grows or moves while it plays: a bar growing in on a chart's update (the run starts on its target, then hears each frame), a resize, a host's transition with `watch`. Once it's done, a change draws nothing.
- **End state: the mark as it is,** with nothing drawn and its style its own. `end()` does nothing, so reduced motion and Off show the mark at once. An abort gives the mark back its style and takes the paths away, and so does a clear.
- **Not for hover, and not a preset.** In the hover slot it would make the mark being read faint, so `trace` stays the highlighter. The built-in presets stay `flash`, `wiggle` and `pulse`, so no chart's bundle carries it unless the page imports it.
- `duration` must be a finite number, 0 or more, and `faint` a number from 0 to 1. Anything else throws a `RangeError` when it's made.

### delta and label

```ts
delta({ value?, format?, color? })          // on: { update: delta() }
label((data, mark) => text, { color? })     // on: { decorate: label((data) => …) }
```

`delta` and `label` are data effects that put text past the end of a mark, clear of its own labels, other marks' near it, and other effects' text. `delta` says the change since the last update ("+2"); `label` says whatever the page works out from the mark's data. They place and rise through one internal helper, `src/effects/caption.ts`, so they behave the same way. `delta` is the effects guide's [worked example](effects-guide.md#delta), grown.

- **Where the text goes.** From the end of the walk, along its heading: 10 px past the end, or 6 px past the farthest of the mark's own labels ([`labelBounds`](#the-marks-own-labels)) the heading meets, whichever is further. The heading meets a box when it passes within 6 px of it: the text has height, and a heading that just missed a label would put the text on it. So the text is past a bar's value label, centred above a column's, past a negative bar's or a negative column's name, and past a line's end label when the line heads at it or close by.
- **Then clear of the other boxes, by its own box** (M11). From there it moves along its way until its own box, as the context's [`texts`](#where-effects-text-sits) measures it, meets no other box: other marks' labels near it ([`nearbyLabels`](#other-marks-labels-nearby)) and other effects' text held before it. It meets a box from where its box comes within 6 px of it. It leaves one the heading meets 6 px past it along the heading, as it passes its own, or where its box is clear of it, if that's further; and one the heading misses where its box is 6 px clear of it, or, for other effects' text, where it's clear of it: a box already holds the text's ascent and descent, so text a row above or below is a line apart, not in its way. So the second of two lines' changes goes past the first's, a line's change goes past its own `label` beside its end label, text centred along a slice's ring keeps off a label beside it, and the changes on a slope chart's stacked rows, 17 px apart, stay beside their names. A box it would only meet further along isn't passed: the text is clear of it where it is. Without `texts`, it goes 6 px past the farthest of these the heading meets, as before M11.
- **Centred text** (within 45° of vertical, below) reaches out to either side, so it goes 6 px past a label's top or bottom, though the heading leaves the label through a side. Before M10 it went 6 px past that side, and on a slanted heading its text could sit on the label it was placed past.
- **When the heading meets none of its own labels** but the mark has some, it goes up from the mark's centre (`angle(0.5) − π/2`), 6 px past the farthest label that way meets, its own or another's. A slice's heading runs along the ring, so it never meets the slice's label outside it; its up side goes out through that label. If neither way meets one, it's 10 px past the end, as on a mark with none: a host mark, unless the page's `geometry` gives its boxes.
- **Other marks' labels and other text never turn it.** The way is picked by the mark's own labels alone, and other boxes only take it further that way. So a slice's text still goes out through its own label, and a slice with no label of its own keeps to its ring.
- **How it's anchored.** By the way it was placed: at its start reading rightwards, its end leftwards, and its middle within 45° of vertical. Its baseline is below the placed point by a share of the overlay's 12.5 px text: 0.36 em read sideways, so "20 +2" share a baseline, as the charts centre their labels; none read upwards, so it stands on the point; 0.8 em read downwards, so it hangs from it, as a negative column's value label does. Its width comes from `texts.box()`, measured by the chart's renderer; the drawing API stays renderer-neutral.
- **What it holds.** From its first draw it holds the box where its text ends, risen into place, through `texts.hold()`, and holds it again on each change, so later runs go past it as it is. No text holds nothing.
- **The rise.** It starts 8 px across the way it was placed, on that way's down side, unseen, and rises into place as it fades in, over 400 ms base with `effect` timing, eased in and out (140 ms in Analysis). Rising across, it never crosses the labels it's placed past.
- **It stays, and follows.** The text follows `onChange` wherever the mark and its labels go. `delta`'s text is this update's change, so it keeps it until the chart's [next update](#events-and-effect-slots) clears the run, whether or not that update changes its mark. `label` works its text out again from each change's data. A chart tells a mark's runs when only its row changed, too (a new row object, the same values, no `update` event), so a label from a field the chart doesn't plot, such as `vsLastMonth`, follows it.
- **End state: the text in place**, so reduced motion shows it.
- **`delta`'s change** is `value(data) − value(data.previous)`, by default the last sample's value: a bar's total, a line's value at its revealed end, a slice's share. `data.previous` is the values the last update gave, or where the mark has rested since, never the values part way through a change ([runner](#runner)): so an update that replaces one still moving says "+1", not "+1.88". No `previous`, a change that isn't a finite number, or one within 1e-9 of the values (float noise: 0.1 + 0.2 against 0.3) draws nothing. The default `format` is `Intl.NumberFormat` in the page's locale with `signDisplay: "always"` and at most two decimals, so it never reads "+0.30000000000000004", and a change too small to show reads "+0".
- **`label`** calls `text(data, mark)` when the run starts and on each change, not every frame. `undefined`, `null` or `""` draws nothing, and the text comes back when a change gives some. Its row type comes from `text`, as `defineDataEffect<D>`'s does.
- **Screen readers.** The overlay is `aria-hidden`, so a page that relies on the text says the same in its table or its announcement.
- **Line charts.** `update` and `decorate` run on a line's points too, so a change or a label meant for the line goes in `only((mark) => mark.length > 0, …)`.
- **Text that keeps clear** (M11 step 3, in jsdom's estimate). On 1,500 random donuts with a 6-character change on every slice, before M11, 61 of the 963 slices whose label was dropped put their text on another slice's label (M10 step 3's own probe: 63 of 592), and 275 changes sat on another's. Now none does either, and a dropped slice's text sits nearer its slice: half of them within 13 px of its end, from 19. On the season page's goals and xG lines, their two changes met in 5 of the 9 matchweeks where both change at 1,000 px, and in 8 at 320 (M10 step 6); now in none.
- **Where text can still meet text.** A box its way never meets is never in the way, so text placed past a label far along its heading can still reach one the chart didn't give: a host mark's, unless the page's `geometry` gives its boxes. Text another effect draws without holding it through `texts` isn't known to the others.
- **The chart's edge.** The layouts leave room for their own labels, not for these, so text past the outermost labels reaches past the chart's edge, where it's drawn: the `<svg>` is `overflow: visible`. Measured in Chrome at 320 px wide, with a bar at the end of its scale: a bar's text reaches 19.7 px past the right edge, the tallest column's 17.6 px above the top, a negative bar's, past its name, 20 px past the left edge, and the deepest negative column's, past its name, 14.1 px below the bottom (since M10 put the names below the value labels' room). The slices measured stay inside, but a line's text that goes past an end label reaches past the right edge. A bar chart keeps that much clear with [`room`](#bar-chart): `room: 28` keeps each of them inside at 320 px. A line chart has [`room`](#line-chart) too, to the right of its end labels: the season page's two changes, side by side past them, need `room: 60` at 1,000 px (20 at 320) to stay inside its width. A line that ends at the top of its plot heading up puts its text above the top: there, the season page's goals change alone rose up to 11.7 px above the chart at 320 px, and xG's, past it, up to 31. The line chart's `room` keeps space above the plot too (`{ right, top }`, M12): with `{ right: 60, top: 40 }` both stay inside at 320 and 1,000 px, in jsdom's estimate. Elsewhere a page leaves the room beside the chart, or it may scroll sideways at 320 px. `src/captions.test.ts` measures the same with jsdom's estimate of the text.
- **Its size.** Overlay text is 12.5 px, weight 600, with tabular digits, in the theme's text colour, on our charts (`.ec-chart .ec-text`) and on attachments (`.ec-overlay .ec-text`), which is the size the placing counts on. Both rules are in `:where()`, so a page's own CSS wins.
- Neither is a preset. `value`, `format` and `text` that aren't functions throw a `TypeError`, and a `color` that isn't a non-empty string a `RangeError`.

### threshold

```ts
threshold({ compareTo, when?, color? })   // on: { decorate: only("goals", threshold({ compareTo: "xg" })) }
```

`threshold` is the first data effect. It colours the parts of the mark's walk where its values are below `compareTo`, or above it with `when: "above"`: one overlay path per run, `mark.slice(t0, t1)`, stroked in `color` (default `"negative"`) at the mark's `thickness` with butt caps. On a bar that colours the part past a target across the bar's full thickness, with a square end over a rounded tip; on a line it lies exactly over the stroke and ends at the crossing.

- **The reference.** `compareTo` is a number, compared with every sample as it is, or a series' name, read through `data.related(name)` and listed in `needs.related`, so a chart without that series throws when it's created. A series is matched by `at` when every sample of both has a number or a `Date` there: the reference is interpolated between its samples (sorted by `at`), and nothing is coloured outside its range. Otherwise it's matched by `t`. A missing related series draws nothing.
- **Crossings.** Between neighbouring samples, and at the places in between where the reference has samples of its own (where it bends), both the mark's values and the reference are taken as linear in `t`, so each crossing is where their difference reaches 0. That's exact where the walk is straight between samples: bars, `describe.line` polylines, a curved `lineChart` line, which has a sample at each bend of its flattened curve ([Curves](#curves)), and a host polyline sampled at its vertices. Along a curve sampled less often, such as a D3 curve with `samplesAlong` samples at its rows, values aren't linear in distance, so crossings between samples are approximate; denser samples narrow the error. With samples at rows alone, a `curveMonotoneX` line on a 900 × 250 px plot changed colour up to 2.4 px from where the drawn lines cross on the line page's season, and up to 6.8 px on values per match (measured while planning M10).
- **Gaps.** Nothing is interpolated across a sample with `gapBefore`, the mark's or the reference's, so where either has no value nothing is coloured. A gap in the mark's samples puts no stations between the samples either side, even where the reference bends; inside a gap in the reference, the reference has no value, though its ends do. And `slice()` leaves the mark's own [gaps](#gaps) out of what's drawn.
- **Edge cases.** Equal values aren't coloured, and neither are values within 1e-9 of the reference, relative to their size, so float noise in a sum colours nothing. A sample whose value isn't finite colours neither leg beside it. A walk under 0.5 px (a point) draws nothing.
- **No animation.** It's an encoding, so it draws at once, with no tween; a fade would flicker as a line extends. It redraws on every `onChange` with the latest data, after a run and after `end()`, reusing its paths, so it follows a transition, a resize or a line being revealed. `end()` draws the same picture, so the colour shows with motion off. It belongs in `on.decorate`.
- `compareTo` must be a finite number or a non-empty string, `when` `"below"` or `"above"`, and `color` a non-empty string, or it throws a `RangeError` when it's made. It reads no row fields, so its type is `DataEffect` (rows `unknown`), which fits any chart.

### morph

```ts
morph({ points?, align? })   // chartSwitch's default transition
```

`morph` is the first transition effect: it turns one mark's shape into another's, as the morph demo's donut turns into columns. It reads only the two geometries' outlines, walks and pivots, so it morphs any mark into any other.

- **Two closed outlines** (bars, slices, points). Both are sampled with `outline.sample(points)` (default 160, 40 a side, as in the prototype), and each point moves in a straight line to its partner, drawn as one filled path in `"mark"`, the key's colour. At progress 0 the path is `from`'s own `outline.d`, at 1 `to`'s; in between it's the polygon through the moving points.
- **Which point is whose partner** (`align`). `"unroll"` pairs point i with point i, so each side meets the same side: a slice's walk becomes a column's, and it stands up, its outer arc becoming the column's left side. `"drop"` turns the pairing by a quarter of the points, as the prototype does: a slice's outer arc meets a column's top, so it settles onto the baseline. The turn goes from a mark that goes round its pivot to one that doesn't, whichever is `from`: a mark goes round its pivot when its `start`, `center` and `end` are the same distance from it, give or take 0.5 px, and more than 0.5 px away, the test the adapter's ring order uses. A slice does, a bar or a point doesn't. Between two marks that both go round their pivots, or neither does, `"drop"` pairs as `"unroll"` does. The polygon starts at the round mark's first point either way, and each coordinate is weighted on both sides (`x·(1 − p) + y·p`), so a run back from `1 − p` draws exactly the picture the run forward drew at p, to the last rounded digit.
- **The default `align` is `"unroll"`,** picked by comparing the two in the morph demo (`demo/morph.html`). `"drop"` stays an option.
- **Holes.** A closed outline's holes are the subpaths of its `d` other than the longest, which `sample` goes round: a D3 ring's inside edge, a shape's holes. Of two as long, give or take the path data's rounding, the first is the outside, as [`describe.shape`](#shapes) writes it first. Holes morph as the outside does:
  - **They pair by area,** largest with largest, whatever order they're written in. Each is sampled at a quarter of `points`, clockwise from its upper left, as a shape's outline is, and each point moves in a straight line to its partner. With `align: "drop"` the holes aren't turned.
  - **A hole with no partner** closes by half way, or opens after it, while its centre (its bounds') heads for where it lands in the other mark. Every point of it moves in a straight line to the one point it closes to.
    - **Where it lands:** its centre's place in the other mark's bounds, at the same fractions across and down, so the hole keeps with the shape: one that stayed where it was would leave a shape that moves, and be drawn filled outside it. Where that place is outside the other's filled area, or nearer its edge than a quarter of the hole's size, as in three quarters of a ring, whose bounds' middle is outside it, it lands on the deepest point of that area instead, of the other's centre and a 9 × 9 grid across its bounds.
    - **Sooner where the shape leaves it.** A shape part way between two can be far from both, so the hole's way is checked once a run, at each eighth of it: where a point of the hole would be outside the shape there, it closes by a quarter of the run instead, then an eighth, as soon as a sixteenth.
    - Both are worked out from the hole's own mark, whichever is `from`, so a run back retraces.
  - **Each is written the other way round from the outside,** anticlockwise from its upper left, as `describe.shape` writes a D3 ring's, so it stays a hole under either fill rule. Its points are written after the outside's, in the same path.
  - An outline with no holes, a bar's, a slice's or a point's, morphs as before, byte for byte.
- **Two lines that each run one way across x** (M12 step 2). Two open outlines whose vertices' x each go one way, every one more than the one before or every one less, the same way for both, pair by x across their spans: the point a share s of the way from one line's first x to its last pairs with the point s of the way across the other's. So the ends pair with the ends, and two lines over the same x's, as a season per match and to date are, pair each x with the same x, whatever the two plots' widths. Each point moves in a straight line to its partner.
  - **The vertices** are read from the outline's `d`, in the order the walk goes through them: each stretch with data that has length is the next subpath of `d`, and a value alone between two gaps, which `d` doesn't draw, is the walk's point at their ends. A line with an arc, a line of one point, or a `d` whose subpaths don't match the gaps pairs by length.
  - **The stops** are at `points` shares evenly across, and at each vertex of either line, which is where each gap begins and ends. So near 0 the stroke is the old line's own polyline, corners and all, and near 1 the new line's, and the first and last frames, the lines' own `d`, don't jump. Shares within 0.01 px of a stop's first, across the wider line, are that stop, at each line's own vertex where it has one there: path data is written to 0.001 px, so the same x in plots of two widths comes out a few millionths apart. A stop takes one vertex of each line at most, so a line's vertex, however close to the one before, starts a stop of its own and is never lost.
  - **A dense line.** Of a line with more than 1,000 vertices, the stops are the first, last, highest and lowest in each of 250 columns across its span, and every gap's ends, so its peaks and dips stay where they are. Measured on a chart switch between two line charts of ten years of days (3,652 across 1,000 px) in headless Chromium, the median of 15 switches: with every vertex, a frame's main-thread work was 0.8 ms more than with 160 points with one line a chart, and 1.5 ms with two; with the cap, 0.2 to 0.3 ms and 0.1 to 0.7, over two runs. Reading the lines' path data adds 10 to 15 ms to the switch's first frame, of 60 to 110, against 1 for 160 points, and about 5 once the code is warm: no cap saves that.
  - **Gaps** are found at the stops by x: a stretch between two stops is inside a line's gap when its middle is, as that line's shares. So two lines missing the same x's have their gaps at the same stops, and nothing is drawn there on any frame.
- **Any other two open outlines** (a spiral, a scatter trail, a line with a step straight up, or two lines that run opposite ways): both strokes are sampled at `points` along their length, point i to point i, as before, byte for byte.
- **Either way,** a line is drawn as a stroked path whose width moves from `from`'s thickness to `to`'s.
- **Lines with gaps.** Where either line has [`gaps`](#gaps), the stroke between two stops is inside the old line's gap, the new line's, both or neither. Two lines that pair by length have a stop at the ends of each gap too, at both lines' `path(t)`, so the samples and the gaps share one `t`. Each piece is drawn at an opacity of 1 − ((1 − p) · a + p · b), where p is the eased progress and a and b are 1 inside the old and the new line's gap and 0 outside. So the stroke inside a gap of the old line fades in as the morph goes, and inside a gap of the new line fades out, nothing is drawn inside a gap both have, and the first and last frames are the lines' own: nothing jumps.
  - **Three paths at most:** the pieces at full strength, those fading in and those fading out, each one path, in the order their first pieces come along the walk. That's the same whichever line is `from`, so a run back from `1 − p` draws what the run forward drew at p.
  - **Gaps meet by x** between two lines that pair by x. Between two that pair by length they meet by `t`, as the samples do, so two lines missing the same value have their gaps at about the same `t`, and the part of one that isn't the other's fades.
- **A closed and an open outline** crossfade: `from`'s own outline fades out as `to`'s fades in, the area always below the stroke, so a switch back draws the same picture. The end state is `to` alone, with no opacity.
- **Timing.** 950 ms base with `transition` timing (the prototype's: at most 200 ms in Analysis, a jump in Off), eased with `easeInOutCubic`. A run from `ctx.start` begins with the shapes at that eased progress, and takes the rest of the time a full run would: it starts at the linear time where the ease reaches `start` and ends when a full run would, so it takes its share of the *scaled* duration, as `playback()` does, and keeps a full run's speed in Analysis too (half a switch takes 100 ms there). It plays through one `ctx.tween()` of the whole 950 ms, finished early.
- **End state:** `to`'s own outline, filled or stroked as the mark is. `chartSwitch` then clears it and shows the real mark.
- **Motion off.** A run draws the end at once and asks for no frames; motion turning off mid-run jumps there on the next frame. An abort stops it where it is, and clearing removes its path.
- `points` must be a whole multiple of 4, at least 4, and `align` `"unroll"` or `"drop"`, or it throws a `RangeError` when it's made.

### Combinators

- `sequence(...effects)` runs the parts in order, each on the geometry and data as they are when it starts: the combination follows `onChange` from the start, so a part that starts after the mark moved (a transition, a line being revealed) doesn't start where the mark was. An abort stops the chain. `end()` draws every part's end state in order, and `clear()` clears every part, passing on the first error after all have run. A part with nothing to do finishes at once, so `sequence(travel(ball, { along: "goals" }), travel(cleat, { along: "assists" }))` tells the right story whether the bar shows goals, assists or both.
- `parallel(...effects)` runs the parts together and finishes when they all have, or rejects with the first part that does. `end()` and `clear()` work as for `sequence`.
- `only(filter, effect)` runs the effect only on marks whose key or series equals `filter`, or for which `filter(mark)` is true. Elsewhere it does nothing. It keeps the effect's kind and `needs`.
- `stagger(effect, { delay })` starts each mark of a batch a little after the one before; see [below](#stagger).

The parts share the run's context: one overlay group, one mark handle (whose `set()` merges fields, so parallel parts don't undo each other) and one signal. `Combined<E>` is the type `sequence` and `parallel` return: a data effect if any part is one, needing every part's row type at once (an intersection), so a generic part like `threshold()` can't widen a typed part back to `unknown`. A data combination's `needs.related` lists every part's. A part that isn't a mark effect (a transition effect, say) is a type error, and throws a `TypeError`.

### stagger

```ts
stagger(effect, { delay? })   // enter: stagger(pulse({ times: 1 }))
```

`stagger` makes the mark at `ctx.batch.index` wait `index × delay` ms (default 50) before the effect runs. The whole spread, `(count − 1) × delay`, is capped at 500 ms base, so in a big batch the delay shrinks to `500 / (count − 1)`. The wait is a tween with `stagger` timing, never a timer, so it's the base in Presentation and nothing in Analysis or Off. A batch of one, such as a hover, never waits.

- **Never a default.** Research finds staggering helps little and can hurt, so no chart, adapter or preset staggers; it's there for a page that asks.
- **While it waits** nothing is drawn. An abort ends the wait and the effect never runs. If the mark moves meanwhile (bars growing in on enter), the effect starts on the geometry and data as they are when its turn comes.
- **End state:** the effect's own, drawn at once by `end()`. `clear()` passes through.
- It keeps the effect's kind and `needs`, like `only`: a data effect stays a data effect with the same row type. A part that isn't a mark effect throws a `TypeError`, and a `delay` that's negative or not a finite number a `RangeError`.

### Drawing API

Effects touch the screen only through the context. It's deliberately small and renderer-neutral, so Canvas can implement it later without changing any effect.

- `layer.icon(icon, { size })` draws an icon, hidden until the first `place(transform)`. **Size rule:** the icon is scaled by `size / icon.size` about its anchor, in icon space, *before* the `place()` transform. So an effect builds the transform as if the icon were its natural size, and the anchor still lands where the transform puts it; icon-space lengths (footprint, radius) scale by the same factor. Each shape is one path; an unset `fill` or `stroke` draws none, `width` is in icon units, and `clip` is path data in icon space.
- `layer.path(d, paint)` draws an overlay path, unfilled unless `paint.fill` is given; `update(d, paint?)` replaces the path data and merges the paint fields given. `paint.part`, a segment's key, makes `"mark"` and `"mark-strong"` that segment's colours in the path (M12 decision 12): unset, or a key the mark hasn't, they're the mark's own. It's an optional field, an addition under the 0.x promise. In SVG, the path gets the segment's colours as its own `--ec-mark` and `--ec-mark-strong`, over its group's, and `data-part` with the key, so `recolor()` sets them again. The surface asks the chart for them (`colors(key, part)` in `svgSurface`'s options): the bar chart gives a segment's by its place among the bar's segments, `expressive()` the part of that segment's series, from its own fill or stroke, and the donut and line charts, whose marks have one part, the mark's own.
- `layer.text(content, style)` draws text in the theme text colour by default, with `at` on its baseline; `update(style, content?)` merges the style fields given. Series colours are for swatches, never for words.
- `mark.set(style)` changes only the fields given, so effects running in parallel don't undo each other's transform or halo. A field given as `undefined` goes back to its default. `mark.reset()` restores the mark's own style. `transform` (chart space) and `opacity` apply to the mark's body, so its labels and pointer target stay put; `emphasis` mixes toward the strong colour; `halo` strokes the outline behind the mark, `width` being the stroke width (half of it shows outside). On a reference chart's open outline (a line), `emphasis` mixes the stroke's colour, and the halo is stroked the line's own width wider, with round caps, so as much shows on each side as round a closed mark.
- **What a run draws follows its mark.** Its paths and icons take the mark's `transform`, so a red run or a ball stays on a line that `wiggle` turns, and they fade with the mark when hover dims it. Its text doesn't: it stays put and keeps its contrast, as the mark's labels do. The mark's `opacity` stays on its body. In SVG, a run's paths and icons are in a `<g class="ec-follow">` in its group; text drawn between them starts another, so everything stays in the order it was drawn.
- Colours are theme tokens (`"text"`, `"text-muted"`, `"negative"`, `"series-3"`, `"series-3-strong"`, and `"mark"` / `"mark-strong"` for this mark's colours, or with `part` a segment's) or any CSS colour.
- **Where runs draw.** Each run has a group in the chart's overlay, stacked by start order. On the bar chart, the donut and attachments, the overlay is above the marks. On a line chart it's above the lines, with their end dots and end labels, and below the points, so nothing a run draws covers a point being read (M13 decision 5, [Line chart](#line-chart)). A chart switch's own overlay is above both views.

The runner empties the layer and resets the mark when a run is cleared, so cleanup happens even if an effect forgets. The SVG implementation is in `src/charts/render/` (see [Rendering](#rendering)).

### Where effects' text sits

An effect sees only its own mark, so before M11 two marks' changes could land on each other. `EffectContext.texts`, a `TextSpace`, tells an effect where other effects' text sits on the same chart or attachment (M11 decision 12). It's optional, an addition under the 0.x promise: an effect that ignores it works as before, and a context without it is still one. Unset means no other text is known.

```ts
const box = ctx.texts?.box("+2", { at, anchor: "start" }); // the box the text takes, as the chart measures it
const before = ctx.texts?.held() ?? [];                     // the text of the runs that started before this one
ctx.texts?.hold(box);                                       // this run's text is there now
```

- **One space a runner.** Every run on one chart's or attachment's runner shares one, so two charts' text never counts against each other. Our charts, `expressive()` and `fromVegaView()` always give it, and so do `testContext()` and `checkEffect` through it.
- **`box(content, style)`** is the box `content` takes drawn with `style`, at the overlay's 12.5 px, measured as the chart measures its own labels (`textBox` in `src/charts/render/text.ts`, with the chart's own measure, so a font load clears both), its digits as 0s, from 0.16 em past the text at either side and 1.05 em above its baseline to 0.25 em below it. Where there's no layout it's estimated, 0.6 em a character, as a chart estimates its labels in jsdom. The box's shape is in `src/core/text-box.ts`, shared by both. A surface gives the runner its measure through `RunnerSurface.box`; without one the runner estimates.
- **`held()`** gives the boxes the runs on this runner that started before this one hold now. Runs start in the chart's mark order, so the first mark's text keeps its place and the next goes past it. Earlier runs never move for later ones. A run that takes another's place (motion turning off, `update({ on })`) takes its start order too.
- **`hold(box)`** says this run's text is at `box` from now on, until it holds another, holds `undefined`, or the run is cleared (a leave, a re-trigger, the next update, an exit, destroy), when the runner lets go of it. A finished run keeps its box while its text stays, as `delta`'s does.
- **Text placed again keeps the rule.** When marks move, a chart tells them in its mark order, and the runner tells a mark's runs in their start order, so a run placed again goes past the text before it as that is now. A chart doesn't tell a mark that didn't move, and a run's start order needn't be its mark's (a decoration started at enter, a change at the update), so the runner keeps track: once the chart has told every mark it's moving (a microtask), each run that was placed before text held before it moved, or let go, hears `onChange` again, in start order. Text that didn't move tells nothing.
- **Who reads it.** [`delta` and `label`](#delta-and-label) go past what's held and hold their own. An effect written outside the library can do the same: the effects guide says how.

### Testing effects without a DOM

`src/core/testing` has in-memory versions for effect tests. `testContext`, `play` and the recording types are public, re-exported from `expressive-charts/testing` with the conformance suite (below); the rest is internal.

- `recordingLayer()` and `recordingMark()` record every call and keep what's drawn now, a path's `part` with its paint. `picture()` gives that as plain data with numbers rounded, so a full run can be compared with `end()`.
- `testContext({ mode, scaling, icons, batch, previous, held })` is a complete `EffectContext` on a manual clock, with `abort()`, `clear()` and `change(mark)` (fires `onChange`). It's built on the same run scope the runner gives every run, so `clear()` is exactly the runner's cleanup after `effect.clear(ctx)`. Its `texts` estimates boxes as in jsdom, gives `held` as the boxes held before it, and says what the run holds now as `texts.holding`, which `clear()` lets go.
- `recordingSurface()` is a `RunnerSurface` whose groups are recording layers and whose marks are recording marks, for runner and chart tests.
- `measurePath(d)` measures the path data the geometry writes: length, start, end and commands.
- `play(clock, running)` advances a manual clock a frame at a time until a run settles, letting promise callbacks run between frames, and resolves with the ms it took.

**The conformance suite**, `expressive-charts/testing` (`src/testing/`, its own build entry), runs the conformance checks on any effect, the library's own or one written outside it: `checkEffect(effect, { marks, icons, data, batch, moved, name })`. On every mark it checks that:

1. a full run ends with the same picture and mark style as `end()` (pictures as `picture()` gives them; styles rounded the same way, key order and unset fields ignored);
2. clearing (`effect.clear(ctx)`, then the runner's cleanup) leaves nothing drawn and the mark's own style, and nothing comes back over the next three frames;
3. an abort two frames in settles the run without more frames, as a resolve rather than a rejection, and clears to nothing with no frames left running;
4. with motion off, the run asks for no frames and draws what `end()` draws;
5. after a full run, and after `end()` with motion off (what the runner draws instead of running), a `change()` to the mark moved somewhere else leaves the picture and mark style `end()` draws on the moved mark, once any animation the change started has finished. So an effect that should stay attached is checked to follow `onChange`.

It imports no test runner: it resolves when everything passes, and otherwise rejects with one `Error` listing each failure (the mark, the check and what differed), so it works in Vitest, Jest, `node:test` or Mocha. A test removes the runner's globals while it runs to keep it that way.

- **Marks.** `fixtures` by default: a bar, a negative bar, a column, a stack with a gap, a 6 px bar, a donut slice, a line, the line with a [gap](#gaps) after its second point, and a point. `marks` takes named marks, or a list such as `chart.marks()`, each named by its key.
- **Moved marks.** Each fixture has a moved twin (internal, in `src/testing/fixtures.ts`): the same key and series, somewhere else and another size. The bars are a row lower and shorter, the stack's segments in another ratio, the slice turned on a smaller ring, the lines rescaled with a fifth point (the gapped line keeps its gap after the second), and the point moved. `moved(mark)` gives other marks theirs, such as the same chart drawn at another width; without it, check 5 is skipped on them. A data effect's change gets `data(moved)`.
- **Icons.** None by default, so the suite doesn't bring in `src/icons`; `icons` gives the ones an effect looks up by name.
- **Data effects** get `data(mark)`, or by default no datum, samples from 0 to 1 (each sample's value is its `t`) and no related series. On a mark with [gaps](#gaps), the default has a sample at each end of each gap too, with `gapBefore` on the one after, so a data effect sees the gap as on a line chart's line; samples at one `t` (a gap from 0, or the gaps either side of a value alone) are one. Before M9 it had only the two samples on every mark, so a data effect never saw a gap. An effect that `needs` related series without `data` throws a `TypeError`, and one typed for its own rows without `data` is a type error.
- **Batch.** `batch` places the mark in its event's batch, so a staggered effect waits its turn first.
- Also a failure: `run()` not returning a promise, a run that hasn't settled after 10 s, and anything that throws.

**Transition effects** have `checkTransition(effect, { pairs, icons, name })`. On every pair, from a to b and from b to a, it runs checks 1 to 4 above, on contexts with `start: 0`, and a run from `start: 0.5`, which must end as `end()` draws. Then it checks that the effect **retraces**: at p = 0.25, 0.5 and 0.75, a run from b to a from `start: 1 − p` must begin, before its first frame, with the picture a run from a to b begins with from `start: p`, which is where a full run is at p. So a switch back mid-way doesn't jump, and a pairing that depends on which mark is `from` fails. Check 5 doesn't apply: a transition's `onChange` never fires.

- **Pairs.** `fixturePairs` by default: a slice and a column (a mark that goes round its pivot and one that doesn't), a bar and a column, two slices, two lines and two points, the second of two alike being the first's moved twin. `pairs` takes named pairs `[a, b]`, or a list, each named by its marks' keys.
- **Contexts** are `testContext()`s with `start`, so a page's own transition tests can make one the same way: `{ ...testContext(), start: 0.5 }`.
- The report names the pair, which way, the check and what differed; for long path data, the place where the two parted.

`src/effects/conformance.test.ts` runs `checkEffect` for every built-in effect (`travel` with each gait and option, and by icon name; `flash`; `wiggle`; `pulse`; a staggered `flash` on the third mark of five; `trace`, with its options and beside a rolling ball; `threshold` against a constant, above in a colour, against a related series, and with a riding ball; `delta` and `label`; and combinations) on the fixtures, and plays each on the gapped line frame by frame, through a run, a `change()` to its moved twin and `end()`, checking that nothing is drawn inside its gap (`drawnInGaps`, internal, in `src/core/testing/gaps.ts`: a path that runs along a gap, or an icon or text whose nearest point on the walk is inside one). It runs `checkTransition` for `morph` with each `align`, and with 8 points, on the fixture pairs. `src/conformance.test.ts` runs it for the same effects on real marks: bars from `barChart`, from `expressive()` and from a stacked Observable Plot bar through `expressive()`, slices from `donutChart` and a D3 pie through `expressive()`, lines from `lineChart` (with its points) and from a D3 line, a D3 line with missing weeks (drawn with `.defined()` and described with `breaks`) and a Plot line through `expressive()`, and [shapes](#shapes) through `expressive()`, each described from its path data with `describe.shape` (a D3 curve with `curveMonotoneX`, the same with `.defined()`, a D3 area and D3 rings), each drawn again at another size for check 5, with no change to the effects. It runs `checkTransition` for `morph` between those shapes too, rings among them, and between lines with gaps, checking frame by frame that `morph` draws nothing inside a gap both lines have. On the lines with gaps, it checks frame by frame that no effect draws inside one. `src/effects-guide.test.ts` runs it on the guide's worked examples.

## Runner

`src/core/runner.ts` plays a chart's slots. It's internal: each reference chart and adapter creates one and calls it as things happen, and the runner owns every run's lifecycle, so effects stay small and stateless. A *run* is one effect playing on one mark for one slot.

```ts
const runner = createRunner({ effects: resolveEffects(options.on, presets), surface, motion, icons });
runner.enter(marks);         // decorate, then enter
runner.interrupt();          // a data transition starts: hover runs are cleared
runner.update(changed);      // an update: ends the others' update runs, then runs update with the geometry and values before
runner.change(mark);         // every frame of the transition: onChange for that mark's runs
runner.settle();             // the transition settled: hover replays on marks still hovered
await runner.exit(leaving);  // then remove their elements
runner.hover([mark]); runner.leave(); runner.destroy();
runner.swap(effects, marks); // update({ on }): the changed slots start again where they were
```

- **One run per mark and slot.** Re-triggering clears the previous run, then starts the new one. Marks are matched by key.
- **Clearing** a run aborts its `signal`, calls `effect.clear(ctx)`, empties its layer group, resets its mark style and drops its `onChange` listeners. This happens even if the effect forgets, and anything it draws or styles afterwards is ignored.
- **Finished runs stay.** When `run()` resolves, what it drew and styled stays, and it keeps getting `onChange`, until it's cleared: by leave, a re-trigger, the next update (an `update` run), exit or destroy. So a ball that rolled to the end rests there while the pointer stays.
- **An update.** A chart or adapter calls `update(changed)` only for [an update](#events-and-effect-slots), even one that changes no mark (`update([])`). It first clears the `update` runs of every mark not in `changed`, as a re-trigger would, finished or still playing, then starts the changed marks' runs. Charts call it from `playUpdate` (`src/charts/shell/transitions.ts`), told whether `update()` had `data`; `expressive()` from `refresh()`, when its read finds a new row, a new value, or a mark entering or leaving.
- **Changes.** `change(mark, data?)` hands every live run of the mark the new geometry and the mark's latest data: the data given, or else the last seen, in the runs' start order. An `update` run's data keeps the previous values it was given, so an effect that reads them on a change still compares with the values before the update.
- **Text.** Every run's context has the runner's one [text space](#where-effects-text-sits). When a run's held text moves or goes, the runs after it that were placed before it moved hear `onChange` again once the chart is done (a microtask), so text keeps going past the text before it.
- **Off.** When the effective mode is `off`, the runner calls `end()` instead of `run()`, on a fresh context. If the mode turns off mid-run (the device asks for reduced motion, or the viewer picks Off), runs still going are cleared and replaced by `end()` on a fresh context with the mark's latest geometry; finished runs keep what they drew.
- **Data transitions.** `interrupt()` clears hover runs, and a hover that arrives during the transition waits. `settle()` replays hover, in the order the marks were hovered, on the marks still hovered or focused, with their latest geometry. Other runs keep going, and decorations follow every `change()`.
- **Exit.** `exit()` clears the mark's other runs (hover too), runs `exit`, then clears that and forgets the mark. Its promise resolves when every exit is done, which is when the chart removes the elements. A leaving mark can't be hovered, and one that re-enters mid-exit cancels its exit.
- **Errors.** An effect that throws or rejects, in `run`, `end` or an `onChange` listener, is reported (with `reportError`) and its run cleared; other runs and marks carry on. An error in `clear()` is reported and the cleanup continues. A rejection caused by the run's own abort isn't reported.
- **Mark styles merge.** Every live run's `mark.set()` fields are merged into the mark's one style handle. When two runs set the same field, the one that started later wins; when it's cleared, the earlier run's value comes back. A run that `end()` replaces when the mode turns off keeps its place.
- **Swapping effects.** `swap(effects, marks)` takes a chart's new effects, as its `update({ on })` resolves them. A slot whose effect is the same object keeps its runs. A changed slot's runs are cleared, and the new effect starts where they were, in their place (their start order, and the `exit()` promise waiting on an exit):
  - `decorate` starts again on every mark in `marks`: the marks staying through the chart's update, as that update leaves them (their new rows), in visual order, with batches as `enter()` gives them. The marks entering start theirs with `enter()`. Their geometry and data start the runs but aren't taken as the marks' own, so the `update()` that follows still gives an update run the values from before;
  - `hover` replays on the marks still hovered, in the order they were hovered, or from `settle()` while a transition is in flight;
  - `enter`, `update` and `exit` draw the new effect's end state, on the run's own geometry, data and `previous`, so nothing enters again, an update keeps showing what it explains, and an exit still ends and lets its mark go;
  - a slot left empty just clears its runs.

Each run's `EffectContext` has its own `signal`; the motion view; `tween()` bound to the clock, the motion and the signal (a tween given its own signal is still cancelled with the run); its own `layer` group and `mark` handle; the icon source; `batch`, the mark's position among the marks in that call; `previous` on update runs; and `texts`, its view of the runner's text space. Data effects also get the mark's `MarkData`. On update:

- **`previous`** (geometry) comes from the chart (an `update` event's `from`), or else from the last geometry the runner saw for that key. Either way it's the mark on screen, which the transition starts from, part way while a change plays.
- **`data.previous`** (values) comes from the chart, or else from the data the key last rested at: its last `enter()` or `update()` (where it was heading), a `change()` outside a transition (a resize, a line's reveal), or `settle()` (the frame the change landed on). Not the latest frame's, so an update that replaces one still moving counts from the values the last update gave: "+1", not "+1.88". The latest frame's data is still what `change()` hands the runs.

The renderer implements `RunnerSurface`: `group(key, slot, order)` returns a new overlay group for one run, asked for on the run's first draw and cleared once when the run is. Groups stack by `order`, the run's start order, rather than by when they were asked for, since a decoration may first draw long after it started. `mark(key)` returns the mark's style handle. `box(content, style)`, optional, measures a run's text for `texts`; without it the runner estimates. `svgSurface()` in `src/charts/render/` is the SVG one, measuring with the chart's own text measure, or in the overlay when it's given none (`expressive()`). It gives a key's `.ec-follow` groups the `transform` the runner sets on its mark, and can also hide a key's groups, as the line chart does for points past its reveal, and give them `ec-hot` with their mark (`hot(key, on)`) for the hover's dimming; `recordingSurface()` in `src/core/testing` is an in-memory one.

### Playing transitions

`src/core/transition.ts` plays a [transition effect](#transition-effects) on pairs of marks. It's internal, beside the runner: [`chartSwitch`](#switching-between-charts) uses it.

```ts
const transition = playTransition(pairs, { effect: morph(), surface, start: 0, motion, clock, icons });
await transition.finished;   // every pair finished (its end state stays drawn) or was cleared
transition.clear();          // abort, effect.clear(ctx), empty every group
```

- **One run per pair**, on a context of its own built on the runner's `runScope`: `signal`, `motion`, `tween()`, a `layer` group, `icons`, `batch` (the pair's place among the pairs) and `start`. Its `mark` handle does nothing and `onChange` never fires.
- **Off.** With motion off, `end()` draws on the context instead of `run()`. If the mode turns off mid-run, runs still going are cleared and replaced by `end()` on a fresh context, in the same group order; finished runs keep what they drew. The player follows the mode only until every run has settled.
- **Clearing** aborts every run, calls `effect.clear(ctx)` and empties its group, even if the effect forgets; draws after that are ignored. `finished` resolves then too, and it never rejects.
- **Errors.** An effect that throws or rejects on one pair, in `run` or `end`, is reported and that pair cleared; the others carry on. An error in `clear()` is reported and the cleanup continues. A rejection caused by the run's own abort isn't reported.
- An effect that isn't a transition throws a `TypeError`, and a `start` outside 0–1 a `RangeError`.

The overlay implements `TransitionSurface`: `group(key, order)` returns a new group for one pair, in overlay coordinates, asked for on the run's first draw with the pair's key (`to.key`), so `"mark"` is that key's colour. Groups stack by `order`, the pair's index.

## Presets and icons by name

A slot can name a preset instead of holding an effect, `on: { hover: "wiggle" }`, and an effect can name an icon, `travel("cleat")`. Charts resolve names through registries the composition root (`src/index.ts`) hands them, so a chart never knows what a name means.

- `registerPreset(name, factory)` makes a name usable in any chart's `on`. The factory returns a fresh effect that works on any rows. The built-in presets are exactly `flash`, `wiggle` and `pulse`, each that effect with its defaults; none combines effects, draws an icon or staggers.
- `registerIcon(icon)` and `registerIcons(icons)` make icons usable by their `name`, through each run's `ctx.icons`. The core icons (`dot`, `arrow`, `chevron`) are registered from the start; the sport pack is opt-in, with `registerIcons(sport)`.
- A later registration replaces an earlier one with the same name.
- Charts call `resolveEffects(on, presets)` when they're created. An unknown preset name throws a `RangeError` that lists the registered names. A transition effect in a mark slot, or a slot that doesn't exist, throws a `TypeError` naming the slot. Misspelled names aren't type errors (custom names are allowed), so this is where they're caught.

Internally both are a `createRegistry({ kind, entries, hint })` (`src/core/registry.ts`) with `get`, `resolve`, `register` and `names`; a `Registry<Icon>` is an `IconSource`.

## Icons

An icon is path data plus paint (`src/core/contracts/icon.ts`), never raw SVG markup, so any renderer can draw it and Canvas can draw each shape as a `Path2D`. Shapes are drawn facing +x with their up side towards −y, in px at the icon's natural size, `icon.size`.

| Field | What it is | Default |
| --- | --- | --- |
| `shapes` | paths drawn in order, each with `fill`, `stroke`, `width`, `linecap`, `linejoin`, `fillRule`, `opacity`, `fillOpacity`, `strokeOpacity` and an optional `clip` path; an unset fill or stroke draws none | |
| `box` | icon-space bounds | |
| `size` | the natural length along the walk, px | the box's width |
| `anchor` | the point that sits on the walk | |
| `pivot` | what it spins or tilts around | the anchor |
| `footprint` | `[behind, ahead]`: its extent along +x from the anchor | from the anchor to the box's edges |
| `gait` | `"roll"`, `"step"` or `"slide"` | none, so travel slides |
| `radius` | rolling radius | half the box's height |
| `upright` | mirror instead of turning upside down | false |

- **A shape's fill rule and opacities** are SVG's. `fillRule` is `"nonzero"` (the default) or `"evenodd"`, which leaves a hole where the path's parts overlap, as solid icon sets draw them. `opacity`, from 0 to 1 (default 1), fades the whole shape, its fill and stroke together, as a duotone set fades its lighter part. `fillOpacity` and `strokeOpacity`, from 0 to 1 (default 1), are the fill's and the stroke's own, inside `opacity`, so one shape can have a faint fill inside a full outline. The SVG layer sets each on the shape's `<path>`, and leaves them unset where the shape has none.
- `defineIcon(spec)` fills the defaults, checks every field (a `RangeError` names the bad one; path data must start with a move and contain only path characters) and freezes the icon, since one icon is shared by every run.
- `iconFromSvg(markup, spec)` reads SVG markup as text, with no DOM. It keeps only `path`, `circle`, `rect`, `ellipse`, `line`, `polyline` and `polygon`, with their fill, stroke, stroke width, caps and joins, fill rule, opacity, fill opacity and stroke opacity (as attributes or in `style`, inherited from groups), and applies their transforms. A polyline is a polygon left open. A group's opacity is multiplied into its shapes', which looks the same unless they overlap, where SVG would fade the group as one. A fill or stroke opacity is inherited as SVG inherits it: a shape's own replaces its group's. Each opacity is a number or a percentage, and one past 0 or 1 counts as 0 or 1. One that can't be read counts as 1 for `opacity`, and leaves the group's for the other two. A shape with an opacity of 0 is dropped, and so is a fill or stroke with one of 0. Everything else is dropped: scripts, event handlers, `<use>`, text, images, and the contents of `<defs>`, `<clipPath>` and the like. Path data is rewritten from the numbers it contains, and colours must be plain colours or theme tokens, so nothing from the markup passes through. `currentColor`, in any case, becomes the `text` token, so an icon from an icon set such as Lucide, Heroicons or Tabler follows the chart's theme rather than the page's `color`. Gradients, patterns, square caps, bevel joins and CSS classes aren't kept. `size` scales the whole icon so its box is that many px wide; the spec's anchor, pivot, footprint and radius are in the SVG's own units. [api.md](api.md#an-icon-from-an-icon-set) has a recipe for an icon from an icon set.
- **Core icons** (`icons.dot`, `.arrow`, `.chevron`) are neutral and drawn in theme colours (`surface`, `text`), so they read in light and dark themes and on any series colour.
- **The sport pack** is a separate entry point, `expressive-charts/icons/sport`, with `soccerBall`, `cleat` and `sport` (both, for `registerIcons`). They're converted from the prototype and drawn in fixed colours:

| Icon | `anchor` | `pivot` | `footprint` | `gait` | Notes |
| --- | --- | --- | --- | --- | --- |
| `soccer-ball` | centre | centre | 8.5 / 8.5 | `roll` | The panels are clipped to the ball. |
| `cleat` | (0, −6): the heel, raised so the boot sits centred in a bar | (13, −4), the ball of the foot | 0 / 26 | `step` | `upright` |

## Reference charts

Our charts are in `src/charts`. They import only from core, and the composition root (`src/index.ts`) hands each one a `ChartEnv`: the preset and icon registries and the page-wide motion. So a chart never imports an effect or a registry. Every chart has `update(next)`, `on(type, listener)`, `marks()` (in visual order, as they are on screen now, so part way through a transition while one plays), `focus(key)`, `leave()`, `labels()`, `element` (the `<svg>`) and `destroy()`.

- **`focus(key)`** moves focus to the mark `key` as a key press would, whatever the last input was, as the [adapter's](#adapters) does: the focus ring shows and its hover plays (`source: "keyboard"`), even on a mark already focused from a click. On the [line chart](#line-chart) the x takes focus, for the x's key or one of its points' (`"12"` or `"goals@12"`); a line's key isn't one x's, so it does nothing. So does a key that isn't on screen: unknown, leaving, or past a line chart's reveal. It's the keyboard's own `focus(key)`, through the shell's hover.
- **`leave()`** ends the chart's hover, the pointer's or focus's, as the viewer moving away would: the emphasis, the dimming, the tooltip and the hover runs end, and `leave` fires for each mark that was hovered, in one batch. Focus stays where it is, with its ring, as after Escape, and the next key press or pointer move onto a mark hovers again. With nothing hovered it does nothing. A [chart switch](#switching-between-charts) ends the old view's hover with it.
- **`update({ on })`** swaps the chart's effects in place, so a page with an effect picker needn't recreate its charts, which would lose the tab stop and play the enter effects again.
  - The new `on` is resolved as when the chart is made, so an unknown preset name or slot rejects before anything changes, and so does a data effect whose `needs` name a series the chart doesn't have.
  - A slot given the same effect, or the same preset name, keeps its effect and its runs. A slot left out is emptied.
  - The changed slots go through the [runner's](#runner) `swap()`: `decorate` starts again on every live mark, and a hover that's held replays with the new hover effect once the change settles. `enter`, `update` and `exit` draw the new effect's end state where their runs were, so nothing enters again.
  - Focus stays on its mark, and nothing fires: no `enter`, and no `hover` or `leave`.
  - It plays with the rest of the update. The swap comes once the update has matched its new layout to the marks, and before the runner hears the change (`playUpdate`'s `swap`), so the new effects start on the marks as the update leaves them, and `update({ on, data })` plays the data change with them: a new data effect finds a series the same update adds.
- **`labels()`** gives each mark's labels as drawn now, in the marks' visual order (leaving marks left out): `{ key, role, text, x, y, anchor, element }` (`ChartLabel`). `role` is `"category"` (the mark's name) or `"value"`; `x`, `y` and `anchor` place the `<text>`'s baseline in the chart's `<svg>`, in its viewBox units, unrounded (its attributes are rounded to 0.001); and `element` is the `<text>` itself, so a copy keeps the stylesheet's styling. A bar has its category and its value, a slice its category and share outside the ring (the centre's total is no slice's), and a line its end label, as its value. A label that isn't shown (a slice's dropped for room, a line's with `labels: false`) or has no text is left out. Part way through a change they're where they're drawn, counting as they go. A [chart switch](#switching-between-charts) moves them from one view to the other.
- **Hiding the marks.** While the `<svg>` has the class `ec-morphing`, the shared stylesheet hides its marks and their labels ([Rendering](#rendering)), so no chart needs a method for it.

What a chart does that doesn't depend on the shape of its marks is shared, in `src/charts/shell/`, so `barChart`, the donut and the line chart behave alike. Each module is a function or a small factory that takes callbacks (no base class), and none names a chart type or an effect. `events.ts` keeps the listeners and emits events in batches. `hover.ts` is the one hover that pointer, touch, keyboard focus and a [link](#linked-hover) share, as described for bars below: the emphasis and dimming, the runner's hover and leave, the focus ring's mark and the tooltip, with the chart finding marks and drawing the ring and tooltip. The pointer on the tooltip of its own hover is on its target (`src/charts/interaction.ts`). What it hovers is a target, which stands for one mark or for several hovered together: a bar or a slice is its own mark (the default), and a [line chart](#line-chart)'s x stands for each series' point there (with `hover: "point"`, each point is a target, found from where the pointer is on every move, and the chart says where the arrow keys go). Each of the target's marks gets `ec-hot`, a hover run in one batch, and a `hover` event with its place in that batch (`batch.index` of `batch.count`); leaving ends them all, with `leave` events batched the same way. If the marks a hovered target stands for change (a series added by an update), the ones it lost are left and the new ones hovered. The keyboard still moves between targets, as one tab stop. `transitions.ts` keeps one transition in flight, draws every frame until its tweens settle, then lands, settles the runner and resolves the waiters; its `playUpdate` plays an update through the runner in the order it expects. `leaving.ts` keeps a leaving mark until it has faded out and its exit effects are done. `order.ts` puts marks in visual order in the DOM without moving the focused one. `watch.ts` follows the container's width, web fonts and the hover duration. `setup.ts` and `format.ts` hold `ChartEnv`, the container, the chart's accessible name, the check of the options every chart shares, the `needs.related` check, the default `format` and a share as a whole percent. `transitions.ts` also has the small tests a chart's retarget makes (whether a value still has to move, whether a mark's geometry changed). The layout, the marks' drawing and the staging of a change stay in each chart. Marks that touch, such as slices, have their focus ring and halos drawn above them and masked to outside the mark (`src/charts/render/outside.ts`), as the adapter's are.

### Bar chart

```ts
barChart("#goals", { label: "Goals by player", data: players, y: "name", stack: ["goals"], sort: "value", colors: { goals: 1, assists: 4 }, on: { hover: ballThenCleat } });
```

- **Encoding.** The axis whose values aren't numbers is the category: `y: "name", x: "goals"` draws horizontal bars, `x: "name", y: "goals"` columns. With `stack`, the one axis given is the category. `orientation` forces it, and is needed when both axes hold numbers. Each value field is a segment named after it (a function's is `"value"`), so a plain bar has one segment, as `describe.bar` gives it (`gap: 2`, `radius: 4`).
- **Keys** default to the category, are converted with `String()`, and must be unique. `sort` is `"none"` (data order, the default), `"value"` (largest total first), `"key"` (A–Z, numbers in numeric order) or a comparator; sorting never changes a key or a colour.
- **Values.** Missing values (`null`, `undefined`) count as 0; anything else that isn't a finite number throws. Negative bars grow from zero the other way (baseline `right` or `top`). A stack that mixes signs throws for now.
- **Data effects** read other series through `data.related(series)`, which on a bar is that series' segment in the same row. The series an effect lists in `needs.related` must be among the chart's (the stacked fields, or the value field), or creating the chart throws and `update()` rejects.
- **Layout.** The chart measures its container (or takes `width`) and lays out in px; a `ResizeObserver` re-lays it out on the next frame, without animating, calling `change()` for the marks that moved. Horizontal rows are 34 px with 20 px bars, so the height follows the rows unless `height` is given; columns default to 300 px high. Label margins are measured in the chart's own SVG (estimated from the character count where there's no layout, as in jsdom) and measured again once web fonts load. The layout (`bar-layout.ts`, pure) is drawn from a few numbers: a frame, which is the value scale (`lo`, `hi`, where they sit in px, and the category labels' place) and the category bands (start, band size, bar thickness, plot span, chart size), plus each row's values and slot. `placeRow` and `placeTick` draw a laid-out row or any state in between, which is how transitions draw their frames.
- **Room.** `room` is px the layout keeps clear past the labels at each end of the value axis that bars reach, for text an effect draws there, such as a [`delta`](#delta-and-label). Default 0, so nothing moves. The positive end gets it if a total is above 0, the negative end if one is below; an end no bar reaches gets none.
  - It's the outermost space: past the value labels at a bar's tip or above a column; on a negative bar's side past the names too, since its text goes past its name; and under negative columns past the names under the axis, which are below their value labels' room.
- **Names under negative columns.** With a negative column, the value labels hang below the tips, so the layout keeps 18.5 px under the plot for them (12.5 px text and 6 px), and the names go 18 px below that room rather than 18 px below the plot. So the deepest column, reaching the plot's bottom, has its value label above its name, 4.5 px clear in Chrome, never on it. The plot keeps its height: the room was kept already, below the names, where nothing used it. A chart with no negative column draws as before (M10 decision 11).
  - The chart doesn't know which effect it's for. At 320 px a `delta` reaches about 20 px past the chart, so `room: 28` keeps it inside, with a little to spare for wider fonts. A number of px, 0 or more; anything else throws a `RangeError`, and `update()` rejects it.
- **Thinning** (M8 step 6). Past about 40 bars, labels would overlap, and overlapping labels help nobody, so the layout leaves some out. There's no option.
  - **Category labels.** It draws every nth, from the first, with n the smallest of 1, 2, 5, 10, 20, 50 and so on that leaves no two overlapping. **Value labels** are drawn all or none: none when any two would overlap, wherever they are. A category label and a value label aren't compared, since within a row they sit apart.
  - Two labels overlap when their boxes do, the boxes `labelBounds` gives ([above](#the-marks-own-labels)); boxes that touch don't. They're found in one sweep along the category axis, which compares each box only with those it reaches along it.
  - **What's kept.** Every name and value stays in the marks' names, the tooltip, the legend and the table. `labelBounds` and `labels()` have only the labels drawn, so a chart switch moves those and fades the rest.
  - **The frame keeps room for every label**, the value labels' margin too, so thinning moves nothing, a re-sort that draws other names doesn't shift the bars, and `room` stays past where the value labels would be.
  - **An update** draws the labels its new layout draws, from its first frame: the names of the bars heading for every nth place, as they move there, and no values, not even counting, when the new layout has none. A chart whose labels didn't overlap draws them all, as before.
- **Hover.** Pointer hover is delegated from the `<svg>`: each mark's whole row (or column) band is its target, and the hovered mark's tooltip counts as it too (below). A touch tap acts as hover until a tap elsewhere. The hovered mark turns its strong colour and the others' bars dim to `--ec-dim-opacity` (0.3), with the paths and icons their effects draw, while their labels and any text effects draw stay as they are, so text keeps its contrast; `dim: false` keeps the others as they are. Both are CSS transitions timed by `--ec-hover-duration`, which the chart sets from `motion.duration(100, "feedback")`, so they're instant when motion is off.
- **Keyboard.** The chart is one tab stop: one mark has `tabindex="0"` (the first in visual order, then whichever was focused last, or the one a [chart switch](#switching-between-charts) moves it to without focus, with the handle's `moveTabStop(key)`) and the others `-1`. The arrow keys move to the next or previous mark in visual order, following the current sort: Down and Right go to the next, Up and Left to the previous, whatever the orientation. Page Down and Page Up go a page on or back, a tenth of the marks rounded up (3 of 25, 1 of 10 or fewer), and stop at the ends, as the arrows do. Home and End jump to the ends. Keys pressed with Alt, Ctrl or Meta are left to the browser.
  - Focus that follows a key press plays the hover story (`source: "keyboard"`), with the same emphasis and dimming as the pointer, and jumps to its end state when motion is off, as hover does. Escape stops it and keeps focus; blur leaves. Focus from a click or tap moves the tab stop but leaves the hover to the pointer.
  - Pointer and focus share one hover. The pointer moving onto another mark takes it over; focus arriving on the mark under the pointer holds that hover until blur, and a blur with the pointer still over the mark leaves it to the pointer.
  - Focus stays on its key across `update()`, and the story replays once the change settles. The focused mark's element never moves in the DOM (the others move around it), because moving a focused element blurs it. If the focused mark leaves, focus moves to its nearest neighbour, the next mark or else the previous one; with no marks left, it leaves the chart.
  - **Focus ring.** It's drawn from the focused mark's `outline.d` as it is on screen, so it follows the mark through a transition, and takes the mark's `transform` when an effect moves it. It's in `<g class="ec-focus">` behind the marks: a 2 px ring in `--ec-focus` outside a 2 px gap in `--ec-surface`. So it never covers data, and stays distinct from a bar of the same colour. As with `:focus-visible`, it shows unless the last input on the page was a pointer. The mark's own outline is turned off.
  - **Labels.** Each mark's `aria-label` gives its category and its values in the chart's `format`, each with its series' label, "Okafor: 16 goals, 4 assists" (a lone value read by a function has no series name unless `seriesLabels` gives it one: "Okafor: 16"). It changes as soon as an update starts.
  - `markLabel(d, mark)` words it instead, so a page can say "1 goal". It's given the row and the mark as it's heading (a `MarkSummary`): its `key` and `category`, `values` (each series it shows, from the baseline, so a new stack names only the new series, with its `label`), `total`, the chart's `format`, and `text`, the default name. It's called for every mark when the chart is drawn and as each update starts, never per frame; `update()` can change it.
  - An empty or blank result keeps the default name, and so does a throw, which is reported as a tooltip function's is. A focusable image with no name fails WCAG 4.1.2, so clumsy wording beats none. (A tooltip function's empty string means no tooltip, because a mark without one loses nothing.)
  - The default keeps the field names as they are, so a value of 1 reads "1 goals". The chart can't make a singular from a field name (it may not be an English noun, or a noun at all), and naming the series first ("goals 1") would read worse in the common case. Pages that care pass `markLabel`. `seriesLabels` renames the series everywhere, but can't make "1 goal" either.
  - **Why `markLabel`.** The plan called it `describe(d)`, but `describe` is already the geometry builders' namespace, and in ARIA a description is something else: a tooltip function's text is the mark's `aria-describedby`. `markLabel` pairs with `label`, the chart's own name, and isn't tied to SVG attributes the way `ariaLabel` would be. `expressive()` takes a `markLabel` too, for host marks ([Adapters](#adapters)).
  - Focus events are heard on the document (or the shadow root the chart is in), not on the `<svg>`: Chrome makes an SVG element with focus listeners of its own a tab stop.
- **Tooltip** (`src/charts/tooltip.ts`). An HTML box beside the hovered or focused mark, so pointer, touch and keyboard hover all show it: it follows a touch tap until a tap elsewhere, and hides on leave, Escape and blur.
  - **Escape anywhere** ends the hover, the pointer's too, as `leave()` does, so the tooltip can be dismissed without moving the pointer (WCAG 1.4.13: it covers other marks). The chart listens on the document only while something is hovered, and leaves an Escape the page has already handled (`defaultPrevented`) alone. The pointer hovers again when it next moves onto a mark. Added after the accessibility audit ([a11y-audit.md](a11y-audit.md)); `expressive()` has no tooltip, and its Escape still needs focus on a mark.
  - It's placed from the mark's `bounds` and `center` as they are on screen, so it follows the mark through a transition: centred on the mark and 12 px above it, or below it when there isn't room above (when neither side has room, the side with more). It's clamped to the chart's left and right edges, but never moved over the mark it describes. It moves with an effect's `transform` on the mark, as the focus ring does, but keeps the side it has at rest, so a wiggle near the edge can't flip it back and forth.
  - A chart can also show it at a point instead of beside a mark: centred on an x, above a top or, without room there, below a bottom, in the `<svg>`'s units. The [line chart](#line-chart)'s crosshair places it over the highest of the points it crosses. The default text can leave the total out, for series that don't add up.
  - It sits in `<div class="ec-tooltip-layer">`, a positioned, zero-height layer just after the `<svg>`, made the first time it shows, with the box (`.ec-tooltip`) and its bridge (`.ec-tooltip-bridge`, below). Its place is worked out in px from the boxes of the `<svg>` and the layer, so it lands right on a scaled `<svg>` and whatever the page's layout.
  - **It can be hovered** (WCAG 1.4.13, M8 step 1), so its text can be read, selected and magnified. While it shows it takes the pointer, and `pointerHover` counts the pointer on it as on the target it's for. Leaving the `<svg>` for it keeps the hover, and a line chart's crosshair keeps its x. Leaving it for a mark hovers that mark, and leaving it for anything else ends the hover, as leaving the chart does. A touch tap on it isn't a tap elsewhere. Escape and `leave()` end the hover as before. With the pointer on the tooltip, the browser may then hit-test the mark it uncovers and send it a `pointerover`, though the pointer hasn't moved; that doesn't hover it, so the tooltip stays dismissed until the pointer moves. A linked chart shows no tooltip, so links don't change. It looks the same.
    - **The bridge.** Beside a mark, a clear `<div>` spans the 12 px between the box and the mark: a trapezoid from the box's edge to the mark's, 1 px into each (a `clip-path` polygon, which hit-testing follows). The box's height is a whole number of px (`offsetHeight`), and its edge can be a fraction of a px from that, so without the overlap a row of px could fall between them. The pointer can go straight from the mark onto the box across it. Without it, the pointer crossed 4 or 5 px of the next row on horizontal bars, and 10 to 13 px of nothing round a donut, and the hover went before it got there. At a point there's none: a crosshair's target is its whole column, which reaches the box, and a bridge there would catch a pointer running along a falling line.
    - **Why a bridge, not a delay.** Holding the hover for a moment while the pointer heads for the tooltip (the audit's other option) would get it there too, but every hover near a tooltip would wait. The bridge waits for nothing, and covers only the gap.
    - **Under the pointer.** A tooltip can come up, or move, under a pointer that didn't move onto it: a crosshair's does, since its column is the plot's height. Then it lets the pointer through (`ec-tooltip-through` on the layer) until the pointer is off it, so it never catches a pointer running along the chart. The tooltip hears the pointer on the document, before the chart does, to know.
    - **When it moves from under the pointer.** While the pointer is on it, a `MutationObserver` watches it. When a change moves it, resizes it or hides it, and it isn't under the pointer any more, the pointer hovers whatever it's over then (`elementFromPoint`), or nothing. If focus moved the hover meanwhile, the pointer hovers nothing until it next moves onto a mark, so a resting pointer never takes the hover from the keyboard. The pointer on the tooltip of a keyboard hover is on that target, so that hover stays past blur, as on the mark.
    - **What it costs.** While it shows it covers the marks under it, as it always did, and now the pointer can't reach them through it. They're reached round it, since a bar's target is its whole row or column, a slice's label hovers it too, and a line's x is its whole column, or by keyboard.
  - `tooltip` defaults to `true`: the category in bold, each series' value in `format` with its label ("16 goals · 4 assists"), and the total for a stack. A function `(d) => string` gives a row's text instead, with `\n` for line breaks. Its result is only ever set as `textContent`, never parsed as HTML. An empty string shows nothing, and a function that throws is reported and shows nothing. `false` turns it off; `update()` can change it.
  - The box is `aria-hidden`, so it isn't read twice. A tooltip function's text is also, by default, each mark's accessible description: `aria-describedby` points to a `<desc class="ec-description">` inside the mark, kept in step with updates, so whatever it adds beyond the values (a player's position, say) reaches screen readers.
  - `markDescription` decouples the two. A tooltip that repeats the values the mark's name already says would otherwise be read twice: "Okafor: 16 goals", then "Okafor · Forward, 16 goals". `markDescription: (d) => d.pos` describes with only what the name doesn't say. `false` describes nothing, and so do an empty string and a throw, which is reported. The demo uses it.
  - **Why the default stays the tooltip's text.** Without it, a custom tooltip's extra facts would be visible only, which loses information for screen-reader users. Reading something twice is the smaller harm, and `markDescription` removes it. The default text describes nothing, because the mark's `aria-label` already has its values (and the data table has the total).
  - Showing and hiding fade over `motion.duration(100, "feedback")`, so they're instant with motion off. A function is called once per row and data change, not on every frame.
  - Its styles use theme tokens: `--ec-surface`, `--ec-text`, and a hairline border in `--ec-ring`, so it follows light and dark like the chart.
- **Series labels** (`src/charts/series.ts`). A series is named after its field (a function's value is `"value"`), which is often an identifier: `xg`, `revenue_usd`. `seriesLabels` gives each a name for people, `{ goals: "Goals", xg: "Expected goals" }`, used as given wherever the chart names a series: the legend, the table's column headers, the default tooltip and mark names ("16 Goals · 4 Assists"), and the announcement of new series ("Showing Goals and Assists"). A series without one keeps its own name.
  - Keys don't change: segments' `data-series`, colours, `stack`, a hover event's `segment` and data effects' `related` all go by the series' own names. Labels for series the chart doesn't show yet are fine, so a page can name every metric up front.
  - It's used as given, with no change of case: a heading ("Goals") and a count in running text ("16 goals") want different cases in English, and the chart can't know which a language wants. The default tooltip and mark names follow the label ("16 Goals"); a page that wants "16 goals" there words them with `tooltip` or `markLabel`, whose `values` carry each label.
  - A lone value read by a function goes unnamed unless it's labelled: `seriesLabels: { value: "points" }` gives "Okafor: 16 points".
  - `update()` can change it: the legend, table and names follow as the update starts. New labels for the same series show the same view, so they aren't announced. Each label must be a non-blank string; anything else throws, and `update()` rejects.
- **Legend** (`src/charts/legend.ts`). A swatch and a name (the series' label) for each series, in stack order, in `<div class="ec-legend">` just before the `<svg>`. A single series has none. With `colorBy: "category"` it lists the categories instead, as the donut's does (see Colours below). `legend: false` turns it off.
  - The swatches take their colours from the chart's `ColorAssignment`, through `--ec-mark` as the segments do, so a series keeps its colour when the stack changes. The names are in `--ec-text`: text never takes a series colour.
  - **The page's entries.** `legend` is one of the options every chart shares. `legend: { entries: [{ label, color }] }` adds entries after the chart's own, for colours the page's effects draw, which a chart can't know about: `{ label: "Goals below xG", color: "negative" }`. `color` is a theme token (`"negative"`, `"series-3"`) or any CSS colour, set on the swatch as `--ec-mark`; `"mark"` and `"mark-strong"` throw, since an entry has no mark of its own. Each label must be a non-blank string. With entries, a single series is listed too, so its colour is named beside theirs. The page's entries have no `data-series` or `data-key`.
  - It follows `stack`, `colors` and `legend` as soon as an update starts. A rejected update leaves it as it was.
- **ARIA structure.** The `<svg>` is `role="group"`, named by `label` (`aria-label`) and described by `description` (a `<desc>`). Each mark is `role="img"`, named by its `aria-label` (the default name or `markLabel`'s) and described by `markDescription`'s text (by default a tooltip function's), and takes focus with the roving tabindex. Its text and shapes are `aria-hidden`, so its name is all that's read: "Okafor: 16 goals, 4 assists", never "Okafor" and "16" on their own. The grid, axis, focus ring and overlay are `aria-hidden`, and so is a mark while it leaves.
  - **Why `group` and `img`.** They're core ARIA, so every screen reader knows them. `img` has presentational children, so a mark is read as one item in browse mode too. Two alternatives were left out. The graphics roles (`graphics-document`, `graphics-symbol`) are mapped unevenly: browsers map `graphics-symbol` to an image, but screen readers announce `graphics-document` inconsistently, and an unsupported role falls back to nothing. With `list` and `listitem`, NVDA and JAWS often read a list item's text rather than its `aria-label`, so a bar would lose its units, and a list item isn't expected to take focus. The NVDA + Chrome check in [a11y-check.md](a11y-check.md) confirmed them; VoiceOver + Safari hasn't been run.
  - In NVDA's browse mode the arrow keys move NVDA's own cursor, which reads the next mark, rather than reaching the chart. Focus mode passes them to the chart, which moves focus and plays the story.
- **Data table** (`src/charts/table.ts`). The fallback every screen reader can read. `table` defaults to `true`: a closed `<details class="ec-table">` "Data table" after the `<svg>`, holding a `<table>` that scrolls sideways when it's too wide.
  - **Contents.** A `<caption>` from `label`, visually hidden, since the chart's own title is beside it. Column headers (`<th scope="col">`): the category, any extra columns, each series (by its label), a total when there's more than one series, then any extra columns placed after the values. The chart decides whether there's a total: one whose series don't add up, as a line chart's goals and xG won't, leaves it out. Each row's category is its header (`<th scope="row">`). Values are in the chart's `format`. Numbers are right-aligned, and so is an extra column holding only numbers. Text is set as text, never as HTML.
  - **Following the chart.** Rows are in visual order, so the table follows the sort. It changes as soon as an update starts, with the data, `stack`, `format`, `label` and `table`. Rows are kept by key and only changed cells are written, so an open table, and a screen reader's place in it, stay.
  - **Options.** `"hidden"` (or `{ hidden: true }`) keeps the table out of sight but still read: a visually hidden `<div>` instead of the `<details>`, since a closed `<details>` hides its contents from screen readers too. `false` removes it. An object adds `columns`, each `{ label, field, format?, after? }`, where `field` is a field name or `(d, i) => value`. They go after the category, as the prototype's position did, or, with `after: "values"`, last: after the series, the total and a donut's share, as the prototype's Difference column is. The donut's total row leaves their cells empty. Numbers in them use the chart's `format` unless the column has its own, and `null` or `undefined` shows nothing. It can also name the category header (`category`; default: the category's field name, or "Category" when a function reads it), the total header (`total`, default "Total", which also heads the [donut's](#donut-chart) total row), the donut's share header (`share`, default "Share"), each series' header (`series`, by series: `{ shots: "Shots" }`; default its `seriesLabels` name, or the series itself), and the summary (`summary`, default "Data table"). `series` names only the table's columns: a donut's value column, which `seriesLabels` would also rename in the slices' names and the centre, or a line chart's "Goals" and "xG", as the prototype heads them.
  - A column that throws makes `barChart()` throw, and `update()` reject, changing nothing.
  - Its styles use theme tokens: `--ec-text` for cells, `--ec-text-muted` for headers and the summary, `--ec-grid` for row rules, and `--ec-focus` for the summary's focus ring.
- **Announcements** (`src/charts/announce.ts`). `announce: true` adds a polite live region: a visually hidden `role="status"` (`aria-live="polite"`, `aria-atomic="true"`) beside the `<svg>`, which sums up each update as it starts. It's off by default.
  - **The chart's summary** is a sentence for each kind of change, joined with ". ". A new `label` is said as it is; otherwise new series are named by their labels ("Showing goals and assists"). Then the sort ("Sorted A to Z", "Sorted highest first", "In data order", "Sorted" for a comparator). Then the marks whose values changed: by name up to three ("Okafor and Tanaka changed"), counted past that ("5 of 8 changed"). That's skipped when the series changed, since every value did. Last come marks added and removed ("Added Novak. Removed 4"). An update that changes none of these says nothing.
  - **A function** `(change) => string | undefined` writes the page's own text instead. It's given the chart's summary (`text`) and the keys `changed`, `added` and `removed`, so a page can say "Matchweek 25: Okafor and Tanaka changed". It's called while `update()` runs, before it returns. An empty string or `undefined` says nothing; a function that throws is reported and says nothing.
  - The same text twice in a row is announced twice. Turning `announce` on with `update()` makes the region, and it announces from the next update, since screen readers miss text in a region that appears with it. Turning it off removes it.
- **Updates.** `update(next)` merges the options and checks them (if it can't draw the result, it rejects and changes nothing), then animates to the new state, calling the runner in its order: `interrupt()`, `exit` / `update` / `enter` as the change starts, `change()` on every frame for each mark whose geometry moved, `settle()` once it has settled. An `update` event means the mark's values changed; a re-sort or a new scale only moves it. An `update()` with `data`, or one that changes a value or adds or removes a mark, is [an update](#events-and-effect-slots) to the runner, so it ends the last one's `update` runs on the marks it leaves alone. A new `on` swaps the effects first, as above; `motion` can't be changed by `update()` yet.
  - **Presentation** (`motion.staged`) splits the change into two stages of 500 ms base each, `transition` timing. Values: bars resize, leaving bars shrink to zero and their labels fade, the scale retargets, and ticks the scale gains or loses fade in or out. Positions: rows move to their new slots, the bands and the chart's height follow, and entering bars grow in at their slots, their labels fading in, during the second half. A stage with nothing to do is skipped, so a re-sort alone takes 500 ms.
  - **Analysis** runs everything at once, as one stage as long as the stages it has to do together, which the scaling table caps at 200 ms. **Off** (including reduced motion with no viewer choice) jumps: everything lands before `update()` returns. So does a change of orientation.
  - **State.** Each mark keeps one `animated` value per property: its values by series (in data units, so a bar always reads true against the axis mid-change), its slot, and its presence (the labels' opacity as it enters or leaves). The chart keeps one each for the scale and the bands, and one opacity per tick. A stack that gains or loses a series keeps the old ones in place until they've shrunk away. In-between values are clamped where `describe.bar` can't draw them (a stack crossing zero mixes signs for a moment; values against the total's sign draw as 0). A mark that stays has its value label count between its totals; one entering or leaving shows its own value as it fades.
  - **Frames.** Every frame writes what moved, all in chart space: `d` for the segments, and positions for the labels and the pointer target. Rows move by their geometry rather than a group `transform`, because each frame needs the chart-space geometry for `change()` anyway, and an effect's own `transform` on the mark is in chart space too. When the transition settles, the chart draws exactly the layout.
  - **Interruptions.** Another `update()` mid-change retargets every value from where it is now, so nothing jumps, and stages again from there: values not yet at their targets take a values stage first. The earlier `update()`'s promise resolves at once. A resize mid-change lands it at once (resizes never animate).
  - **Leaving marks** stay, unhoverable, until they've faded out and their exit effects have finished; one that comes back meanwhile keeps its element and grows back from where it is. The promise resolves when the change has settled and the marks it removed are gone, or as soon as another `update()` supersedes it.
- **Colours** follow the series through a `ColorAssignment`: `colorAssignment(fixed?)` gives each key a palette slot (1–8), pinned or the next free one in the order keys are first seen, and never reassigns it. `colors` takes pinned slots or a shared assignment.
  - **New colours** (M13 decision 13). `update({ colors })` draws every bar on the change's first frame, so a bar the change leaves in place takes its new colour then, not as the change lands. With motion off, and with `colors` alone, it's at once. The donut and line charts already drew every mark on an update's first frame.
  - **Overlays follow every part.** When any of a bar's parts changes colour, the surface sets the overlays' colours again (`recolor()`): the run's group takes the first part's, and each path drawn in a part's colour (`data-part`) its part's, so a stack's later parts' paths, as `drawIn` draws them, follow. `expressive()` does the same when a read finds any part's colour changed.
  - **By category.** `colorBy: "category"` (the default is `"series"`) gives each bar its own slot instead, by its key (its category unless `key` is given), as the [donut](#donut-chart) colours its slices. So one assignment shared with a donut keeps each category's colour in both: the shot outcomes' columns match their slices, whichever chart meets them first. `colors` then pins slots by key.
  - The chart then never asks the assignment for its series' slot, so the series' name (`"shots"`) can't take a slot a shared assignment would give a category.
  - The legend lists the categories in the bars' order (`data-key`), then the page's `entries`, as the donut's does; one category is listed too.
  - It needs one series. On a stack it throws (a `TypeError`), and `update()` rejects a stack with it, changing nothing: a stack's segments colour by series. `update()` can switch between the two, and every bar takes its new colour on the change's first frame.
- **Motion.** `motion` takes a `Motion`, or a mode as this chart's author default: the viewer's choice on the page-wide motion and the device's reduced-motion setting still win, as they do over `setMode()`.

### Donut chart

```ts
donutChart("#shots", { label: "Shot outcomes", data: outcomes, category: "outcome", value: "shots", sort: "value", on: { hover: travel("soccer-ball"), update: "flash" } });
```

`donutChart` (`src/charts/donut.ts`, with the pure `donut-layout.ts`) is built on the same shell as the bar chart, so hover, focus, the tooltip, transitions, leaving marks, sizing and the update order behave alike. What differs:

- **Encoding.** `category` (a field or a function) names each slice, and is its key unless `key` is given; keys are converted with `String()` and must be unique. `value` (a numeric field or a function) sizes it. A slice's `series` is the value field's name, or `"value"` for a function, as a plain bar's one segment is. A missing value counts as 0, and a negative or non-finite one throws. A total of 0 draws no slices: they're still marks, named and in the table, with no angle.
- **Shape.** Each slice is a `describe.arc`, in the `d3.pie()` convention, so effects get the same geometry from our donut and from a D3 pie: from 12 o'clock, clockwise, in data order (`sort: "none"`, the default) or largest first (`sort: "value"`, ties in data order). The inner radius is 0.6 × the outer, as in the prototype. Slices are separated by 2 px strokes in `--ec-surface` rather than `padAngle`, so the angles stay true to the data. A slice with no angle draws nothing, not even its separator.
- **Layout.** 300 px high unless `height` says otherwise, as wide as the container (or `width`), with the ring centred. The ring is as large as the room left for labels allows wherever they land (the widest category beside it, a label's height above and below it), so it keeps its size as values change. When that leaves less than half the radius the chart could have, the ring takes half, and labels that don't fit are dropped. A resize re-lays out on the next frame, without animating; the labels' room is measured again once web fonts load.
- **Labels.** Outside the ring, the category over its share as a whole percent, on slices of 15° or more, in theme text colours. A label sits 10 px out at its slice's middle angle and leans away from the ring the way the slice points (beside it at 3 and 9 o'clock, above it at 12, below it at 6, and smoothly in between), so it never jumps as its slice turns. A label that would overlap the one before it, or going round the first, is dropped; every slice is still named in the legend, the tooltip, the table and its ARIA name.
- **Centre.** `center` is the text in the hole for the total: `(total, format) => string`, with `"\n"` between lines and the first line drawn large (26 px, shrunk to fit a narrow hole), or `false` for none. The default is the total in `format` over the value's series label ("406" over "shots"; the total alone for an unlabelled value read by a function). It's `aria-hidden`, and its text is added to the chart's description, after `description`, so the total is heard on entering the chart. A function that throws is reported and shows nothing.
- **Colours** are per slice, through a `ColorAssignment` keyed by the slice's key (its category unless `key` is given): `colors` takes slots pinned by category, or a shared assignment. A [bar chart](#bar-chart) with `colorBy: "category"` colours its bars the same way, so one assignment shared with it keeps each category's colour in both.
- **Legend.** One entry per category (`data-key`), in the slices' order, then the page's `entries`. One category is listed too, since the entry names its colour. `legend: false` turns it off.
- **Hover and keyboard** are the bar chart's. A slice is its own pointer target, and its label hovers it too; hover events carry no `segment`. The arrow keys go round the ring clockwise from 12 o'clock, so they follow `sort`: Right and Down to the next slice, Left and Up to the previous, Page Down and Page Up a tenth of the slices on or back, Home and End to the ends, with no wrap-around.
- **Focus ring and halos** are drawn above the slices, masked to outside the slice (`src/charts/render/outside.ts`, shared with the adapter), so they show evenly on every side; behind a slice they'd hide under the neighbour drawn after it. The ring is 2 px in `--ec-focus`, 2 px out, and takes an effect's `transform`. It can cover a 2 px band of a neighbour, which is dimmed while a slice is focused. While it runs, a halo (`flash`, `pulse`) can cover half its width of a neighbour.
- **Accessibility.** As on bars: the `<svg>` is `role="group"` named by `label`, and each slice `role="img"`, named by its category, its value in `format` with its series' label, and its share: "Saved: 112 shots, 28%". `markLabel(d, slice)` words it instead, given the bar chart's `MarkSummary` plus `share`, from 0 to 1. The tooltip is the category, then "112 shots · 28%". The data table lists the category, the value and a Share column, with a total row in `<tfoot>` whose first cell is its row header: "Total, 406, 100%".
- **Data effects** get the slice's row and samples from 0 at the start of its walk to its share at the end; `related(series)` finds only the slice's own series.
- **Updates.** `update()` merges and checks the options, and calls the runner in the same order as the bar chart. Each slice's name is worked out with the layout and the table, before anything changes, since with `table: false` and `center: false` it's the first thing to call `format`: a `format` that throws makes `donutChart()` throw, leaving nothing behind, and `update()` reject, changing nothing. Values animate in data units, so slices stay joined and every frame's angles are true shares. `update` fires only for slices whose own value changed, not for ones whose share moved because others changed.
  - **Presentation** has two stages of 500 ms base, `transition` timing. Values: slices resize, joined in the order they were in, and leaving slices shrink to nothing where they are. The turn: slices turn the shorter way round to their places in the new order (like bars passing each other when sorted, they can overlap as they go), the ring resizes, and entering slices grow in at their places in the second half. A stage with nothing to do is skipped, so a re-sort alone takes 500 ms. The total in the hole counts between totals.
  - **Analysis** runs one stage of at most 200 ms, and **Off** jumps: everything lands before `update()` returns.
  - **State.** Each slice keeps one `animated` value for its value, one for how far it has turned, and one for its presence (its label's opacity). The slices in the ring are laid end to end from their values; a slice still turning is part way from its start in the order it turns from to its start in the ring, the shorter way, chosen once so it can't flip mid-turn. So another `update()` mid-change carries on from where every slice is, and nothing jumps: slices still joined in the values stage go on from there, and slices turning turn on from where they are.
  - A donut whose total grows from 0 (or falls to it) shows its true shares from the first frame (or to the last): there are no shares to sweep through.

### Line chart

```ts
const chart = lineChart("#xg", { label: "Goals vs expected goals", data: weeks, x: "week", series: ["goals", "xg"],
  on: { decorate: only("goals", parallel(threshold({ compareTo: "xg" }), travel("soccer-ball", { ride: "on" }))) } });
chart.reveal(24.5); // the data up to week 24.5, as playback drives it
lineChart("#daily", { label: "Shots per day", data: days, x: "date", series: ["shots"], timeZone: "local" }); // Dates make a time axis
chart.update({ curve: "monotone" }); // eases each line into d3's curveMonotoneX
```

`lineChart` (`src/charts/line.ts`, with the pure `line-layout.ts`) is built on the same shell as the bar chart and the donut, so the tooltip, transitions, leaving marks, sizing and the update order behave alike. What differs:

- **Encoding.** `x` is a field or a function giving numbers or `Date`s (a time axis, below), and `series` lists numeric fields. There's one row per x, drawn in ascending x whatever the data's order. `key` defaults to the x, converted with `String()` (a `Date` with `toISOString()`), and must be unique; so must the x values, whatever the keys, since each x is one focus stop, one hit column and one place to reveal to. A value that's `null` or `undefined` is missing ([below](#missing-values)); `NaN`, the infinities and anything else that isn't a finite number throw, since they're usually a mistake. `hover` says what the pointer and the keys hover: an x, with the crosshair (`"x"`, the default), or the point nearest the pointer (`"point"`, [below](#line-chart)).
- **Marks.** Each series is a line mark keyed by its field: a `describe.line` through its rows (and with `curve: "monotone"`, the [bends](#curves) between them), 2.25 px wide with round joins and butt caps, so a coloured part ends exactly at its data. Each row's value is a point mark keyed `"<series>@<row key>"` (`goals@12`): a `describe.point` of radius 4.5, ringed in `--ec-surface` and hidden until its x is hovered or focused. A point is a dot, so `travel` does nothing on it and `threshold` draws nothing, while halos and `wiggle` still work: `only("goals", …)` matches the goals points too, and acts on the line alone. `marks()` gives the lines, then the revealed points by x. Series and keys that would join into the same point key throw, and so does a row's key that is also a line's or a point's (a row keyed `"goals@2"` beside a row `"2"`), since `focus(key)` takes either.
- **Data.** A line's `datum` is the row at its revealed end, its last value's. Its `samples` are one per revealed value (`t` by distance along the walk, `at` the row's x: on a time axis a `Date`, a new one for each sample), plus the end part way to the next row when the reveal falls between two with values, and `gapBefore` on the first after a gap. A curved line has one at each bend between two values too ([Curves](#curves)). `related(series)` is the other line. A point has its row and its one value (`{ t: 0, value, at }`), and `related(series)` is the other series' point at the same x. Marks that read each other through `related` hear `change()` together: when any line's data changes, every line's runs hear it, so a threshold on the goals line follows a change to xG alone; the same goes for a row's points.
- **Layout.** 300 px high unless `height` says otherwise, and as wide as the container (or `width`). Values run from 0 (or from the lowest value, if it's negative) to a nice maximum of all the data, with gridlines and ticks on the left. x spans the rows' range, labelled at both ends and at round steps of about a quarter of the range between them that don't come within 8 px of a neighbour (the prototype's 1, 10, 20, 30, 38); a single x sits in the middle. A time axis has its own steps and wording, below. Each line ends in a dot in its own colour.
- **Time axis.** An `x` that gives `Date`s makes one (`src/charts/time.ts`, pure and with no dependency). Every row's x must be the same kind, so numbers and dates together throw a `TypeError`, and so does an invalid `Date`. Inside, an x is its time in ms, so positions, transitions and the reveal work as on a number axis; only the ticks, the wording and the samples' `at` know it's a time.
  - **The zone.** `timeZone` is `"UTC"` (the default) or `"local"`, the viewer's clock, named as `Intl`'s option is so IANA names can join it later. In UTC a date-only value such as `new Date("2026-01-05")`, which JavaScript reads as UTC midnight, is 5 January on every machine, and screenshots match everywhere.
  - **Ticks.** Like the number axis's: both ends, and round steps of about a quarter of the range between them, dropped when they'd come within 8 px of a neighbour. The steps are 1, 5, 15 and 30 seconds and minutes; 1, 3, 6 and 12 hours; 1 and 2 days; a week (from Monday, as ISO 8601's); 1 and 3 months; then years in the number axis's nice steps. The step is the smallest that can be a quarter of the range, each unit taken at its longest (a day of 25 hours, a month of 31 days, a year of 366), so a leap year's days still go in quarters. Each tick falls on its boundary in the zone, found with `Date`'s own UTC or local setters, which handle daylight saving: a day at midnight, a month on its first, every other day from each month's 1st. Hours and smaller are found by stepping through elapsed time (hours a quarter of an hour at a time, since clocks change by whole quarter hours, Lord Howe Island's by half an hour) and kept where the clock shows a whole unit that's a multiple of the step, so an hour the clocks repeat has a tick each time, one they skip has none, and ticks stay on the hour after a half-hour change.
  - **Tick words.** Each tick is worded for its own level, the coarsest boundary it's on, through `Intl.DateTimeFormat` in the page's locale: the year on a year ("2026"), the month on a month ("Feb"), the day on a day ("Feb 8", "8 Feb" in `en-GB`), the time within a day ("3:00 PM", with seconds or milliseconds when it has them). The ends needn't be on a boundary, so each also says the levels up to the step's and up to the coarsest the axis crosses, to be placed even when the ticks between are dropped for room: "Jan 5, 2026" on an axis of years or of months into the next year, "Feb 5, 3:00 PM" on one of hours past midnight. A lone x says everything up to its year.
  - **Words for people.** Each x's name, the tooltip's title, the table's row headers and the announcements say an x one way: a medium date in the page's locale ("Jan 5, 2026"), with the time when any x has one ("Jan 5, 2026, 3:00 PM", to the second when any has seconds, and to the millisecond when any has those), so no two x's are said alike. `markLabel`'s summary has it as `category`. `xFormat(x)` words it instead, given the x as the data has it (a `Date`, or a number on a number axis, where it works too); the ticks keep their own wording, and a throw makes the chart throw and `update()` reject, as `format`'s does.
  - **Only the line chart.** A bar chart's category stays text, so columns over time are labelled by the page.
- **Room** (M11, with sides in M12). `room` is px the layout keeps clear for text an effect draws past the plot: a number, or `{ right, top }`, a side that isn't given 0.
  - **To the right** (a number, or `right`), of the end labels, or of the lines' ends with `labels: false`, for text past them, as a bar chart's `room` is past its labels. The plot is that much narrower, and the end labels stay beside it.
  - **Above the plot** (`top`), for text that rises above it: a `delta` past a line that ends near the top heading up goes up past its end label. The plot starts that much lower, `12 + top` px below the chart's top, and is that much shorter, its bottom and the x labels where they were, and the value labels, the gridlines and the end labels on it as it is. The chart keeps its height, as it keeps its width for `right`.
  - A number, `{}` and `{ right }` lay out as before, byte for byte, and 0 as unset. A bar chart's `room` stays a number: it's past its labels, in the bars' direction. Anything but a number of px, 0 or more, or an object whose `right` and `top` are each one or unset, throws a `RangeError` (`checkRoom` in `line-layout.ts`, called in `layout()`), and `update({ room })` lays the chart out again, as a change.
- **End labels.** In the right margin, which fits the widest label any row's value gives: each line's value in `format` with its series' label ("52 goals"), in theme text colours. Each is centred on its line's end and kept at least 16 px from the others (the prototype's rule): labels that would come closer move apart equally around where they'd sit. They count between values while a change or a reveal plays, rounded to the decimals the series' values have. `labels: false` turns them off. A function `(value, series, format) => string` words them; an empty string shows none, and a throw is reported once and keeps the default.
- **Hover.** Each revealed x is a target standing for every series' point there, so hover and leave events come in one batch per x (`goals@12` 1 of 2, `xg@12` 2 of 2), and each point turns `ec-hot`, showing in its strong colour. Each x has a hit column reaching halfway to its neighbours (the first from the chart's left edge, the last revealed one to its right edge), so the pointer hovers the nearest revealed x without reading coordinates. A dashed crosshair in `--ec-axis` marks the x, and the tooltip sits above the highest of its points: the x in bold, then each series' value with its label ("15 goals · 14.2 xg") and no total, or a tooltip function's text from the row. Nothing dims, since every series is read at once and the lines aren't hover targets, so `dim` does nothing with `hover: "x"`.
- **Keyboard and names.** The chart is one tab stop over its x's: the arrow keys go to the next or previous x (Down and Right to the next, Up and Left to the previous), Page Down and Page Up a page on or back, and Home and End to the ends, with no wrap-around. On numbers a page is a tenth of the x's revealed, rounded up. On a time axis it's a calendar month in the axis's zone: the first x a month or more on, or back, or the last x that way when none is that far. A month on keeps the day and the time of day, or ends a shorter month on its last day, as Temporal's `add` does: 31 January goes to 28 February, or the 29th in a leap year (`monthsOn` in `time.ts`). So ten years of days is 120 presses, not 3,653. An x with a missing value is a stop like any other. Focus hovers every series' point there (`source: "keyboard"`), and a focus ring goes round each one: 2 px in `--ec-focus` outside a 2 px gap in `--ec-surface`, behind the marks, as on bars, moving with an effect's `transform` on the point. Each x is `role="img"`, named like a stacked bar from its x and each series' value with its label, "12: 15 goals, 14.2 xg" ("Jan 5, 2026: 15 goals, 14.2 xg" on a time axis). `markLabel(d, mark)` words it, given the bar chart's `MarkSummary`, whose `category` is the x as text (its `total` adds the values up, though a line's rarely add up). The lines, points, end labels, ticks and crosshair are `aria-hidden`.
- **A hover on one point** (`hover: "point"`, M10 step 2). Each revealed point is a target of its own, instead of each x.
  - **The pointer.** The plot's hit area (`<rect class="ec-hit">`, a dot's radius past the plot all round) takes the pointer, and every move finds the revealed point nearest it, by distance in the `<svg>`'s units (`pointerHover`'s `moves`): it hovers once that's another point, as moving onto another element does, so after Escape or `leave()` the same point isn't hovered again until the pointer reaches another. Of two as near, the series first in `series` wins, then the first x; points drawn on each other go by their lines (below). A missing value has no point, and a point past the reveal can't be hovered. Touch does the same, a tap hovering the point nearest it. Leaving the plot, for the axes or the end labels, leaves. A click or tap there moves the tab stop to the point it hovers, as one on an x's column does, without the ring.
  - **Points drawn on each other** (M11 step 5). Where other lines' points are drawn within a px of the nearest, as where goals equal xG, the pointer hovers the one whose line passes nearest it. Before, the series first in `series` always won there, so the other point could be reached only by the keyboard.
    - A line's distance is to its stroke as drawn, curved and with its gaps, within two dots' radii (9 px) along it each way of the point, up to a gap. Each line's own nearest point within the px counts.
    - A point with no stroke there, a value alone between gaps, counts as its dot: its distance is to the dot's edge, and 0 on it. So the pointer on the dot hovers it, and the pointer on another line through it, just past the dot, hovers that line's point. The reach is two radii, not one, so that the line's stroke goes past the dot: with one, the stroke would end at the dot's edge, and the dot would be as near or nearer everywhere past it.
    - Of two as near, the series first in `series` wins, as before: so at the points' centre, where every line passes through.
    - It's the nearest point that the hover held on a dot (below) falls back to, and touch's and a click's too, so they keep the rule. The keys are as before.
    - It goes by the marks as the chart draws them, not as effects move them, as the nearest point does.
  - **What's hovered.** `hover` fires for the point alone (`goals@12` 1 of 1), and its hover effect plays on it. The point turns `ec-hot`, in its strong colour; its line gets `ec-hot-line` and its runs `ec-hot` (the surface's `hot`, as bars and slices have since #105), so with `dim` the `<svg>`'s `ec-hovering` fades every other line's body (its stroke and end dot), every point shown at rest (`ec-alone`), and every other mark's `.ec-follow` groups to `--ec-dim-opacity`. The end labels and the text effects draw keep their contrast. A line's own stroke stays in its colour: `ec-hot-line` isn't `ec-hot`, which would turn it strong.
  - **The tooltip** goes beside the point, as beside a bar: above it, or below it without room, with a bridge across the gap and an effect's `transform` followed. There's no crosshair. While it shows, the pointer on the hovered point's dot, as drawn and moved by its effects, stays on that point, though another is nearer, so it can go straight from the point onto the bridge, which starts a px inside the dot (WCAG 1.4.13, the audit's finding 7). Without that, a point drawn just above or below took the hover first. A bridge from the point's centre would do it too, but the pointer is on the dot when the hover starts, and a tooltip that comes up under the pointer lets it through. It says the x in bold, then that series' value with its label, or a tooltip function's text, given the row and `{ series }` (with `"x"` it's given the row alone). Each point's text is kept by an object for its row and series.
  - **Keys** (`keyboardFocus`'s `move`, which the chart gives). Left and Right go along the point's line to the next or previous x where it has a value, Home and End to its first and last, and Page Down and Page Up a page along it: on a time axis the first of its points a month or more on, or back, as for x's, and on numbers a tenth of its points, rounded up. Up and Down go to the point above or below at its x, by where they're drawn now, top to bottom, passing over the series missing there; two drawn at one height go in series order. Every key stops at the ends. Escape ends the hover and focus stays, with its ring.
  - **Focus stops and names.** The x's columns go (`.ec-columns` gets `display="none"`), and each live point has a stop in `<g class="ec-stops">`, above them: a `<g class="ec-stop" role="img">` holding a circle the size of its focus ring, unfilled, which gives its bounds to a screen reader's highlight and a magnifier. The stops are in the keyboard's order, line by line, each in ascending x, in the DOM too, and one is the tab stop. Each is named by its x and its value with its label, "12: 15 goals", or `markLabel(d, mark)` given that series alone in `values`, the point's key as `key` and its value as `total`, and described by a tooltip function's text for its series. The x's aren't named while their columns are hidden (M11 step 5): `markLabel` is called for the stops shown, once for each point, as the chart is drawn and as each update starts, and `update({ hover: "x" })` works out the x's names. Before, it was called for every x as well. Nor are the x's described, so a function written for points, `(d, { series })`, is never given a row alone. The ring goes round the focused point. `focus(key)` takes a point's key, or an x's for its first series' point there.
  - **Links** go by x, as before: a point hovered tells its link its own mark, whose linking value is its x, so the other sources hover their marks there. A link's hover here hovers every point at that x, each a target, in series order, with nothing dimmed and no tooltip or crosshair, as on an `"x"` chart.
  - **`update({ hover })`** changes it at once, before the rest of the update plays. A held hover ends, with its `leave` events, as `leave()` ends it. The new stops show, then the tab stop moves to the nearest of the new kind (a point's x, or an x's first series' point, or the nearest x's with a point when it has none) and focus with it, keeping its ring but not hovering, so nothing fires; then the old stops go. A link's hover from another source shows again in the new targets. Focus moves while the window is in the background too, when no focus events come. Anything but `"x"` or `"point"` throws a `TypeError`, and `update()` rejects it, changing nothing. Without `hover`, the chart draws and hovers as before, with no stops and no change to its DOM.
- **Reveal.** `reveal(x)` shows the data up to x, at once. It's a view, not a data change, so it fires no `enter`, `exit` or `update`.
  - Each line ends at x, part way between rows, and its runs hear `change()`, so decorations follow every frame of a playback: the threshold's colour, a ball riding the leading edge.
  - Points past x are hidden, with whatever effects drew on them, can't be hovered or focused, and aren't in `marks()`. If the focused x is hidden, focus moves to the nearest revealed x; a focused point's, to its line's nearest revealed point.
  - It's clamped to the rows' range and kept across `update()`. The default, `reveal(Infinity)`, shows everything, rows added later too; after `reveal(20)`, a row added past week 20 stays hidden until it's revealed. It takes a number, or a `Date` as its time in ms, which is how a time axis has its x's, so `playback({ from: +first, to: +last })` plays one. NaN, an invalid `Date` or anything else throws a `RangeError`.
  - The scales are laid out from all the data, so nothing moves while the line plays out, and the table, the names and the announcements cover all the data.
- **Legend and table.** The legend lists the series, then the page's `entries`, such as `{ label: "Goals below xG", color: "negative" }` for the colour its threshold draws. The table has a row per x: the x (headed by its field's name, or `table.category`), one column per series and no total, then the page's columns, where one with `after: "values"` (a Difference column) goes last.
- **Colours** follow the series through a `ColorAssignment`, as on bars.
- **Layers** (M13 decision 5). The overlay where runs draw is above the lines and below the points: the `<svg>` has its lines in one `.ec-marks`, then the overlay, then its points in a second `.ec-marks`, then the x's and the stops. So every run's drawing (`threshold`'s runs, `travel`'s icon, `trace`'s and `drawIn`'s strokes, and `delta`'s and `label`'s text) is above every line, end dot and end label, and below every point: a decoration never covers a point being read, as the red run crossed week 12's hovered goals point before. An end dot is part of its line, so a decoration still draws over it. The points are marks of their own, so `ec-morphing` hides them with the lines, and the overlay still hides while a switch switches and takes no pointer.
- **Updates.** `update()` merges and checks the options, and calls the runner in the shell's order. Values animate in data units, per row key. A line gets `update` when any of its values changed or its rows came, went or moved along x, and a point when its own value changed. A new row's points `enter` and a removed row's `exit`, as do a series' line and points when it's added or removed. Announcements name rows by their x; a function's `changed`, `added` and `removed` are row keys.
  - **Presentation** has two stages of 500 ms base, `transition` timing. Values: the rows' values and the value scale, ticks fading, a series' line fading in or out, and a change of [curve](#curves). Positions: rows move along x as the x range and the plot follow; a new row grows out of the nearest row that stays (the one before it, or after it when it's first), and a leaving row folds into its own. So a season that gains a week grows its line out of the last point, and one that loses its first week folds it in while the line's start stays on the plot's edge. Lines aren't cut at the new last x while everything is revealed, so rows removed from the end fold in too. A stage with nothing to do is skipped.
  - **Analysis** runs one stage of at most 200 ms, and **Off** jumps: everything lands before `update()` returns, with the geometry the events reported. Resizes re-lay out without animating.
  - With no row in common with what's shown, new rows have nothing to grow out of and appear at once.

#### Missing values

A series' value that's `null` or `undefined` is missing: `series` takes fields of `number | null | undefined`. A bar counts a missing value as 0, but a line can't: 0 is a value it would draw.

- **A gap in its line.** A missing value is no vertex of its line, so the line's geometry has a [gap](#gaps) from the value before to the value after, with `breaks` where each run starts. The stroke, its halo and `threshold`'s colour leave the gap out, and the walk runs straight across it, so `travel` jumps it. Missing values before a line's first value or after its last are no gap: the line starts and ends at values, with its end dot and label at its last.
- **No point.** A missing value has no point mark, so `marks()` and the hover's batch leave it out. A value with a gap on either side and no other value beside it has no stroke, so its point shows at rest (`ec-alone` on its `.ec-point`, which the stylesheet shows), in the series' colour, and strong when its x is hovered.
- **The x stays a stop.** It's a row, so it keeps its hit column, its focus stop and its place in the keyboard's order, and the crosshair stops there. Its name says each series' value and which is missing, "3: goals missing, 3.6 xg"; the tooltip says the same, "goals missing · 3.6 xg"; and the table's cell says "missing". `markLabel`'s `MarkSummary` lists only the values the x has, and its `total` adds those up. An x with every value missing has no point: its crosshair and tooltip show, at the crosshair's top, and it has no mark for `link()` to read a linking value from, so linked charts don't follow it. A focused x's ring goes round its points. An x with none has no point to ring, so keyboard focus there is a 2 px line in `--ec-focus` where the crosshair is, drawn as the ring is (`ec-focus-ring`, in `<g class="ec-focus">`, behind the marks). It's at 3:1 or more against `--ec-surface` in both themes, as the ring is, where the crosshair's `--ec-axis` is 1.8:1. It stays when Escape hides the crosshair and the tooltip, and the pointer's hover there shows the crosshair alone, as before. While the tooltip shows, it covers the line's top, as it covers the crosshair's.
- **A line with no values** up to the reveal is empty: no stroke, end dot or label, no samples, and no room taken from the other lines' labels. Its geometry is a walk with no length at its level, so effects draw nothing on it.
- **The scale** is laid out from the values there are, and a series with none counts for nothing; with no values at all it runs from 0 to 1.
- **The reveal.** A line revealed into a gap ends at its last value, with its end label there, and goes on from the next value once the reveal reaches it.
- **Changes.** A gap opens or closes as the change starts. A value that goes missing leaves at once from the stroke, and its point exits. A value that comes enters as a point, and starts where the walk ran across the gap: each row keeps a level for a missing value, where its line runs past that x (in proportion to x across the gap, level with its nearest value before the first or after the last, 0 with none), so the value grows out of the line in the values stage. A line gets `update` when a value goes missing or comes, as when it changes.
- **Samples** are the line's values, the missing ones left out, with `gapBefore` on the first after each gap, so `threshold` doesn't join them across it.

#### Curves

`curve: "monotone"` (`src/charts/curve.ts`, pure) draws each line as d3's `curveMonotoneX` does, by Steffen's method: a cubic between each two values, with tangents that keep it between them. So it passes through every value, is flat between two equal ones, and never goes above or below the values either side, and a line never shows a value the data doesn't have. Basis, cardinal and natural curves would, and a step's corners would jolt a riding icon (M10 decision 4). `"linear"`, the default, draws the marks it drew before `curve` came in, byte for byte. Anything else throws a `TypeError` naming it, and `update()` rejects it, changing nothing.

- **In the data's units.** The tangents are worked out in x and value (ms on a time axis). Any scale with x increasing maps that curve to the one d3 draws through the same points in px, so the curve keeps its shape at every size; only its flattening changes.
- **Flattened.** Each piece is a cubic Bézier, as d3 draws it, with its control points a third of the way apart in x, so its x runs evenly with its parameter. It's flattened through the scales into straight pieces at equal steps of x, by the bound `describe.shape` uses ([Shapes](#shapes)): within 0.1 px. Each end's tangent is kept between 0 and 3 times the piece's slope (Fritsch and Carlson's square), so every piece is monotone, between its two values, and never strays from a chord further than the chord's width, since the chord passes every value it does. So it takes no more pieces than its width in tenths of a px, and on a chart with ten or more rows a px a curve adds no vertex. The line is then `describe.line` through the rows and the bends, so its walk, outline, gaps, `slice()` and reveal work as a straight line's, its points sit at its rows, on the curve, and no effect needs to know.
- **Runs.** Each run between gaps is curved on its own, as d3's `.defined()` draws it: a run of two values is straight, and a value alone is its point. Part way through a change, two rows at the same x with the same value are one knot, as d3 skips a repeated point, and two with different values are joined straight, the curve starting again after them.
- **Samples.** Each row has its sample, as on a straight line, and each bend between two rows has one too, its `at` and `value` read off the curve and its `t` by distance, in order. So [`threshold`](#threshold)'s crossings are exact on the line as drawn, as on a straight one. A data effect that counts samples sees more than the rows; `delta` and `label` read the ends, which are rows or the reveal. Ten years of days in four series, curved, 960 px wide, has about 2.6 samples a day (9,647 a line, for 3,653 days), and lays them out in a little over twice the time a straight line takes.
- **The reveal.** The curve goes through every row, revealed or not, so a reveal doesn't change it. A line revealed between two rows ends where the curve is at that x, with its value and end label read off the curve, so playback draws the curve in.
- **Changes.** The rows' values ease as before, and the curve follows them on every frame. A row growing out of a neighbour, or folding into one, bends the curve only as much as it has grown: each tangent within two rows of it eases toward the curve without it, by the row's presence. Otherwise the curve would jump as the row started to grow, since a new value changes the tangents beside it (by up to 2.7 px on the line page's season, adding a week). An eased tangent can be too steep for the piece between the row and the one it grows from, so there the square holds it in: that piece has a corner at its end until the row is there in full, and never goes past its values.
- **`update({ curve })`** plays as a change, in the values stage: each piece's tangents ease between its own slope (straight) and the curve's, which keeps it between its two values all the way. Off jumps. Nothing enters or updates, focus stays, and decorations follow through `change()`.

### Switching between charts

```ts
const shots = chartSwitch("#shots", {
  views: {
    donut: (el, colors) => donutChart(el, { label: "Shot outcomes, share of total", data, category: "outcome", value: "shots", colors }),
    columns: (el, colors) => barChart(el, { label: "Shot outcomes, counts", data, x: "outcome", y: "shots", orientation: "vertical", colorBy: "category", colors })
  },
  initial: "donut",
  announce: true
});
shots.show("columns"); // → Promise<void>; also shots.current, shots.chart("columns") and shots.destroy()
shots.on("hover", (event) => console.log(event.data.datum.shots)); // the view on show's, as are shots.marks() and shots.leave()
link([shots, totals]); // its view on show hovers with the bars beside it
```

`chartSwitch(target, { views, initial, transition, colors, announce })` (`src/charts/switch.ts`) shows views of the same data in one place, one at a time, and turns each mark of one view into its own mark in the next with a [transition effect](#transition-effects), as the morph demo turns its donut into columns. It reads only what it uses of a chart's handle (`ChartSwitchView`: `element`, `marks()`, `labels()`, `focus(key)`, `leave()` and `destroy()`, the optional `paintOf(key)`, `standsFor(key)` and `moveTabStop(key)`, and a reference chart's `on()` and its hover for links), so it never names a chart type, and adapters can join later. It never names an effect either: the composition root fills in `transition` with [`morph()`](#morph) when it's left out.

- **Views.** Each view is a function that draws its chart in the container it's given and returns the chart. It's also given the switch's `ColorAssignment` (`colors`, or a new one): pass it to the chart as its `colors`, so a key has one colour in every view and in the overlay. Bars colour by category (`colorBy: "category"`) to match a donut's slices. Every view is drawn when the switch is made. `chart(view)` returns a view's chart, typed as its function returns it, for `update()` and the rest. `current` is the view shown, or the one a switch is heading for.
- **The view on show** (M9 step 2). `on(type, listener)`, `marks()` and `leave()` are the view on show's, `current`'s, as its chart's are, so a page can call them as on a chart, and a switch is a `LinkSource`. `on()` hears only the view on show. The old view's hover ends as a switch starts, while it's still the view on show, so its `leave` events are heard; from then the view the switch is heading for is the one heard, and `marks()` gives its marks. A view's chart without `on()` isn't heard. The events' rows are the views' charts' rows, as a union.
- **In a link,** the view on show takes part, as a chart would: see [Linked hover](#linked-hover).
- **Layout.** `<div class="ec-switch">` in `target` holds a `<div class="ec-switch-view" data-view>` per view, stacked in one grid cell, then the overlay, `<svg class="ec-chart ec-switch-overlay" aria-hidden="true">`, over the cell and taking no pointer events. The overlay has the charts' class, so copied labels keep the stylesheet's text sizes. The cell is as tall as the tallest view, so the page below doesn't move when the view changes.
- **The inactive view** has `ec-switch-inactive` (`visibility: hidden`), `inert` and `aria-hidden="true"`, so it can't be seen, reached or read. It keeps its layout (a container with no width would lay its chart out at the 640 px fallback), so its geometry is ready for a switch. One view is in the accessibility tree at a time, with its own table.
- **A switch,** `show(view)`:
  - **Focus is read first.** If it's in the old view, the switch remembers the keys the focused stop stands for before anything is hidden, since a browser may move focus off a hidden element. The stop's key is the `data-key` of the focused element or its nearest ancestor with one, in the chart's `<svg>`. It stands for the keys its chart's `standsFor(key)` gives, or else for itself: a line chart's x stands for each series' point key there, in series order (a missing value's too, which another view may have), then itself (M11 step 1). If focus is outside the old view (on a toggle, say), the switch reads that view's tab stop instead, the element with `tabindex="0"`, and the keys it stands for, so Tab can land on the same week in the new view (M12 step 1).
  - **The old view's hover ends** with its chart's `leave()`, as the viewer's would: the tooltip, the emphasis and the hover runs end, with their `leave` events. A link's hover there ends too, and a link hears the viewer's end. Focus stays where it is, already read, until the view turns inert: a browser then takes focus off it (Chromium on its next rendering update, with a blur), and jsdom leaves it there.
  - **Both views' marks hide.** Both views take `ec-switching` and `inert`, and their `<svg>`s `ec-morphing`, which hides their marks and mark labels ([Rendering](#rendering)). `ec-switching` also hides what that leaves: the focus ring, the effects' overlay and a line chart's x's. The new view shows, its other parts faded out.
  - **Overlay px.** Each view's marks and labels are mapped into the overlay's px from where its `<svg>` sits: its screen CTM against the overlay's. Where there's no layout, as in jsdom, a view's coordinates are the overlay's. A mark's path data moves through the same transform, arcs and all, and its gaps stay at the same t, since the transform scales every length along the walk alike.
  - **Pairs.** Marks in both views are paired by key, in the new view's order, and played through the [transition player](#playing-transitions) on the overlay.
  - **Colours** (M11 step 1). Each view's chart says how it paints each mark with `paintOf(key)`: the name its colour comes from in the shared assignment, and whether it's drawn at rest. A bar's name is its key with `colorBy: "category"`, and otherwise its first part's series; a slice's is its key; a line's and its points' are their series. A pair's group is drawn in its new view's colour (`colors.slot(name)`), both ways, so a switch back mid-way draws the same picture. Pages keep the two the same, as `colors` and `colorBy` do. A view without `paintOf`, or a key it doesn't know, is drawn by key, drawn at rest, as before, so a donut and its category columns draw as they did.
  - **Marks not drawn at rest.** A mark its view doesn't draw at rest (a line chart's point, but for a value alone between gaps) starts or ends as a dot of no size at its centre (`describe.point` with `r: 0`), so a column grows out of its point and shrinks back into it. A pair that neither view draws isn't played, so two line charts' points stay hidden.
  - **End dots and rings** (M12 step 1). A chart's `paintOf(key)` can also give `end`, the radius of the dot it draws at the end of a mark's walk (a line chart's line: 4.5), and `ring`, the width of the ring in `--ec-surface` it draws round the mark's filled shape, or round that dot (2 round a point and an end dot). Both are in the view's `<svg>` units, so they scale into overlay px as a mark's thickness does, and a mark not drawn at rest has neither. The switch draws them as the chart does:
    - **An end dot** is a `<circle class="ec-switch-end">` at its line's walk's `end`, filled with `--ec-mark` and stroked with `--ec-surface` at the ring's width. A pair whose two sides both have one draws one dot in the pair's group, after its shape, so it's above its line and below the marks stacked above it, as in the chart. It moves in a straight line from the old end to the new one at s, the shapes' eased progress, as morph moves a line's ends, and its radius and ring are mixed the same way, so it stays on the line's end on every frame and a switch back doesn't jump. A dot whose partner has none fades where it stands, in its own view's colour, as a mark with no partner does.
    - **A ring** is the surface-coloured stroke on each filled path a pair's run draws, its width mixed at s from the old side's to the new side's, 0 for a side without one. So a value alone between gaps keeps its ring into the next line chart, and loses it as it grows into its column. The switch wraps the run's layer to draw it, and sets the width each frame after the run draws.
    - **A view without them,** or a mark its chart gives neither for, draws as before: the morph page's donut and columns are byte for byte what they were (`src/line-switch.test.ts`).
  - **Labels** pair by key and role. Each pair moves in a straight line from the old label's place to the new one's. A copy of each `<text>`, with the chart's classes, goes along, and the new one's text shows from half way: "14%" becomes "58". A label with no partner fades where it is.
  - **Unmatched marks.** A key in only one view fades where it stands, drawn as its outline in its view's colour, with its own ring and end dot: out over the first half, or in over the second. One its view doesn't draw at rest doesn't fade at all.
  - **The other parts.** The old view's axes, centre text, legend and table fade out by 40% of the way, and the new view's fade in from half way, as the prototype's centre and baseline do. The view's container fades; its marks are hidden anyway.
  - **Timing.** 950 ms base with `transition` timing, in one stage: 950 ms in Presentation, 200 ms in Analysis. Everything is drawn from one number, the shapes' eased progress, which the switch works out as morph does. Its own tween has morph's timing and starts at the same time as the pairs' runs, on the same clock: everything a run starts as it begins takes one reading of the clock. A live clock (`performance.now()`) moves while the runs sample their outlines and draw their first frame, so a tween made after them would lag the shapes, and a switch back would jump (by up to 0.6 px in headless Chromium). A transition effect can't report its progress, so this schedule is the switch's: an effect that keeps to it (950 ms base, `easeInOutCubic`, and from `start` the rest of a full run's time, as [morph](#morph) does) stays in step with the labels and fades and reverses with no jump. One with other timing still plays, but its shapes drift from the labels and a switch back can jump ([the guide](effects-guide.md#transition-effects-and-checktransition) says so to effect authors).
  - **Landing.** Once the tween and the pairs' runs have finished, the overlay empties and both `<svg>`s lose `ec-morphing`. The new view becomes the active one and the old one inactive, and `show()` resolves. Focus that was in the old view goes to the first remembered key the new one takes (`focus(key)`, as a key press would: the ring shows and the hover plays). When the new view takes none of them, it goes to the new view's first mark. Focus that has moved on outside the switch meanwhile stays where it is. When focus isn't going in, because it was outside the old view or has moved on, the new view's tab stop moves to the first remembered key it takes, with its chart's `moveTabStop(key)`: the stop moves without focus, so no ring shows and nothing hovers, and Tab from the toggle lands on that key. A view without it, or one that takes none of the keys, keeps its own tab stop (M12 step 1). Then a link's hover from another source, if there is one, shows in the new view.
- **Interrupting.**
  - **A `show()` back** to the view a switch is leaving reverses it from where the shapes are. The runs are cleared, and the pairs play back from `start: 1 − p`, where p is the shapes' eased progress, so the reverse begins with the picture the switch had drawn and takes the rest of a full switch's time. The labels, the fades and the views' opacity are drawn from where the switch is between its two views, as the prototype draws its card from one `t`, so they go back the way they came, with no jump. A reverse reverses the same way.
  - **A `show()` to a third view** lands the switch first and switches from there, carrying the focus it remembered. **A resize** (the cell's width changing by half a px or more) lands it, since the shapes it began with are stale, and so does motion turning off.
  - A `show()` for the view a switch is heading for returns the same promise, and one for the view shown does nothing. An earlier `show()`'s promise resolves as soon as another replaces it. A `show()` a `leave` listener calls as the old view's hover ends runs once the switch has begun, as if called just after, and a `destroy()` there stops the switch from starting.
- **Motion off** (reduced motion included, with no viewer choice). `show()` lands before it returns, without playing the transition, and focus, the tab stop and the announcement follow at once.
- **`announce`** is off by default. With `announce: true`, a polite live region (`role="status"`, as a chart's) after the overlay says the new view's label, its chart's `label`, after each switch.
- **Errors.** Options that aren't a switch's throw a `TypeError`: no views, a view that isn't a function, an `initial` that isn't one of them, a `transition` that isn't a transition effect, or an `announce` that isn't a boolean. So does a view's function that doesn't return the chart it drew in its container; the views drawn so far are destroyed, leaving nothing behind. `show()` rejects for a view the switch doesn't have, and `chart()` throws.
- `destroy()` ends any switch, destroys every view's chart and removes everything the switch added.
- **Line charts** (M11 step 1). A line chart is a view like any other, through `paintOf`, `standsFor` and `moveTabStop`; the switch never names it.
  - **To columns.** A page keys its columns as the points are, with the bar chart's `key` (``key: (d) => `goals@${d.week}` ``). Each point pairs with its column and grows into it from a dot of no size at its centre, or from its own dot, with its ring, when it's alone between gaps. The lines and the points with no column have no partner: the lines fade out over the first half with their end dots, and the hidden points aren't drawn. Back, each column shrinks into its point and the lines fade in. The end labels have no partner among the columns' labels, so they fade, and the columns' names and values fade in.
  - **To another line chart.** Lines pair by series and morph by x ([morph](#morph)), their end dots move from end to end, and the end labels move. Points are drawn in neither view, so they aren't played, but for a value alone between gaps, which plays as its dot, with its ring.
  - **Focus follows the x.** From an x to its first series' column at that x (each series tried in turn, then the x itself, then the first mark), and from a column back to its x, or to its point with `hover: "point"`. With focus on a toggle, the tab stop follows the same way (M12 step 1).
  - **A link** through the switch works as before: a line chart on show takes part by x.
  - Adapters' attachments as views are backlog.

## Adapters

`expressive(target, options)` attaches effects to SVG marks drawn by other code (`src/charts/adapter/`). `target` is a selector, an element, a list of elements, or anything with `nodes()` and `data()` like a D3 selection, whose data types the callbacks. (A D3 selection's `data()` is overloaded, and TypeScript infers from the last overload, so `MarkSource` also takes an optional `each`, whose callback carries the row type. The adapter never calls it.) Like a chart, it gets a `ChartEnv` from the composition root, resolves `on` through the preset registry and plays it through the runner.

```ts
const fx = expressive(d3.selectAll("#goals rect"), {
  key: (d) => d.data.name,                          // required: marks are matched by key
  segment: (_d, el) => el.parentNode.__data__.key,  // rects sharing a key are one mark's segments
  value: (d) => d[1] - d[0],                        // what each rect shows, so a resize isn't an update
  keyboard: true,
  markLabel: (d) => `${d.data.name}: ${d.data.goals} goals, ${d.data.assists} assists`, // one name per bar
  on: { hover: sequence(travel("soccer-ball", { along: "goals" }), travel("cleat", { along: "assists" })) }
});
fx.refresh(d3.selectAll("#goals rect"));             // after the host re-renders

// A D3 donut, read by tag: each path d3.arc() drew in a centred <g> is a slice, through describe.arc.
const donut = expressive(d3.selectAll("#shots path"), {
  key: (d) => d.data.outcome,
  value: (d) => d.value,      // or one new value updates every slice: the total changes, so every arc does
  keyboard: true,             // clockwise from 12 o'clock
  markLabel: (d) => `${d.data.outcome}: ${d.value} shots`,
  on: { hover: travel("soccer-ball") }
});

// Two d3.line() paths, one per series ({ series, rows }), in a margin <g>: each described from the
// points that drew it, with samples from the same points. threshold reads xG through related("xg"),
// and a ball rides the goals line's end. The page reveals the season itself, each frame giving each
// path its rows so far (paths.datum(…).attr("d", …)); watch follows it.
const season = expressive(d3.selectAll("#season path.line"), {
  key: (d) => d.series,
  geometry: (_el, d, key) => describe.line({ key, series: d.series, points: d.rows.map((r) => ({ x: x(r.week), y: y(r.value) })), width: 2 }),
  samples: (d, mark) => samplesAlong(mark, d.rows.map((r) => ({ x: x(r.week), y: y(r.value), value: r.value, at: r.week }))),
  dim: true,                  // the others fade, and the hovered line's stroke takes its strong colour
  watch: true,                // see Watch below
  on: { decorate: only("goals", parallel(threshold({ compareTo: "xg" }), travel("soccer-ball", { ride: "on" }))) }
});

// Read by their tags, with no geometry: a D3 scatter's circles are points, and a curve drawn with
// curveMonotoneX and .defined() is a line with its gaps, from its own path data.
const dots = expressive(d3.selectAll("#scatter circle"), { key: (d) => d.name, value: (d) => d.goals, keyboard: true });
const curves = expressive(d3.selectAll("#season path.curve"), {
  key: (d) => d.series,
  segment: (d) => d.series,   // a shape's series, which threshold reads through related("xg")
  samples: (d, mark) => samplesAlong(mark, d.rows.map((r) => ({ x: x(r.week), y: y(r.value), value: r.value, at: r.week }))),
  on: { decorate: only("goals", threshold({ compareTo: "xg" })) }
});
```

- **Rows and keys.** `datum` defaults to a selection's `data()`, then to `element.__data__` (D3's convention). When `__data__` is a number and no `datum` is given, the adapter warns that it looks like Plot. Keys are converted with `String()`. Rects that share a key throw unless `segment` names each part, and a part named twice throws. A circle or another shape is a mark of its own, so a key it shares with any other element throws a `TypeError` naming the key, with `segment` or without.
- **Values.** `value(datum, element)` returns what an element shows (a stack point's `d[1] - d[0]`, a row's field), so `refresh()` can tell a change in values from a re-layout. With it, an `update` means a part's value changed or the mark gained or lost a segment, as on the reference charts, and a resize or a new axis maximum only moves the marks. Values compare with `===`, except that NaN equals NaN, so it should return a number or a string (a date's `getTime()`, or several values joined). Without `value`, the adapter compares lengths: an `update` means a mark's length or segments changed, so a redraw at a new width or with a new axis maximum updates every bar, and with `update: "flash"` every bar flashes. On a pie, one new value changes the total and so every arc's length: without `value`, every slice updates; with `value: (d) => d.value`, only that slice does, and the others move round.
  - It compares values, not rows: Vega binds new scenegraph items on every render, a page that copies its rows makes every row new, and a row holds fields its bar doesn't show (a goals bar's row has the assists too).
  - A flag on `refresh()` saying that only the layout changed would be simpler, but it can't help when values and the axis change in the same redraw, which is just when a growing value pushes the axis out.
  - **An update.** A `refresh()` that finds a new row (a mark's datum is another object), a new value (or length, without `value`), or a mark entering or leaving is [an update](#events-and-effect-slots): it ends the last one's `update` runs on the marks it leaves alone, so a page's `delta` goes when it joins the next week's rows, even if nobody scored. One that finds none of these, a resize or a host's render for a hover, keeps them. Vega marks each row it takes with a symbol, so rows a page spreads from Vega's (`{ ...row }`) are the same rows to Vega, and it draws nothing new.
- **Geometry.** `<rect>` marks are described with `describe.bar`, in the coordinates of the marks' nearest common ancestor (a lone mark's parent). Each rect's box is converted through its parent's CTM (`getScreenCTM()` where there's layout, otherwise the transform attributes, as in jsdom, which can't see nested `<svg>` viewports or CSS transforms) and its own `transform` attribute. Its own CSS transform isn't read: that's where effects move it, and reading it back would feed an effect's offset into the geometry. Each read takes an element's CTM once, so marks that share a parent cost one. A mark's segments are ordered from the baseline by position, never by DOM order, since Vega-Lite stacks alphabetically. A gap the host leaves between segments becomes `describe.bar`'s `gap`, and the tip takes the tip rect's `rx`. A rect its transforms rotate or skew (anything but scales, flips and quarter turns) isn't an upright bar: one of its own is a shape (below), and one that shares its key with other rects throws a `TypeError`, since a bar's segments are upright.
- **Circles and shapes** (M9 step 6). Each is a mark of its own, read through the same matrix as a rect: its parent's CTM, then its own `transform` attribute. Lengths are read as the browser resolves them (`baseVal`: percentages, units), or as written where there's no layout.
  - **A `<circle>`** is [`describe.point`](#builders) at its centre, with its radius, both through the matrix. A turn, a flip or an even scale keeps it round: the matrix's columns are the same length and at right angles, to within a ten-thousandth, so a browser's rounding doesn't make it an ellipse, and the radius is scaled. Under an uneven scale or a skew it's an ellipse, read as a shape. A circle with a radius of 0 is still a dot, of size 0, since a host may grow it from 0.
  - **A `<path>`, `<line>`, `<polyline>`, `<polygon>` or `<ellipse>`** is read through [`describe.shape`](#shapes), with the matrix as its `matrix`: a path from its own `d`, unrounded, and the others from their outlines as path data, written by `shapeOutline` in `src/core/geometry/path.ts`, which `iconFromSvg` shares. So a curve keeps its curve, a line drawn with `.defined()` its gaps, and an area or a polygon is a closed shape with no direction.
  - **A `<rect>` turned or skewed** (M11 step 4) is a closed shape too, read through `describe.shape` from its outline, its rounded corners with it (`rx` and `ry` as SVG reads them: a missing one takes the other's, and each is at most half its side), moved by its matrix, as a `<polygon>` is. A rect upright is a bar, as before, and with a turned one among bars, every mark keeps document order, as with a circle or a shape among them.
  - **A slice** (M11 step 4, `src/charts/adapter/slice.ts`). A `<path>` whose data draws a ring's slice is [`describe.arc`](#builders), so effects treat it as our donut's slices: one circular arc with two straight sides through its centre (a pie's), two arcs about one centre, one each way, joined along radii (a donut's), or a whole ring, two whole circles about one centre, one each way, as `d3.arc()` draws them. Where the path starts and which way round it goes don't matter.
    - **Read in its own coordinates,** where a host writes its arcs' radii as it means them, then moved through the matrix: the centre by it, the radii by its scale and the angles by its turn, in `d3.pie()`'s convention (radians, 0 at 12 o'clock, clockwise), a flip turning them the other way. So a browser's rounding in a turned group's CTM doesn't make the arcs ellipses. The matrix must keep circles, as a circle's must to stay a point.
    - **The centre** comes from the points the path is written through, never from an arc's own centre, which a host's rounding leaves unsure by far more than the rounding when the arc is a fraction of a px long, or half a turn (a third of a px, with `d3.arc()`'s 3 decimals). A donut's is the outer radius on from each side's outer end, along the side, which holds however narrow the slice. A pie's is where its sides meet. A whole ring's is halfway between the points its outer circle's two half turns are written between, or through three of them, for more arcs; a circle written in two arcs that aren't half turns takes its first arc's own centre, which is sure for an arc that isn't one. A donut's slice so thin that its inner arc rounds away to a point has a pie's form, and is read as a donut's by where that point is. How far each arc turns is measured about that centre.
    - **Within 0.5 px.** The path's corners must be within 0.5 px of the slice's, each arc within 0.5 px of its circle at its ends and its middle, and each arc must turn as far as the slice. Anything else is a shape, as before: a slice with rounded corners (more arcs, about other centres), one with an elliptical arc, or one under a matrix that stretches or skews; a disc (a whole circle alone, which `d3.arc()` draws for a pie with one value: it's a circle, a closed shape); and a donut's slice with a pad angle once its sides are more than 0.5 px off radii, from about 0.02 rad at the donut page's sizes (a smaller pad angle, such as 0.01, reads as slices, and near 0.02 one donut can have both). A pie's padded slice has its sides through its centre, since `d3.arc()` pads only its arc, so it's a slice of the padded angles. A slice of no angle draws a line there and back, and is a shape.
    - Slices round one centre are ordered clockwise from 12 o'clock (Order, below), as with `geometry`. `geometry` still gives a page the shapes, or a padded donut's slices.
  - **An open shape's width** is its stroke width as drawn, in its own units: the computed `stroke-width`, even a 1 px that the page's CSS sets over the attributes. jsdom computes no presentation attributes, so there, found as for [colours](#adapters), a computed 1, the initial value, gives way to the nearest `stroke-width` attribute on the shape or above it, passing over one that can't be read, as SVG does, and stopping at an inline style, which jsdom computes. The matrix scales it by the square root of its determinant, exactly for an even scale and on average for an uneven one. A width of 0, or none in px, reads as 1 px, `describe.shape`'s default, since `describe.shape` needs more than 0 and the shape is still a line to walk.
  - **A non-scaling stroke** (M11 step 4). With `vector-effect: non-scaling-stroke`, as an attribute or a computed style, the width is in screen px, as a browser draws it, and the shape's transforms don't scale it. Where there's layout, it's turned into the marks' units by the common ancestor's screen scale (the square root of its screen CTM's determinant), so a page zoomed to half size reads a 3 px stroke as 6 units. Where there isn't, as in jsdom, it's kept as given. `vector-effect` isn't inherited, so it's read from the shape alone: a browser's computed value, or in jsdom, where a computed `none` may be the attribute unread, the shape's own attribute, unless an inline style sets it.
  - **A shape SVG wouldn't draw** (no path data, or only moves; an ellipse with a radius of 0; a polyline of one point) isn't a mark, as a Vega line with no point drawn isn't. `refresh()` reads it once it draws something, and it enters then.
  - **`segment`** names a circle's or a shape's `series`, as `describe`'s `series` does, so a data effect reads another of them through `related`, as two D3 curves above.
  - Any other element (`<text>`, `<g>`, `<use>`, `<image>`) throws a `TypeError` naming its tag.
- **`geometry(element, datum, key)`** wins over all of it: with it, every mark is the page's, called once per mark with its first element, and must return a geometry with that key. A page uses it for elements the adapter can't read, a stack whose rects its transforms turn, or to say more or other than an element shows: a padded donut's slice as `describe.arc`, which goes round the donut's centre (read as a shape, each slice has its own centre, so the slices would keep document order), a pie's slice as the shape its path draws, or a straight line by its points, with `breaks`.
- **Order.** `marks()` and keyboard focus follow visual order. Rects alone go top to bottom for bars and left to right for columns. Other marks keep document order: circles, shapes, marks described with `geometry`, and bars among circles or shapes. But marks that go round one pivot go clockwise from 12 o'clock, by the angle of each mark's `center` about that pivot in screen coordinates, in [0, 2π). They go round it when each `pivot` is within 0.5 px of the first, and each mark's `start`, `center` and `end` are the same distance from it (give or take 0.5 px), more than 0.5 px away, as a pie's slices are, read by tag or described with `describe.arc`. A circle's or a closed shape's pivot is its centre, so dots never go round one, and nor do lines that start at one point (cumulative goals and xG both at 0): a line's pivot is its first point, on its own walk, so they share a pivot without going round it. `d3.pie()` sorts slices by value, largest first, but returns its arcs in data order, so document order would make the arrow keys jump around the ring. The rule reads geometry, not a chart type. A mark's own parts (`HostMark.parts`) keep document order.
- **Baseline.** `"auto"` (the default) finds the line every mark has an edge on. A mark whose near edge (left, or bottom for columns) is on it grows away from it; one whose far edge is on it grows the other way, like a negative bar. When bars and columns both fit (one mark, or marks of one size), marks spread down the page are bars and marks spread across are columns. If no line is shared it throws: pass the edge.
- **Overlay.** Runs draw in `<g class="ec-overlay">`, the root `<svg>`'s last child, with the common ancestor's transform. So they share the marks' coordinates but never sit inside a group the host manages (Vega removes foreign children from its groups when it redraws). It holds the halos, the run groups and the focus ring, and `refresh()` moves it back to the end and recomputes its transform, as `watch` does when an ancestor at or above the common ancestor changes. Its text (`.ec-overlay .ec-text`) is sized as on our charts, 12.5 px, weight 600, with tabular digits, in `:where()`, so the page's CSS still wins.
- **Events.** Pointer and touch hover and keys are listened for once, on the root `<svg>`. Focus events are heard on its document or shadow root instead, because Chrome makes an SVG element with focus listeners of its own a tab stop; `refresh()` picks that again, so an `<svg>` moved into or out of a shadow root keeps working. An event's target is mapped to its mark through a lookup that `refresh()` rebuilds, so marks the host replaces keep working. Hover events carry the segment under the pointer.
- **Keyboard.** `keyboard: true` adds the [bar chart's](#bar-chart) keyboard focus, on the host's elements: both use `src/charts/keyboard.ts`, so they behave alike. The chart is one tab stop (the first mark in visual order, as under Order above, then whichever was focused last). The arrow keys move to the next or previous mark, Page Down and Page Up a tenth of the marks on or back, Home and End to the ends, and keys pressed with Alt, Ctrl or Meta are left to the browser.
  - Focus that follows a key press plays the hover effects (`source: "keyboard"`). Focus from a click or tap moves the tab stop but leaves the hover to the pointer, so a tap still reports `"touch"`. Escape stops the effects and keeps focus; blur leaves. Pointer and focus share one hover: focus arriving on the mark under the pointer holds that hover until blur, and a blur with the pointer still over the mark leaves it to the pointer.
  - A mark's first element gets its `tabindex` (`"0"` on the tab stop, `"-1"` on the others) and its other segments `"-1"`, so a click on any of them focuses the mark. Focus that lands on one of a mark's elements marked `aria-hidden="true"` (a segment `markLabel` hides) moves on to the mark's first element, which carries its name, so focus never rests where a screen reader can't follow. The adapter writes them through its edits, so `destroy()` puts back the host's own, and writes them again on every `refresh()`, for elements the host replaced.
  - `refresh()` keeps focus on its key: on the mark's new element if the host replaced the focused one (Vega does), even when the old one stays in the page for a while (a D3 exit transition), or, if the mark left, on its nearest neighbour, the next mark or else the previous one. With no marks left, focus leaves the chart. Focus that has moved elsewhere on the page meanwhile is never pulled back. Chrome fires a blur on a focused element the host removes, while it's still in the page, so a blur that leaves focus nowhere counts as the host removing the element only if the element is gone by the end of that task.
  - A ring follows the focused mark's outline in the overlay: 2 px in `--ec-focus`, 2 px out from the mark, as on the bar chart. The overlay is above the marks, so the ring is masked to outside the mark and its gap, as on the [donut](#donut-chart), which shares the code (`src/charts/render/outside.ts`). It never covers data, and it stays distinct from a bar in the focus colour. The gap is left clear rather than painted in `--ec-surface`, since a host's background may be another colour. Around an open outline (a line, or an open shape), the gap starts at the stroke's edge, on both sides. As with `:focus-visible`, it shows unless the last input on the page was a pointer (a click or tap). It stands in for the marks' own focus outline, which is turned off.
  - `focus(key)` moves focus to a mark as a key press would, whatever the last input was: the ring shows and its hover effects play.
- **Names for screen readers.** The adapter writes no ARIA unless asked: the host names its own marks (Vega and Plot have options for it). `markLabel(datum, mark)` names each mark as one item, the way `barChart` names its bars. The element that takes the mark's focus becomes `role="img"`, with the text as its `aria-label`, and loses any `aria-hidden` the host gave it; that's its first part (from the baseline for rects, the first in document order with `geometry`). The mark's other parts get `aria-hidden="true"`, so a stack is read once, not segment by segment. It's given the mark's row (its first part's, as the hover events see it) and a `HostMark`: the `key`, and each part's `series` and `datum`, from the baseline.
  - **Why the adapter does it.** `keyboard: true` makes the host's elements focusable, and a focusable element needs a role and a name (WCAG 4.1.2). Which element of a mark takes focus is the adapter's choice, so it's the one place that can put the name there. A host that names each segment ("Okafor: 4 assists") is read in pieces, and focus, which lands only on the first segment, reads "Okafor: 16 goals" without the assists. Plot can only hide a whole mark, not some of its elements, and Vega-Lite gives each segment its own description, so neither can say "name this one, hide that one". On D3 the page could, but only by mirroring the adapter's baseline order.
  - It's called for every mark on each read (`expressive()` and every `refresh()`), never per frame or on hover, so the names follow the data. It writes through the edits: a part that stops being the first, an element that leaves its mark, and `destroy()` all get back the host's own `role`, `aria-label` and `aria-hidden`. That's the host's latest: a host that reuses its elements and writes its own name again before `refresh()` gets that name back, not the one it had at first, and an empty `markLabel` then leaves it as it is. The other parts keep any names the host gave them, hidden.
  - An empty or blank result, or a throw (reported, as a tooltip function's is), leaves that mark's ARIA as the host drew it, so the adapter never writes an empty name.
  - **The groups around named marks.** An unnamed host element between the `<svg>` and a named mark's parts loses its `role` and `aria-roledescription` when the role is `img`, `graphics-symbol` or `graphics-object`. Vega gives the group around each line `graphics-symbol`, an image with no name, which axe flags (WCAG 1.1.1) and a screen reader may read as one picture; and `graphics-object` takes its name from its contents, so the lines' names would be read again as a group's. Found by the accessibility audit ([a11y-audit.md](a11y-audit.md)). Vega writes them again when it redraws, so they're taken off on every read, and a group with no named mark inside any more gets its role back. A named group, and any other role, stays the host's.
  - The rest stays the host's: the `<svg>`'s role and name, and hiding its own text and axes, which would otherwise be read beside the names. The `<svg>` should be `role="group"` (or have no role), as on `barChart`, not `role="img"`: an image's children are presentational, so screen readers skip the marks inside it. With `keyboard` or `markLabel`, the adapter warns once when the root `<svg>` is `role="img"`.
- **Styling.** The host owns it, so nothing dims unless `dim: true`. The adapter still injects the shared stylesheet, for the theme tokens its overlay and focus ring draw in; its rules only match the library's own classes. Then the attachment's mark elements get `ec-attached`, and while one is hovered the others get `ec-dimmed`, which the shared stylesheet fades with `:where()`, so host CSS still wins. The classes go on the attachment's own marks only, never on the root, so two attachments on one `<svg>` leave each other alone. The paths and icons its effects draw for the dimmed marks fade too, as on our charts: the attachment's overlay gets `ec-hovering`, and the hovered marks' run groups `ec-hot`.
  - **Hover colour.** Under `dim: true` the hovered mark also takes its strong colour, as our charts' marks take their `-strong` colours: each of its elements gets its colour stepped a quarter of the way toward the text colour in OKLab, so the hue stays (`color-mix(in oklab, <colour>, var(--ec-text) 25%)`), as an inline `fill`, or `stroke` on a line. So it's darker in the light theme and lighter in the dark, as our palette's `-strong` colours are, which sit 20% and 29% of the way. The stylesheet's `.ec-attached` rule fades `fill` and `stroke` with the hover feedback, as it does `opacity`. An effect's `emphasis` decides the colour while it's set. Without `dim`, the host's styling stays untouched.
  - **The host's colours.** A mark's colour is its fill, or its stroke when the fill is `none` (or transparent), as on a D3 line: the computed value, as the browser draws it, even black or `none` that the page's CSS sets over the element's attributes. jsdom computes styles but no presentation attributes, so there a computed value that's the property's initial one (black, or `none` for a stroke) gives way to the nearest one declared on the element or above it. Which kind of environment it is, the adapter finds once a root `<svg>`, with a probe: a `<g stroke-miterlimit="7">` put in the root, its computed `stroke-miterlimit` read, and taken out at once, so nothing draws it (from Codex's review on PR #102). A gradient or pattern gives no colour, so emphasis and the hover colour leave it alone.

  Effects restyle marks with inline styles only:
  - `transform` becomes a CSS transform composed with the element's own transform attribute, which is never written;
  - `opacity` is the element's opacity;
  - `emphasis` mixes the host's colour (its fill, or its stroke on a line) toward its strong colour, as on our charts, and the "mark" and "mark-strong" colour tokens are the host's colours;
  - `halo` is drawn in the overlay, masked to outside the mark, so it shows only where it would behind the mark. Around an open outline (a line, or an open shape), the mask cuts out the stroke, as the focus ring's does, and the halo is stroked at the line's thickness plus its own width with round caps, so as much of it shows as round a closed mark, ends included, as behind our charts' lines.
- **Refresh.** `refresh(source?)` re-reads the marks: from `source` if given (and from then on), otherwise from the last source, running a selector again. Like a chart's update, it calls the runner in order: `interrupt()`, then `exit`, `update` and `enter` by key, `change()` for marks that moved, and `settle()`. An `update` is a change in values (see Values above); a mark that only moved (its outline, its segments, or its thickness alone, as when a line's stroke width changes), or got a new row or new samples, follows through `change()`. When a mark of a series some effect `needs` changes, moves, comes or goes, every other live mark follows through `change()` too, since its effects may read that series through `related`. A new root `<svg>` (Plot draws one each time) takes the overlay and the listeners. Marks it can't read, bad samples and missing series throw before anything changes.
- **Swapping effects.** `update({ on })` swaps the effects of the slots a new `on` changes, as a [chart's](#reference-charts) does, through the [runner's](#runner) `swap()`. So a page with an effect picker needn't attach again, which would lose the tab stop and play the enter effects again.
  - The new `on` is resolved as when the attachment is made, so an unknown preset name or slot rejects before anything changes, and so does a data effect whose `needs` name a series the marks don't have. Any option but `on` rejects too, since nothing else can change yet.
  - A slot given the same effect, or the same preset name, keeps its effect and its runs. A slot left out is emptied.
  - A changed slot's runs are cleared and the new effect starts where they were: `decorate` again on every live mark, and a held hover (the pointer's, the keyboard's or a link's) replays with the new hover effect at once, since an attachment has no change to settle. `enter`, `update` and `exit` draw the new effect's end state where their runs were, so nothing enters again, and a leaving mark's exit ends there.
  - Focus, its ring and the tab stop stay, and nothing fires. The series the new data effects read (`needs`) are found again, so from then on a change to a mark of one of them makes every other mark follow, as in `refresh()` and `watch`.
  - It returns a promise, as a chart's does, which resolves once the swap is done: at once. After `destroy()` it resolves, changing nothing.
- **Leaving.** `leave()` ends the hover, the pointer's or the keyboard's, as the viewer moving away would and as a chart's `leave()` does: the emphasis, the dimming and the hover runs end, with their `leave` events, and focus stays where it is, with its ring, as after Escape. The pointer hovers again when it next moves onto a mark, the same one too. A [link's](#linked-hover) hover shown on the attachment ends there, and the link's other sources keep theirs; the attachment's own hover ending tells its link, as the pointer leaving does. With nothing hovered, or once destroyed, it does nothing. It's the `leave()` the attachment's link port already had.
- **Watch.** `watch: true` follows the host's own transitions frame by frame without `refresh()`, which would fire `update` and cut a hover short. It's opt-in because of its cost, below.
  - **What it hears.** A `MutationObserver` (`src/charts/adapter/watch.ts`) notes changes to the marks' geometry attributes (`d`, `x`, `y`, `width`, `height`, `cx`, `cy`, `r`, `rx`, `ry`, `x1`, `y1`, `x2`, `y2`, `points`, `transform`), and to `transform` and `style` on every ancestor from the marks up to the root `<svg>`: a host that animates a parent `<g transform>` changes none of the marks' own attributes. The marks' own `style` isn't watched, since the adapter writes it.
  - **Once a frame,** on the chart's clock, the marks whose attributes changed are read again: their rows, geometry and samples. An ancestor that changed below the marks' common ancestor has every mark inside it read again. One at or above it moves the overlay, whose transform is computed again, and nothing is read: the marks' geometry is in that ancestor's coordinates, so it can't have changed. With `baseline: "auto"`, the edge every bar shares is found again from all the bars' boxes, as a full read would, so a bar that ends a transition on the other side of the line grows from it the other way; in a frame where no edge is shared (a bar crossing the line), each keeps the one it had. The marks are put back in visual order (a sort's last frame reorders the keyboard), and the runner hears `change()` for each, with no events and no interrupt, as on our charts' frames. When a mark of a series some effect `needs` moves, every other live mark follows too, as in `refresh()`. As on any read, an element's screen CTM is read once a frame, so bars that share a parent cost one read between them.
  - **Timing.** The first change wakes the clock, and it stays on until a frame with no changes, taking the observer's pending records when its frame comes. So a host that draws in its own frame callback (a D3 timer), and asks for its next frame there, is followed in the frame it draws, from its second frame on; so is a page that draws from the clock (a reveal in `playback()`'s `onFrame`), in the same tick. If the clock is already running an animation whose callback comes before the host's each frame, the effects trail the marks by one frame.
  - **What stays.** Values (`value`), colours, a shape's stroke width (in its own units, which a new transform still scales, or in screen px for a non-scaling stroke, which it doesn't: a frame that moves the common ancestor reads those marks again, and they follow if the ancestor's screen scale changed their width), names (`markLabel`) and the elements themselves stay as the last `refresh()` read them. A bar of one rect that turns in a frame is read as a shape from then on, as a full read would read it, and a turned rect stays a shape through frames that bring it upright, until `refresh()` reads it as a bar. A shape that draws nothing in a frame stays as it was, until `refresh()` takes it out. So call `refresh()` when the host joins new data, before its transition starts: it fires `enter`, `update` and `exit`, an update comparing values with the previous `refresh()` and starting `from` the mark as it is before the transition. `watch` then follows the frames the transition draws. Elements the host adds, removes or replaces need `refresh()` too; it watches what it reads.
  - **The page's `geometry`** should read the element, or a row the host updates each frame, as a reveal does (each path's rows so far, with `selection.datum()`). One that reads a transition's target row sees only the end. Rects, circles and shapes are read from the element, so a D3 transition on bars, dots or a curve needs nothing more.
  - A mark it can't read in a frame (a rect a transition turns) is reported, and nothing changes. `destroy()` disconnects the observer and cancels a frame that's waiting.
  - **Cost,** measured in headless Chromium on a desktop CPU as main-thread time a frame, against the same frames without `watch` (open question 13 in the [development log](plan.md) has the table and the method). Following a D3-style transition on 20 bars adds 0.56 ms a frame, on 200 bars 2.7 ms (about 13 µs a moving bar), and a page's reveal of a two-line season with `threshold` and a riding ball 0.5 ms; that includes the effects' redraw, and is a little less than a `refresh()` every frame. With a 4× CPU slowdown it's about five times as much, and 200 moving bars miss a quarter of their frames. It keeps step with the host on every frame but a transition's first. Nothing moving costs nothing, since the observer wakes the clock only when a watched attribute changes. So it stays opt-in. The stress page measured it again on more columns: from 500 up it adds 17–19 µs a moving column a frame (about 95 µs at 4×), and it halves the largest number of columns that stay smooth, from 1,000 to 500 (from 100 to 20 at 4×; [Limits](#limits)).
- **Destroy.** `destroy()` clears every run, removes the overlay and the listeners, and puts back every attribute, style property and class the adapter changed. When nothing else has changed them, attributes get their exact text back, so the host's markup reads as it did before. An attribute the host wrote again since the adapter last did keeps the host's value.
- **Data effects** get the mark's row (its first part's) and its samples, and find other series through `related(series)`.
  - **`samples(datum, mark)`** gives a mark's samples, `{ t, value, at? }`. It's called on every read for each mark, with its row and geometry, and for each of its named segments, with that part's row and the segment's geometry. The samples are checked when read: `t` in [0, 1] and never decreasing (equal `t` is a step), finite values, and `gapBefore`, if it's there, `true` or `false`; `gapBefore: true` is kept. Anything else throws a `RangeError` (or a `TypeError` for something that isn't an array) naming the mark, before anything changes. The adapter keeps a copy.
  - **`samplesAlong(mark, points)`** (public, `src/core/geometry/samples.ts`) gives a line its samples from the points that drew it: each `{ x, y, value, at? }`, in the marks' coordinates, is projected onto the nearest point of the walk, and the samples come back in `t` order (points at one `t` keep their order). It reads only the `MarkGeometry` contract: a grid of a point every px (up to 4096) finds each point's nearest stretch, and a golden-section search narrows it down, exactly for a point on the walk (a vertex lands where it is, and the ends on 0 and 1) and to well under 1e-6 px off it. On a polyline whose points sit at its vertices, values are then linear in `t` between samples, so `threshold`'s crossings are exact; on a curve they're approximate. On a mark with [gaps](#gaps), the first sample past each gap's middle gets `gapBefore`.
  - **Without `samples`,** rect marks with a numeric `value` for every part get the bar chart's samples: from 0 at the baseline to the parts' total at the tip, in proportion to distance, and each segment over its own span of it. A circle with a numeric `value` gets it as its one sample, `{ t: 0, value }`, as a Vega symbol does. Other marks get none: a page gives a curve's with `samples` and `samplesAlong()`.
  - **`related(series)`** is the mark's own segment of that series (a stack's part: its row, and samples over the segment), or else the first other live mark, in visual order, whose geometry has that `series`, such as two D3 line paths described with `describe.line({ key, series, … })`. That mark is looked up when an effect calls it, so it's as last read, by `refresh()` or `watch`. A mark isn't its own related series. Among grouped bars (each rect a mark of its own), that first mark needn't be the same row's.
  - **`needs.related`** is checked against the marks' series (each mark's `series`, its segments' and its parts') on creation and on every `refresh()`, and a missing one throws a `RangeError` before anything changes. With no marks yet, there's nothing to check.
  - With `watch`, a mark's samples are read again on every frame it moves.

What each library needs (from the [adapter spike](ideas/adapter-spike.md)):

- **D3** works as is: `__data__` holds the row, and a stack's series key is on the parent `<g>`. A stack point's value is `d[1] - d[0]`. A pie's or a donut's slices are read by tag (M11 step 4), each `d3.arc()` path a slice, clockwise from 12 o'clock, as above; a slice's value is `d.value`. `geometry` with `describe.arc`, from the datum's angles and the arc generator's radii, gives the same marks within 0.5 px, and reads a padded donut as slices too. A scatter's circles, a line's path, any curve, an area and `d3.symbol()` paths are read by tag, with only a key: a path from its own `d`, so a curve keeps its curve and a line drawn with `.defined()` its gaps, one at each move. A line's `samples` come from `samplesAlong` on the points that drew it, and `segment` names its `series`. A straight line can still be described with `geometry` and `describe.line`, from its points, with `breaks` at the ones after a missing value. The tests run on real D3 (`d3-shape` and `d3-selection`, pinned dev dependencies, never runtime ones): `src/d3-pie.test.ts` (with `geometry`, and read by tag: pies, donuts, a whole ring, pies turned, scaled and flipped, through a browser's rounded CTMs, padded and rounded ones as shapes, the donut page's pie, and a transition followed with `watch`), `src/d3-line.test.ts` (`threshold` against xG, a ball riding the goals line, keyboard order, and a reveal the page draws frame by frame, followed with `watch`) and `src/shapes.test.ts` (a scatter's dots named, dimmed and reached by the arrows, symbols, a curve with gaps coloured by `threshold` through a transition followed with `watch`, and an area), and a D3 pie source, two D3 line sources, one with missing weeks, and the scatter, the curves, the area, the donut and a pie read by tag, in the effect conformance checks.
- **Observable Plot** binds indices, not rows, so the page passes a `datum` accessor. Plot draws a new `<svg>` each time, so pass the marks, not the `<svg>`: `refresh(newSvg.querySelectorAll('g[aria-label="bar"] > rect'))`. Which accessor depends on the mark:
  - one element per row, with no transform that derives new data (bars, dots): `datum: (el) => rows[el.__data__]`, and then `value` reads that row, `value: (d) => d.goals`. A dot is a `<circle>`, read by tag as a point, in the dot group's coordinates. A stack's segments all sit in one `<g>`, so `segment` reads the row too (`(d) => d.metric`);
  - a line path: `el.__data__` is that series' array of row indices, with `-1` at gaps, so `el.__data__.filter((i) => i >= 0).map((i) => rows[i])`. Read by tag, it's a shape from its own `d`, its gaps included; or it's described with `geometry` from those rows' points, through Plot's own scales (`svg.scale("x").apply(r.week)`). Either way, its `samples` come from `samplesAlong` on those points. The points are in the line group's coordinates: the `translate(0.5,0.5)` Plot puts on that group for crisp edges (at a device pixel ratio of 1) stays out of them, and the overlay takes it. Where Plot breaks a line at a missing value, the page gives `describe.line` the `breaks`: the indices of the rows after each `-1`;
  - after a group, bin or other reducing transform: the index points into the derived data, so `rows[i]` is silently the wrong row. Read the channel values through the mark's `render` option instead: it gets the index and the derived data's channels (`values.channels.y.value[i]`), unscaled.

  Plot has no pie mark. These accessors and the caveat came from the spike; the tests now run them on real Plot 0.6.17 (`@observablehq/plot`, a pinned dev dependency, never a runtime one), rendered in jsdom through Plot's `document` option. `src/plot.test.ts` has a stacked bar (rows, segments and samples, keyboard order and names, the warning when no `datum` is given, a `groupY` total read through `render`, and a new `<svg>` followed through `refresh()`) and a two-series line (rows, geometry and samples, the group's offset, `threshold` against xG, keyboard order, and a gap). A Plot bar source and a Plot line source are in the effect conformance checks.
- **Vega and Vega-Lite** go through `fromVegaView()`, below. They need the SVG renderer (vega-embed's default; a bare `vega.View` uses canvas). Their bars are `<path>` elements and `__data__` is a scenegraph item, new on every render, so plain `expressive()` would need `datum` (the row is `el.__data__.datum`) and `geometry` written for Vega; the helper writes them.

Adapters follow the chart rules:

- They never know specific effects.
- They express geometry in the marks' nearest common ancestor's coordinates, and draw their overlay on the root `<svg>` with that ancestor's transform.
- They leave the host's styling, axes and tooltips alone, and undo everything they change.

### Vega and Vega-Lite: fromVegaView()

```ts
const { view } = await vegaEmbed("#season", spec);  // Vega-Lite: one row per week and series
const fx = fromVegaView(view, {
  key: (d) => d.series,                             // required, as for expressive()
  sample: (d) => ({ value: d.value, at: d.week }),  // each point's value, and its week for threshold
  keyboard: true,
  markLabel: (d) => (d.series === "goals" ? "Goals scored" : "Expected goals"),
  on: { decorate: only("goals", parallel(threshold({ compareTo: "xg" }), travel("soccer-ball", { ride: "on" }))) }
});
```

`fromVegaView(view, options)` (`src/charts/adapter/vega.ts`) reads the marks of a Vega or Vega-Lite chart from the View's scenegraph and attaches to the elements Vega drew for them, through `expressive()`, so effects, keyboard focus, names, dimming, `update({ on })` and `leave()` work as they do there. It's duck-typed on the View (`renderer()`, `scenegraph()` and `container()`), so the library imports nothing from Vega; vega and vega-lite are dev dependencies, pinned to exact versions, for the tests and the demo.

- **Which marks.** `mark` names the Vega mark to read, `"marks"` by default, the name Vega-Lite gives a chart's data mark. Every mark of that name counts, wherever it is in the scenegraph: Vega-Lite draws a line per series inside a facet group. Each item's element is the one whose `__data__` is the item (a line's one path is bound to its first item), and its row is `item.datum`. Vega-Lite derives its own rows, so `key` reads fields, never identity.
- **Geometry** comes from the items' numbers, mapped from each element's parent's coordinates into the marks' common ancestor's, as `expressive()` expects of `geometry`. Rects are bars, growing from the edge `baseline: "auto"` finds; parts that share a key and are named by `segment` are a stack's segments, ordered from the baseline whatever order Vega-Lite stacks in. Arcs are slices, with their angles put in order (Vega-Lite's can run anticlockwise). Symbols are points of radius √(size/π). Lines are lines at the item's `strokeWidth`, each its own series (its key), so `related("xg")` finds the line keyed `"xg"`: straight between the items' points, or the path Vega drew for a curve (below). Other mark types throw a `TypeError`.
- **Curves** (M10). A line Vega draws with any `interpolate` but `"linear"` (`"monotone"`, `"basis"`, `"step"`, `"natural"` and the rest; Vega reads the first item's) is the path Vega drew: its element's `d`, read with [`describe.shape`](#shapes), moved by the element's matrix into the marks' coordinates as the items' numbers are, at the item's stroke width (one of 0 reads as 1 px, as `expressive()` reads a shape by its tag). So its gaps come with it, one at each move, as on a D3 curve read by tag, and a curve Vega closes on itself (`"linear-closed"`, `"basis-closed"` and the other `-closed` ones) is a closed shape, with no walk.
  - **Samples** are at the items drawn, projected onto the curve with `samplesAlong`: at each item's point on a curve through them (`"monotone"`, `"natural"`, `"step"`), at the nearest point of one that misses them (`"basis"`), and all at the start of a closed one.
  - **So [`threshold`](#threshold)'s crossings** between items are approximate on a curve, as on a D3 curve: values are linear in `t` between samples, and a curve's distance isn't linear in x. On the tests' season drawn `"monotone"`, at 60 px a week, the colour changes up to 8 px from where the drawn lines cross.
  - **A straight line** (`"linear"`, or no `interpolate`) is read from its items through `describe.line`, as before, the same mark byte for byte.
- **Gaps** (M9). A line's items that Vega leaves out (`defined: false`) are left out here too, and the next item Vega draws starts a new run: a straight line is described with `breaks`, and a curve has a move there, so it has [gaps](#gaps), and its samples have `gapBefore` after each one, so no effect draws inside a gap. Items left out before the first one drawn or after the last only shorten the line, and a line with none drawn has no mark, as Vega draws nothing.
  - Vega-Lite 6 breaks a line at a missing value (`null`, or `NaN` on a continuous scale) by default: its default `invalid` mode, `"break-paths-show-path-domains"`, gives the line a `defined` encoding, as `"break-paths-show-domains"` and `"break-paths-filter-domains"` do.
  - `"filter"` leaves the missing rows out, so the line is joined straight across them, as Vega draws it.
  - `"show"`, or `null`, draws them at zero or the scale's minimum, so they're points like any other, and the page's `sample` gives their value there: one that gives `null` throws, as for any value that isn't a finite number.
- **Data.** The items say where each point is but not which field it shows, so data effects' values come from `sample(row)`: a number, or `{ value, at }`. A line gets a sample at each point (through `samplesAlong`, exact at a straight line's vertices; a curve's are as Curves says), a bar from 0 at its baseline to its value (a stack's segments each over their own range), a slice from 0 to its value, and a point its value. Unless `value` is given, `sample` is also what each element shows (a line: all its points', a point Vega leaves out as empty, so a value that goes missing or comes back is an update), so a re-render that only moves marks, such as a resize, isn't an update. `samples` replaces it.
- **Following the View.** Vega replaces its mark elements when its data changes, and redraws them on a resize or a signal. Its data and resize listeners, and `runAfter`, run before it renders, so they'd read the old elements; instead a `MutationObserver` on the View's `<svg>` notes what Vega draws (new elements, and `d`, `transform`, `x`, `y`, `width`, `height`, and `stroke-width`, which a line's thickness is read from), ignoring the adapter's own overlay, and the View is read again on the next frame through `refresh()`, as a page would call it. A View that hasn't run yet attaches with no marks and takes them up once Vega draws. The attachment's own `refresh()` reads the View again at once, and `destroy()` stops following.
- **Errors.** A renderer other than SVG, a `mark` that isn't there (the error lists the names there are) and an unreadable mark type throw when attaching. A later read that fails is reported, changing nothing.
- **Frame by frame.** Every data change gives new elements, so a page that played a Vega chart frame by frame would have the adapter re-read it each frame (about 1.8 ms on the demo's line, beside Vega's own 0.7 ms), fire an `update` for every mark each frame, replace a focused mark's element each frame, and run a frame behind. The demo's Vega-Lite line shows the whole season instead.

The tests (`src/vega.test.ts`) run on real Vega-Lite charts rendered as SVG in jsdom: a two-series line (geometry, samples, `threshold` against xG, the riding ball, keyboard order, following new data and a resize, attaching before the first run, `destroy()`); the line with missing weeks in each of Vega-Lite's `invalid` modes (its gaps and samples, `threshold` and the riding ball drawing nothing inside a gap frame by frame, weeks missing at its ends and all through, and renders that open and close gaps); the line drawn as a curve (`"monotone"`, `"basis"`, `"step"` and `"natural"`, each the mark `describe.shape` gives its `d`; closed on itself; with missing weeks in each breaking mode, its gaps at each move; moved by its group; its samples at the items; `threshold` and the riding ball, drawing nothing inside a gap frame by frame; a signal that changes the curve, followed; `update({ on })`; and a straight line, the same mark as before); `update({ on })` and `leave()`; bars, a stack, a donut and points; the errors; and `checkEffect` for every built-in effect on the View's lines, with and without gaps, with their moved twins. The View's monotone curves, with and without missing weeks, are in the effect conformance checks too.

## Linked hover

```ts
const goals = barChart("#goals", { label: "Goals per matchweek", data: weeks, x: (d) => String(d.week), y: "goals", orientation: "vertical" });
const xg = lineChart("#xg", { label: "Goals vs xG", data: weeks, x: "week", series: ["goals", "xg"] });
const shots = expressive(d3.selectAll("#shots rect"), { key: (d) => d.week, dim: true });
link([goals, xg, shots]);                           // by matchweek
link([players, teams], { by: (event) => event.data.datum.team, effects: false }); // a team's slice and its players' bars
```

`link(sources, { by, effects })` (`src/charts/link.ts`) links hover across charts, chart switches and attachments (M7 step 4, and M9 step 2 for switches). When one source is hovered by the pointer, touch or the keyboard, every other one hovers its targets with that linking value, and leaves them when it leaves. It isn't an effect: effects only touch their own mark, and a link hovers other marks, so it lives with the charts, as hover dimming does.

- **The linking value.** By default, a mark's last sample's `at` if it has one, else its key. A line point's `at` is its x, and bars and slices have no `at`, so a column keyed by its matchweek links with the line's point there. Values are compared as strings, a `Date` by its ISO string, as keys are. Keys alone wouldn't do: they're identities and differ across marks on purpose (`goals@12` and `12`). `by(event)` gives the value instead, from the mark and its data, typed by the sources' rows (a union when they differ). Each hovered mark gives one, and a target matches when one of its marks has one of them: a line chart's x, through its points; a bar, a slice or an attachment's mark, through itself. Every target that matches is hovered, in one batch, so a team's slice can hover its players' bars.
- **A linked hover** is the chart's own: its targets' emphasis (`ec-hot`, or the hovered colour on an attachment with `dim`), the dimming of its other marks (none on a line chart, whose link hovers dim nothing), and its hover effect, held mid-change and replayed when the change settles, as for any hover. The `hover` events have `source: "linked"`, and `effects: false` keeps it to the emphasis and dimming. It has no tooltip, focus ring or focus, a line chart draws no crosshair, and nothing is announced: linked hover is visual only, so a page that relies on it says the same in its table. Effects can't tell a linked hover from any other, so the effect contract doesn't change.
- **One hover a link.** The newest hover anywhere in the link is the one shown: when a source is hovered, every other one ends what it showed, its own hover or a linked one, before hovering its matches. A source with no match hovers nothing. Escape and `leave()` on the hovered source end it, and every linked hover with it. Escape with focus on a source that shows a linked hover ends the link's hover where it started, so the tooltip there goes too (WCAG 1.4.13). `leave()` on a linked source ends only its own.
- **A [chart switch](#switching-between-charts)** takes part through its view on show. Hovering that view hovers the others, and their hovers hover it, as a chart's do; the hidden view is never hovered, and its hovers aren't linked.
  - **While a switch plays,** neither view can be reached, so the switch neither starts a link's hover nor shows one. A hover in the view it leaves ends as it starts, a link's too, and the link hears the viewer's hover end, so every linked hover ends with it.
  - **When it lands,** the link's hover from another source, if there is one, shows in the new view, from the hovered marks' linking values: the one there was as the switch started, or a newer one that came while it played. Focus carried into the new view hovers its mark first, and that's the newer hover. A switch back or to a third view shows it where it lands, and with motion off it shows at once.
  - **`leave()` on the switch** ends a link's hover in it, mid-switch too, so it shows again with the link's next hover, not when a switch lands.
- **Its limits.** A source can be in one link at a time: a second throws a `TypeError`, as does the same source twice or anything that isn't a chart, a chart switch or an attachment, before anything is linked. A chart switch's views' charts go with it: a switch whose view's chart is in a link throws, and so does a view's chart whose switch is in one, or the two in one link. A destroyed source drops out, ending the link's hover if it was the one hovered, and a destroyed switch frees its views' charts. `link()` returns `{ destroy() }`, which ends the linked hovers and frees the sources.
- **Inside.** Each chart and attachment registers its hover with the link module when it's made, in a `WeakMap` keyed by its handle, so `link()` can hover given targets without focus; `fromVegaView()`'s handle shares its attachment's. The charts' shared hover (`src/charts/shell/hover.ts`) and `expressive()`'s own each give a port: their live targets with their marks, hovering given targets as linked, ending a linked hover, and the source's own `leave()`. They tell their link when their own hover starts and ends, when Escape ends a linked one, and when they're destroyed.
  - A chart switch registers a port made of its views' charts' ports, which are its parts and go into a link with it. While it rests, its targets and hovers are the view on show's, and it passes on that view's own hovers; mid-switch it has no targets, and remembers whether the link has a hover for it. When it lands, it tells its link, which hovers the new view's targets with the linking values it kept.
  - Nothing new is public on the handles but the switch's `on()`, `marks()` and `leave()`.

The tests (`src/charts/link.test.ts`) link columns and a line by matchweek both ways, a donut, D3 columns through `expressive()` and Vega bars through `fromVegaView()`, with real D3 and Vega: the keyboard, Escape and `leave()`, the newest hover winning, a hover listener that ends or replaces the hover, `by` (several targets, a time axis, a throw, the rows' type) and `effects: false`, a source mid-update, an attachment's refresh, a destroyed source, a second link throwing, and no tooltip, ring, focus or announcement on a linked chart. A chart switch's (M9 step 2) link its view on show with bars and with D3 columns through `expressive()`, both ways, by the pointer and the keyboard, before and after a switch; a switch started while its view is hovered and while it shows a link's hover; a link's hover that comes mid-switch, and one that ends mid-switch; a switch back; motion off; focus carried into the new view; `effects: false`; `leave()` mid-switch; the hidden view; a switch and its views' charts in two links; the switch destroyed, at rest and mid-switch; and `by`'s rows read from the views' charts. `src/charts/switch.test.ts` checks `marks()`, `on()` and `leave()` on the view on show.

## Controls

On-page controls the viewer operates are in `src/charts/controls/`. Like the charts, they import only core, and the composition root hands them the page-wide motion by default. The `playback()` controller that the play button drives has no DOM, so it's in core (`src/core/playback.ts`).

### Motion switch

```ts
motionSwitch(target, motion?, { label?, labels?, hints?, persist? }) // → { element, destroy() }
```

`motionSwitch` builds the prototype's segmented control in `target` (an element or a selector): Presentation, Analysis and Off. It's the library's one caller of `motion.chooseMode()`, because the viewer operates it, so a click overrides the device's reduced-motion setting.

- **Structure.** A `role="group"` named by its visible label ("Motion"), with real `<button type="button">`s that carry `aria-pressed`, so Tab, Enter and Space work as they do on any button. A note beside them says what the mode does; it's the group's description and a polite live region, so a screen reader hears the new note after a click.
- **What it shows.** The pressed button is the effective mode. While the device asks for reduced motion and the viewer hasn't picked, Off is pressed and the note says so ("Your device asks for reduced motion…"); picking any mode, Off included, makes it the viewer's choice. It follows `motion.subscribe`, so it stays right when the author, the device or another control changes the mode.
- **Persisting.** `persist: "key"` is opt-in: the viewer's choice is saved in `localStorage` under the key and restored when the switch is made, so it carries across pages and visits; `clearChoice()` removes it. A stored value that isn't a mode is ignored, and storage that's blocked or full is skipped (every access is guarded).
- `label`, `labels` and `hints` replace the text, for other languages. `destroy()` removes the switch and stops following the motion; the viewer's choice stays.
- **Styles.** Its rules are in the shared stylesheet, so `expressive-charts/style.css` and `configure()` cover them as they do the charts'. They use `:where()` and theme tokens (`--ec-text`, `--ec-text-muted`, `--ec-surface`, `--ec-ring`, `--ec-focus`), so they follow light and dark, and host CSS restyles them without specificity fights.

### Playback

```ts
playback({ from, to, duration, ease?, timing?, motion?, clock?, onFrame })
// → { play(), pause(), seek(x, { animate? }?), position, playing, subscribe(listener), destroy() }
playButton(target, playback, { labels? }) // → { element, destroy() }
```

`playback()` plays a value through a range, such as a season revealed week by week, and `onFrame` draws each position. It's a controller on the clock with no DOM, so it runs in Node and, in tests, on a manual clock. It follows the page-wide motion and clock unless it's given its own (`motion`, `clock`, as on [animated values](#animated-values)). Nothing plays by itself: there's no autoplay option.

- **Where it starts.** At rest at `to`, the way a chart shows all its data until something reveals less. `onFrame` isn't called until the position changes.
- **`play()`** goes on from where it is to `to`, or starts again from `from` when it's at the end. The whole range takes `duration` scaled by `timing` (default `"playback"`: base in Presentation, × 0.3 in Analysis). A play from part way takes its share of that scaled time, so the speed is the same wherever it starts and whatever the timing's rule: the line demo's season takes 6.5 s from week 1, or 1.95 s in Analysis. It moves at constant speed (`ease` defaults to `linear`). With motion off it jumps to `to`. If motion turns off mid-play, it jumps there on the next frame, as tweens do; other mode changes keep the speed it started with. `play()` while playing does nothing.
- **`pause()`** stops a play where it is, and the next `play()` carries on from there. Pause is the control WCAG 2.2.2 asks for, so there's no `stop()`: `seek(to)` shows the end. `pause()` doesn't stop a seek on its way, so a scrubber's handler can call both.
- **`seek(x)`** pauses and moves to `x`, clamped to the range, over 350 ms base `"transition"` timing (122.5 ms in Analysis, a jump in Off), as the prototype's scrubber does. From rest it eases in and out. A seek while the position is moving (playing, or on its way to another seek) starts from where it is and eases out, as animated values do. `{ animate: false }` jumps.
- **`subscribe(listener)`** hears `"play"`, `"pause"`, `"end"` and `"seek"`, not frames, which go to `onFrame`. A seek during a play is heard as `"pause"` and then `"seek"`, and a play with motion off as `"play"` and then `"end"`. A listener can call the playback; whatever it starts wins. A listener that throws is reported, and the rest still hear.
- **Errors.** If `onFrame` or `ease` throws, the position stops where it is (a play is heard as paused) and the error is reported once: by the clock, or thrown to whoever caused a jump. The options are checked when it's made: `from` and `to` finite and different (`from` above `to` plays backwards), `duration` a non-negative number of ms, `timing` one of the five, and `onFrame` a function.
- `destroy()` pauses it, telling its listeners, and then every call does nothing.

`playButton(target, playback, { labels })` is the pause control a playback needs: a real `<button type="button">` in `target` (an element or a selector) whose text is Play or Pause, for what a click does. It has no `aria-pressed`, since a toggle button's name stays the same and this one's changes. `labels` gives the page's words (`{ play: "Play season" }`), which must have some text besides spaces; the defaults are "Play" and "Pause". It follows `playback.subscribe`, so it goes back to Play at the end, on a seek, or when the page pauses, and it's the same element throughout, so focus stays on it. Its `.ec-play` rules are in the shared stylesheet, which it injects as `motionSwitch` does. `destroy()` removes it and stops following the playback, which carries on.

The page wires its own `<input type="range">` to `seek()`, and its status to `onFrame`:

```js
const season = playback({
  from: 1, to: 38, duration: 6500,                           // 6.5 s in Presentation, 1.95 s in Analysis, at once in Off
  onFrame(week) {
    chart.reveal(week);                                      // lineChart: a view, with no events
    status.textContent = `Through matchweek ${Math.round(week)}`;
    if (season.playing) range.value = String(Math.round(week)); // a seek leaves the slider where the viewer put it
  }
});
playButton("#play", season, { labels: { play: "Play season" } });
range.addEventListener("input", () => season.seek(Number(range.value)));
```

## Rendering

SVG first, in `src/charts/render/`. Canvas or WebGL rendering is a later option for charts past the [limits](#limits) below; effects describe what to draw, so they should not need to change when a renderer is added.

- **Structure.** A chart's `<svg class="ec-chart" role="group">` holds the grid, the axis, the focus ring, the marks and the overlay where runs draw, last on the bar chart and the donut, and between the lines and the points on a line chart (one `<g class="ec-run">` per run, stacked by start order, with `--ec-mark` set to the mark's colour, and set again when that colour changes; its paths and icons in a `<g class="ec-follow">`, its text beside it). Each mark is a `<g class="ec-mark" role="img" data-key>`, which takes focus and carries the `aria-label`, with its pointer target, label, body (the segments, which effects restyle) and value label. The donut's `<svg>` holds the centre text (`.ec-center`, `aria-hidden`), the marks and the overlay, where halos (`.ec-halos`) and the focus ring come before the runs (`.ec-runs`); each slice's mark holds its pointer target, its body (the `.ec-slice` path) and its label's two lines. The line chart's `<svg>` holds the grid, the axis, the crosshair (`.ec-crosshair`), the focus rings, the lines (`.ec-marks`, `aria-hidden`, holding `.ec-lines`: each line's `<g class="ec-line">` with its body, the `.ec-stroke` path and the `.ec-end` dot, and its end label), the overlay, the points (a second `.ec-marks`, `aria-hidden`, holding `.ec-points`: each point's `<g class="ec-point">` with its `.ec-dot`), the x's (`.ec-columns`: each a `<g class="ec-column" role="img">` holding its hit column, which takes focus), and with `hover: "point"` the points' stops (`.ec-stops`: the plot's hit area, then each `<g class="ec-stop" role="img">`, while the x's are hidden). So its runs draw between its lines and its points (M13 decision 5). Lines and points aren't `.ec-mark`s: lines are never hover targets, and only with `hover: "point"` do they dim. DOM order follows visual order. Beside the `<svg>`, in the container, are HTML elements: the legend (`.ec-legend`) before it; after it, the tooltip's layer (`.ec-tooltip-layer`, with the box and its bridge), the data table (`.ec-table`) and, with `announce`, the live region (`.ec-announcer`). `.ec-visually-hidden` hides an element from sight but not from screen readers.
- **Hover styles.** A hovered mark has `ec-hot` and, with `dim`, the `<svg>` has `ec-hovering`, which fades the parts in every other `.ec-mark`'s body (`.ec-body > *`: its segments or slice, and a halo) to `--ec-dim-opacity`. Its labels don't fade, so they keep 4.5:1 or more, which `a11y.spec.ts` checks in the browser. Nor does the body itself: an effect's `opacity` is an attribute there, which a stylesheet rule would override, and on the parts the two multiply. Each part fades on its own, so a halo behind a dimmed bar shows faintly through it. In the overlay, every other mark's `.ec-follow` groups fade the same way (the run groups without `ec-hot`, which the surface gives a mark's runs with the mark), each as one, so an icon's parts fade together; text there doesn't fade. That's opacity, so it fades strokes as it does fills. A segment (`.ec-segment`) or slice (`.ec-slice`) is filled with `--ec-mark`, and `--ec-mark-strong` inside an `ec-hot` mark. A stroked part (`.ec-stroke`, for an open outline such as a line) is `fill: none` and stroked the same way, with round joins. Its width is left to the chart's `stroke-width` attribute, which is the geometry's `thickness`, because a stylesheet rule would override it. Effects' `emphasis` mixes the same two colours inline (`svgMarkHandle` in `render/mark-style.ts`): the fill, or an open part's stroke. A line chart's point (`.ec-dot`) is transparent until it's `ec-hot`, then shows in `--ec-mark-strong`, fading over the hover duration; a line's end dot (`.ec-end`) always shows, and both are ringed in `--ec-surface`. With `hover: "point"` and `dim`, `ec-hovering` fades the parts of every `.ec-line` without `ec-hot-line` and every `.ec-alone` point without `ec-hot`, as for `.ec-mark`s; a point that isn't shown stays hidden. The crosshair is dashed in `--ec-axis`.
- **Morphing.** While a chart's `<svg>` has the class `ec-morphing`, its marks layers (`.ec-marks`: a line chart has two, its lines' and its points') are `visibility: hidden`: bars and slices with their labels, lines with their end dots and labels, and points, leaving ones too. A [chart switch](#switching-between-charts) puts it on both views while their marks morph in an overlay of its own. Nothing else is hidden: the axes, the gridlines, the donut's centre text, the line chart's x's (its focus stops), the focus ring, the overlay where runs draw, the legend and the table stay. It has to be on the `<svg>` itself, not an ancestor. A hidden mark can't take the pointer, and a browser may move focus off it, so whatever moves focus across a switch reads the focused key first. A switch also puts `ec-switching` on each view's container, which hides that view's focus ring, overlay and x's (`.ec-focus`, `.ec-overlay`, `.ec-columns`); its other rules (`.ec-switch`, `.ec-switch-view`, `.ec-switch-inactive`, `.ec-switch-overlay`) lay out the views and hide the inactive one.
- **Theme.** Colours are `--ec-*` custom properties: `--ec-text`, `--ec-text-muted`, `--ec-surface`, `--ec-grid`, `--ec-axis`, `--ec-focus`, `--ec-negative`, `--ec-ring` (hairline borders on controls and the tooltip), `--ec-series-1` … `--ec-series-8` with `-strong` variants, `--ec-dim-opacity`, and `--ec-hover-duration`, which the chart sets. Text uses the text tokens, never a series colour.
  - **Light and dark.** The defaults are in `themes` in `src/charts/render/theme.ts`. The stylesheet sets light on `:root`; dark when the device prefers it, unless the root has `data-theme="light"`; and either one on any element with `data-theme="light"` or `"dark"`, for its subtree. They're on the root rather than the chart so that elements outside the `<svg>` (a host's own chart, the tooltip, controls) read the same values.
  - **Overriding.** Every default rule is in `:where()`, so any host rule wins: `.my-card { --ec-series-1: teal }`. A `data-theme` element sets every token again for its subtree, so an override meant to hold everywhere should also name `[data-theme]` elements, or sit inside them. A page with no dark theme of its own sets `data-theme="light"` on `<html>`, so the charts don't turn dark on a light page.
  - **The palette** is validated by `theme.test.ts` in both themes: every mark colour (and `--ec-negative` and `--ec-focus`) is at least 3:1 against the surface; neighbouring slots, with slot 8 next to slot 1, are at least 15 apart in OKLab ×100, and at least 8 apart under protanopia, deuteranopia and tritanopia (Machado 2009); any two slots are at least 9 apart; each `-strong` is within 5° of its colour's hue, with 1.3× its contrast; and text is at least 4.5:1. Slots 1–4 are the prototype's, except light 3 and 4, which are darkened along their hue to reach 3:1.
  - Inline styles and the rules keep light values as `var()` fallbacks, for a page that sets some tokens but has no stylesheet.
  - **Text on other backgrounds.** `--ec-text-muted` has 4.6:1 against `--ec-surface` in light (5.2:1 in dark), so muted text (ticks, a table's headers, the motion switch's hint) passes WCAG 1.4.3 there, with little room. A page that puts a chart or a control on a darker background sets `--ec-text-muted` darker there, as the demo pages do for the motion switch, whose hint sits on the page ([a11y-audit.md](a11y-audit.md)).
  - **Forced colours** (Windows contrast themes). The browser replaces a page's text, background and border colours with the viewer's, but not SVG fills and strokes, so the marks, the chart's text and the focus ring keep the theme's colours, light or dark as `prefers-color-scheme` says. Two rules keep the rest in step: the legend's swatches opt out (`forced-color-adjust: none`), so they still match the marks, and the motion switch's pressed mode takes `Highlight` and `HighlightText`, since its tint is dropped and only its weight would be left. The visual suite checks both under Chromium's emulation (`tests/visual/a11y.spec.ts`).
- **Styles.** One stylesheet holds the tokens and the default rules, and the first chart, adapter or control on a page injects it (`<style data-expressive-charts>`, once per document). Everything else is set through the CSSOM, which a strict CSP allows. `configure()` sets two page-wide options, which are page-wide because the stylesheet is: an option on one chart would only count if that chart came first.
  - `configure({ nonce })` puts the nonce on the injected `<style>`, for a CSP with a `style-src` nonce.
  - `configure({ injectStyles: false })` injects nothing. The page loads `expressive-charts/style.css` (`dist/expressive-charts.css`) instead, for a CSP with no inline styles at all. The build writes that file from the same constant the charts inject, so they can't drift apart.
  - Call `configure()` before creating charts. The stylesheet stays when charts are destroyed, since others may share it.

### Limits

How many marks stay smooth, measured on `demo/stress.html` by `scripts/bench.mjs`. **Smooth** means a 95th-percentile frame interval of 20 ms or less, no frame over 50 ms, and a hover shown within 100 ms. Each case is measured alone on the page (`stress.html?case=…`), with the charts' defaults (legend, table, a name for every mark), on the real clock: the median of five fresh pages, unthrottled and with Chrome's 4× CPU slowdown (Lighthouse's stand-in for a mid-range phone). The machine: an Intel Core i7-12700KF, pinned to its performance cores, Windows 11, headless Chromium 156, a 1000 × 2000 viewport, on 23 October 2026.

| Case | Smooth up to | At 4× slowdown | Just past the limit (unthrottled) |
| --- | --- | --- | --- |
| A bar chart's staged update, every value changing, with or without `flash` | 100 bars | under 100 (100 bars: 50 ms frames) | 500 bars: 33 ms frames (50 with `flash`) |
| Hover, dimming every other bar | 1,000 bars, each hover shown within 28 ms | 500 | 2,000: a hover took 137 ms |
| A line on dates played into `reveal()`, with `threshold` and a riding icon: 1 or 2 series | 5 years of days | 1 year (1 series), under a year (2) | 10 years: 33 ms frames, some over 80 ms |
| The same, 3 or 4 series | 2 years | under a year | 5 years: 33 ms frames |
| D3 columns in a hand-written transition, followed by `watch` | 500 | 20 | 1,000: 50 ms frames |
| The same, `refresh()` once at the end | 1,000 | 100 | 2,000: 33 ms, a frame of 113 |
| A `chartSwitch` between bars and columns, `morph()` on every pair | 200 pairs | 20 | 500: 50 ms frames |

**The first draw** is one long task, so it's never smooth by that rule: 1,000 static columns show 86 ms after the call, 2,000 after 180 ms, 5,000 after 0.48 s and 10,000 after 1.0 s (at 4×, 0.5 s to 5.9 s). The line chart takes 57 ms for a year of days in two series, 380 ms for ten years, and 629 ms for ten years in four.

**Where the time goes.** A staged update redraws every bar on every frame: about 30 µs of script a bar (its geometry with `describe.bar`, about 40%; its attributes, 25%; its labels, 20%), then style, layout and paint. A line's play is mostly paint, and `threshold` redrawing its red runs (a quarter of the script, over ten years). The date axis's `Date` per vertex costs 0.09 ms a frame on ten years of days, so it's left as is.

**A page's other marks count.** With all six cases on the page, about 22,500 DOM nodes at their smallest sizes, every case paid about 5 ms more a frame, and at 4× none was smooth, not even 20 columns.

**Creating and destroying** each case's chart 50 times leaves no DOM node and no event listener behind.

## Build outputs

- `dist/index.js` + `dist/index.d.ts`: ES module for npm and bundlers, under the `import` condition.
- `dist/index.cjs` + `dist/index.d.cts`: CommonJS, under the `require` condition. The package is `"type": "module"`, so a `.d.ts` file describes an ES module: each entry's `require` condition has its own `.d.cts`, or a CommonJS project resolving with `node16` would be given ES module types for the `.cjs` file.
- `dist/expressive-charts.global.js`: script-tag bundle exposing `window.ExpressiveCharts`.
- `dist/expressive-charts.css`: the stylesheet the charts inject, as a file, exported as `expressive-charts/style.css` for pages that use `configure({ injectStyles: false })`. `package.json` lists CSS in `sideEffects`, so bundlers keep `import "expressive-charts/style.css"`, which imports no names; webpack would otherwise drop it. `src/package.test.ts` checks the patterns as bundlers read them, since the repo's own bundlers (Vite 8, esbuild) keep the import either way.
- `dist/expressive-charts.css.d.ts` and `.d.cts`: the stylesheet's types, an empty module, under its export's `import` and `require` conditions. TypeScript 6 and later check that a side-effect import finds something (`noUncheckedSideEffectImports`), so without them `import "expressive-charts/style.css"` is error TS2882. The export ends with a plain `default` to the CSS, since resolvers for CSS's own `@import` match neither `import` nor `require` (css-loader resolves with `style` only, Sass with `sass` and `style`); `src/package.test.ts` resolves it under those conditions. They're built from `src/style.css.ts` by a build of their own in `tsdown.config.ts`, which keeps only the declarations.
- `dist/icons/sport.js`, `.cjs`, `.d.ts` and `.d.cts`: the optional sport icon pack, imported as `expressive-charts/icons/sport`. It's a separate entry, so the core build doesn't carry the ball and cleat. The script-tag bundle doesn't include it.
- `dist/testing.js`, `.cjs`, `.d.ts` and `.d.cts`: the conformance suite for effect authors, imported as `expressive-charts/testing`. A separate entry, like the sport pack, and not in the script-tag bundle.
- **The build** is tsdown (`tsdown.config.ts`), on Rolldown, since M9 step 5; tsup built 0.1.0 to 0.3.0. Rolldown's oxc writes the declarations from each file alone, with no TypeScript, so every export in `src` has an explicit type, which `isolatedDeclarations` in `tsconfig.json` makes `typecheck` require. The sketches, the visual tests and the media scripts aren't built, so their tsconfigs turn it off. The config keeps tsup's output: JSDoc is left out of the scripts, since the declarations carry it; the CommonJS files and the script-tag bundle are in strict mode and set `__esModule`; and each CommonJS entry is a file of its own, where Rolldown would share chunks between them. The step built both ways and compared them: the same files but the chunks' names, the same names from each entry as an ES module and as CommonJS, every exported type identical (read with TypeScript 6's compiler API, both ways), and the sizes in [Bundle size](#bundle-size). On 0.3.0's code its tarball was 37 files, as tsup's, 1.36 MB packed and 5.07 MB unpacked. M10 step 5 took it to tsdown 0.23.3, pinned exactly, whose rolldown-plugin-dts is 0.28.8, a stable release, in place of 0.23.2's 0.29.0-beta.2, and M11 step 6 to 0.23.4, with the same plugin. Each time, built both ways on the same code, every file was byte for byte the same. The script-tag bundle leaves out the `/* @__PURE__ */` marks the other scripts keep for a page's bundler, since nothing tree-shakes it.
- **The package** is `dist/` and `CHANGELOG.md` (`files` in `package.json`), with the README, the licence and `package.json`, which npm always adds. 0.7.0's is 37 files, 1.6 MB packed and 6.0 MB unpacked, most of that source maps, which stay because bundlers and debuggers use them. `scripts/pack-check.mjs` installs the packed tarball in a new project and uses it from there: every entry imported in Node as ES modules and as CommonJS with no DOM, and a consumer typechecked with each TypeScript below, under `bundler`, `node16` (ES module) and `node16` (CommonJS), each reading its own declarations, the stylesheet's included. CI runs it after the build.
- **Types** need TypeScript 5.4 or newer, since they use `NoInfer`. The repository has three TypeScripts, dev dependencies pinned exactly (M8 step 5, and M9 step 5):
  - `typescript` (7.0.2), the native compiler, runs `typecheck`, by its path, since each of the three has a `tsc` and `npx tsc` could run any of them. The four projects take 1.1 to 1.5 s, against 6.8 s with 5.9.
  - `typescript-6` (`npm:typescript@6.0.3`) runs `src/api-docs.test.ts`, which reads the entries with TypeScript's JS API, and 7.0's package has none (its main export is its version).
  - `typescript-5.4` (`npm:typescript@5.4.5`), the oldest README promises, and the two above check the packed types in `pack-check`.
- **Releases** are published by `.github/workflows/release.yml` when a GitHub release whose tag is `v` and the version is published, with npm's provenance statement (`publishConfig` asks for it, with public access). It runs CI's checks first. CONTRIBUTING.md's Releasing has the steps and the authentication: a token for 0.1.0, and trusted publishing from 0.2.0.
- **The 0.x promise** in CHANGELOG.md names every value and type it covers. `src/promise.test.ts` names them all too, so a rename or a removal fails `typecheck`, and it checks that its list and CHANGELOG's match.
- **The API reference** is [api.md](api.md), with README as npm's landing page. `src/api-docs.test.ts` reads every entry's exports, values and types, with TypeScript 6's compiler API, and fails when one has no entry in api.md, an entry names no export, or the entries api.md marks as under the promise aren't CHANGELOG's. It type-checks every code example in README, and every example in api.md that imports the package, against the source with the repository's compiler options, declaring the page's own names (its rows, its D3 selections) in one place. README's links must be absolute, since npm shows it away from the repository, and the links in both must find their files and headings.

**tsdown's sizes.** Rolldown bundles differently from esbuild, which tsup used. On 0.3.0's code (M9 step 5), the script-tag bundle was 6.6 KB smaller gzipped, and the ES module entries shared less: `sport.js` loaded 4.0 KB, not 9.0, and `testing.js` 17.5, not 20.7. The two smallest import sets grew by 0.7 KB each. `animated` and `matrix` are now in `index.js` itself rather than a shared chunk, so a page that imports them keeps `index.js`'s top-level tables too (the stylesheet's text and the theme's tokens, the time axis's steps, the gaits' still pose), which a bundler can't prove free of side effects. Their budgets went up to 3 and 5 KB, and the script-tag bundle's, `sport.js`'s and `testing.js`'s came down to their sizes plus 10%.

**Values built at import.** A bundler keeps a statement at a module's top level that it can't prove free of side effects, such as a call, a template with values in it or a spread, even in a page that uses nothing from it. Since M10 step 5, the values `index.js` builds that way are in calls marked `/* @__PURE__ */`, which a bundler drops when nothing uses them: the theme's tokens and the stylesheet's text (`theme.ts`), the time axis's steps (`time.ts`), the gaits' still pose (`gaits.ts`), a walk's empty gaps (`walk.ts`) and the golden section `samplesAlong` narrows by (`samples.ts`). So a page that imports `motion` and `animated` keeps none of them: it's 1.7 KB gzip, as before tsdown, and one that imports `describe` and `matrix` is 0.74 KB smaller too. Their budgets came down to 2 and 7.5 KB. The other import sets are up to 0.09 KB smaller, and `everything` is the same to the byte. The marks are comments, which the unminified files keep for a page's bundler, so `index.js` and `index.cjs` are about 50 bytes bigger gzipped. The script-tag bundle leaves all of them out, Rolldown's own too, and is about 0.2 KB smaller. A new value built at the top level of a module needs the same, or the small sets carry it.

Bundlers keep only what a page imports, because `package.json`'s `sideEffects` names only CSS and `src/package.test.ts` checks that every JS entry is free of side effects. So the package has no `/core` or `/effects` entry: neither would make a page smaller. A change that breaks tree-shaking grows the small sets and fails the check.
